Оба контейнера жили параллельно около минуты. Всё, что старый успел выпустить в эту минуту, для нового не существовало: восстановление из таблицы выполняется один раз на старте.

Это не истечение срока (`PROPOSAL_LIFETIME_MINUTES` не задан → 720 мин), не чужой секрет (строки `[proposal] wrong secret` нет) и не «подтверждено ранее» (строка `[proposal] confirm` отсутствует).

## Что изменено

- `tg-proposals.ts`: `claimAcrossDeploy(who, id, secret, intent)`. Горячий путь — как прежде, по памяти. При промахе — читается строка из таблицы; если она выпущена, не истекла и принадлежит нажавшему, она принимается в очередь по правилам рестарта (одна карточка на человека, новее побеждает) и `claim` повторяется с тем же секретом. Ни один секрет из процесса не выходит: в строке — только дайджест.
- Зеркальный случай: строка удалена (карточку уже нажали в другом контейнере), а в памяти осталась копия с верным дайджестом → отказ, не вторая отправка.
- Недоступная БД не блокирует нажатие: остаётся прежний вердикт по памяти, в лог уходит `store.load failed`.
- `proposal-store.ts`: у хранилища появился `load(id)` — один `SELECT … WHERE id = $1`, только на нажатии.
- `render-server.ts`: маршруты `/api/tg/proposal/confirm` и `/cancel` идут через `claimAcrossDeploy`.
- Диагностика без секретов: `[proposal] recovered id=… who=…`, `[proposal] miss id=… who=…: no row, no draft`, `[proposal] stale draft id=…: row gone, not sending twice`.

Тесты: `apps/vibee-editor/render/cards-survive-a-deploy.test.ts` (раздел «a card minted by the other container during a deploy», 13 тестов), `invoice-orphans.test.ts` (маршрут отмены).
