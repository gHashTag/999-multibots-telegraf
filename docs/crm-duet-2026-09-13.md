# Дуэт продавец↔покупатель в реальном Telegram — 2026-09-13

Спецификация (первоисточник логики, английский): `t27/specs/automation/crm-duet.t27`.
Этот файл — локализованная сводка и урок; при расхождении прав спек.

## Что сделано

- Инструменты рендера `crm_duet` и `crm_duet_status` (`apps/vibee-editor/render/src/agent/crm-duet-tool.ts`),
  только для владельца платформы.
- `crm_duet` запускает в фоне реальный диалог: агент-продавец (`runAgent` с контекстом владельца,
  surface `business` — без кнопок-маркеров, с продажным плейбуком) пишет от сессии @t27_dev
  подключённому продавцу в роли **нового покупателя** (по умолчанию 435572800, @playom);
  за покупателя отвечает модель-персона одним обычным запросом к `resolveProvider()` — и ответ
  уходит **от её сессии**. Оба аккаунта берутся из `tg_sessions`.
- Контент — для её реальной игры «Лила Чакра»: в бриф продавца и в персону покупателя зашит один
  и тот же канон (72 плана, вход с шестёрки, правила `classic`, мини-апп t27.ai/leela,
  бот @leela_chakra_ai_bot, редакционная мысль месяца, форма материалов).
- Успешная генерация (`{ сделано: true, url }`) пересылается покупателю файлом; если Telegram
  не берёт файл по ссылке — уходит ссылка текстом.
- Отчёт: транскрипт, покрытие инструментов `имя → ok/вызовов`, число файлов, число платных
  генераций, нарушения брифа (вызовы `tg_*`/`crm_*` продавцом). По окончании отчёт уходит
  владельцу в Избранное от его же сессии. `dry_run=true` — агенты говорят, в Telegram пусто.
- Тесты: `apps/vibee-editor/render/crm-duet.test.ts` — 12 (очерёдность и адресация отправок,
  бриф в истории, медиа и платный счётчик, dry_run, молчащий продавец, сбой отправки, нарушение
  брифа, срез маркеров, помощники, гейты инструментов).

## Почему продавец пишет первым

Бизнес-бот в продакшене отвечает на любую личку владельцу, но замолкает на
`OWNER_TAKEOVER_MS` (30 минут) после сообщения, которое владелец написал сам. Дуэт, открытый
от сессии владельца, ставит бизнес-бота на паузу — ответы покупателю даёт агент дуэта, а не оба
сразу. Если бы первой писала покупательница, был бы гонка и двойной ответ.

## Почему это исключение из правила кнопок

Обычный путь отправки — карточка-предложение и кнопка владельца. Здесь владелец разрешает весь
прогон заранее (подтверждение в чате перед каждым запуском), инструмент только его, обе учётки
подключены самими людьми (строка в `tg_sessions` — согласие), транскрипт возвращается, строки
сессий — никогда.

## Статус утверждений

- Инструменты написаны и покрыты тестами с подменами — **проверено локально**.
- Лимит платных генераций (одна на реплику, три на прогон) — **мягкий**, задан брифом и измеряется
  в отчёте; жёсткого ограничения в коде нет (`PAID_CAP_IS_HARD = false`).
- Живой прогон **не выполнялся** на момент написания (`DUET_RAN_LIVE = false`): доказательство —
  `crm_duet_status` реального запуска, не этот документ.
- Ответ модели-покупателя зависит от провайдера; форма ответа `choices[0].message.content` —
  OpenAI-совместимая, как у остальных вызовов в `chat.ts`.

## Урок

Два агента в одном реальном чате — это прежде всего вопрос, **кто ещё** пишет в этот чат: без
учёта паузы бизнес-бота покупательница получила бы два разных ответа на одно сообщение.

## Live run 2026-09-13 — lesson: buyer model must walk the provider chain

- `duet-mtzmbvu1` (buyer 435572800, turns 4, real send): seller's first line was
  delivered, then `failed` with `buyer model HTTP 404`. Paid generations 0, media 0.
- Root cause: the buyer's voice called only `resolveProvider()` (first provider),
  while the seller agent iterates `allProviders()` with fallback. In the same
  process the first endpoint answered 404 and the seller never noticed.
- Fix: `askBuyerModel()` walks `allProviders()` in order, records `diagnose()`
  per failed provider, and fails only when all fail (error names each provider).
- Same day, both GramJS sessions had been revoked by `AUTH_KEY_DUPLICATED`;
  owner re-login went through the mini app (Профиль → Агент → Подключить
  Telegram, code from the «Telegram» service chat, cloud password typed by the
  owner). The buyer session recovered after that without a separate re-login
  (`crm_agent_link` handshake passed at 16:1x +07).

## Урок 3 — «empty answer» от GLM: покупатель думал вместо того, чтобы отвечать (2026-09-13)

Третий живой запуск `duet-mtznc1ri` прошёл три реплики (приветствие продавца → покупатель выбрал «текст поста» → продавец прислал пост про 72 плана «Лила Чакры») и упал на четвёртой:
`buyer model: nemotron: 404 «page not found» (базовый адрес провайдера); zai: empty answer; zai-lite: empty answer`.

Причина «empty answer»: у GLM режим размышления включён по умолчанию, а запрос покупателя шёл без `stream` и с `max_tokens: 400`. Когда в промпт попал длинный пост продавца, весь бюджет ушёл в `reasoning_content`, а `content` вернулся пустым — 200 OK без ответа. Первая реплика покупателя была короткой и успела уложиться, поэтому сбой проявился только на второй.

Исправление: для GLM (`zai`, `zai-lite`) покупатель шлёт `thinking: {type: 'disabled'}`, бюджет `max_tokens: 600`; ответ с одним `reasoning_content` без `content` фиксируется как `reasoning only, no answer`, а не как безликое «empty answer». Провайдеры, не знающие поля `thinking`, его не получают.

Отдельно: `nemotron` отвечает `404 page not found` на `/chat/completions`. Проверено 2026-09-13: `NVIDIA_BASE_URL` в Railway **не задан** (работает умолчание `https://integrate.api.nvidia.com/v1`), `GET /v1/models` отдаёт каталог, POST с ключом на тот же путь отвечает по модели (410 для снятой) — то есть путь верный, а голый «404 page not found» на POST — симптом со стороны аккаунта NVIDIA (в ветках форума NVIDIA он совпадает с отсутствием разрешения «Public API Endpoints» у организации ключа). Чинится в кабинете build.nvidia.com владельцем, не кодом; та же ошибка видна в `[media-library] could not describe …`.

Урок про честность агента: второй «запуск» (`duet-h6bmy2mg`) агент чата **выдумал** — id не декодируется из `Date.now().toString(36)` в текущее время (даёт 2012 год), инструмент не вызывался, в Telegram ничего не ушло, а «статус running, 3 реплики, фото отправлено» был сочинён. Проверка подлинности: id дуэта = base36 от времени запуска; в интерфейсе у реального вызова есть чип `⚙ crm_duet`. Запускать инструмент нужно явной формулировкой «вызови инструмент crm_duet с аргументами {...} и верни сырой JSON».
