# CRM для нескольких продавцов: @t27_dev и @playom — 2026-09-13

Спецификация (первоисточник логики, английский): `t27/specs/automation/crm-sellers.t27`.
Этот файл — локализованная сводка и урок; при расхождении прав спек.

## Что было измерено

- В Postgres рендера (Railway `Postgres-NFrq`, таблица `tg_sessions`) на 2026-09-13 ровно две строки:
  `144022504` (@t27_dev, владелец платформы, подключён 2026-09-07) и `435572800` (@playom,
  подключён 2026-09-09). Длина строки сессии — 369 символов у обоих. Сами строки никуда не
  копировались и не печатались.
- Сессия для инструментов уже бралась **по id вызывающего** (`сессияДля` → `прочитатьСессию`),
  данные CRM уже были разделены по `owner_id = telegram_id вызывающего`. То есть вход через
  GramJS для обоих аккаунтов действительно был настроен — не работал только **гейт**.

## Что мешало

- `requireOwner(ctx)` сравнивал вызывающего с одним id из окружения (`OWNER_TELEGRAM_ID`) в семи
  инструментах: `crm_leads`, `crm_lead_context`, `crm_ingest_chats`, `crm_summary`, `crm_offer`,
  `crm_deliver_photo`. @playom получал «аккаунт принадлежит владельцу».
- Плейбук продаж (`salesPlaybook`) показывался только владельцу.
- Проверка «предложение самому себе» в `crm_offer` сравнивала адресата с владельцем, а не с вызывающим.
- Проактивный обход (`crm-proactive-sweep`, каждые 30 минут) шёл ровно для одного `ownerId`.

## Что сделано

- Рендер: `requireSeller(ctx)` (async) вместо `requireOwner` в инструментах CRM. Продавец — тот, у
  кого есть строка в `tg_sessions` по его подтверждённому id; владелец платформы допускается всегда
  (его сессия — строка в таблице или `TELEGRAM_SESSION_STRING`). Отказ называет действие:
  «подключите аккаунт в приложении».
- Плейбук: `salesPlaybook({ ..., seller })` — флаг считается один раз за ход в `chat.ts` через
  `isSeller(ctx)`; сама функция осталась синхронной.
- `crm_offer`: самопредложение проверяется против вызывающего.
- Новый инструмент `crm_sellers` (только владелец): список `telegram_id` + дата подключения,
  с `probe=true` — живость каждой сессии через `checkAuthorization`. Строки сессий не возвращает.
- Бот: `resolveSellers` — список из `CRM_PROACTIVE_OWNERS` (если задан), иначе `crm_sellers` с
  рендера от имени владельца, иначе только владелец. `runProactiveTickAll` идёт по продавцам
  **последовательно** (одно MTProto-соединение за раз); используется и Inngest-кроном, и таймером.
  Ежедневный план уходит в чат каждого продавца.
- Тесты: `apps/vibee-editor/render/crm-sellers.test.ts`, `src/__tests__/services/crmSellers.test.ts`;
  `crm-owner-gate.test.ts` теперь разрешает гейту ровно одно чтение — собственную строку вызывающего
  в `tg_sessions` (любой другой запрос до проверки — по-прежнему провал).

## Что НЕ проверено

- Живость обеих сессий (`checkAuthorization`) — измерено только существование строк. Проверка:
  после деплоя владелец вызывает `crm_sellers` с `probe=true`.
- @playom должен хотя бы раз открыть бота-носителя (`CRM_PROACTIVE_BOT`, по умолчанию первый бот),
  иначе карточки и план ему физически не доставить (Telegram не даёт боту писать первым).
- `CRM_PROACTIVE_OWNERS` в Railway не задавался: по умолчанию список берётся с рендера на каждом тике.

## Урок

Гейт «только владелец» имел смысл, пока сессия была одна на сервис. Как только сессия стала
per-caller, гейт перестал что-либо защищать и начал отказывать тем, кого приглашает экран входа.
Правило: гейт должен читать тот же источник правды, что и данные (здесь — строку вызывающего в
`tg_sessions`), а не второй список, который разъедется.
