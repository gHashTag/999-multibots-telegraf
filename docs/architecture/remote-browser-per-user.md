# Удалённый браузер на каждого клиента: один браузер, два пульта

**Решение по итогам Ф0, 2026-09-20.** Задача: у каждого клиента сервиса свой
рабочий браузер на нашей стороне, со своими логинами, которым он управляет
удалённо и который водит агент.

Всё, что ниже помечено числом, снято прогоном 2026-09-20, а не оценено. Сырой
лог — `remote-browser-f0-measurements.md` рядом.

---

## 1. Вердикт в одной фразе

Это **не два продукта, а один**: один Chromium в контейнере на клиента и два
канала к нему.

- **человеку** — видео по WebRTC в iframe мини-аппа: смотрит и в любой момент
  берёт руль;
- **агенту** — CDP в том же контейнере, за нашим MCP-фасадом.

Профиль, куки и залогиненные сессии общие, потому что браузер **один**. Отсюда
следует всё остальное, включая решение главной проблемы с паролями (§4).

Готовая основа для этого — **neko** (Apache-2.0, 22k звёзд, живой): его
документация прямо описывает оба режима — «persistent browser: own browser with
persistent cookies available anywhere» и «automated browser: install playwright
or puppeteer and automate tasks **while being able to actively intercept
them**». Второй режим — это и есть агент, работающий в том же браузере, который
видит человек.

## 2. Что измерено

|                           | Chromium+Xvfb    | **neko**             | neo .deb           |
| ------------------------- | ---------------- | -------------------- | ------------------ |
| Образ                     | 1.11 ГБ          | 2.2 ГБ               | 1.9 ГБ             |
| Холодный старт            | **1.56 с**       | **9.5 с**            | 51 с ⚠️            |
| Память в покое            | **215 МиБ**      | **743 МиБ**          | 1004 МиБ ⚠️        |
| Память, 5 тяжёлых вкладок | 730 МиБ          | —                    | 1.96 ГиБ ⚠️        |
| CPU в покое               | 1.4%             | **0.1–6%**           | 600% ⚠️            |
| Профиль после 5 сайтов    | 65 МБ            | —                    | 44 МБ              |
| Версия Chromium           | **153**          | —                    | 151                |
| MCP для агента            | нет (и не нужен) | нет (другой принцип) | **не запускается** |

⚠️ — neo мерян под эмуляцией x86 на arm64; старт, CPU и отчасти память там
завышены кратно. Chromium и neko меряны нативно — эти числа настоящие.

**Три вывода, на которых стоит вся конструкция.**

**CPU в покое почти ноль.** Первый прогон neko показал 228%, и это выглядело
как приговор экономике — постоянно работающий видеокодер. Перемер на пустой
машине не подтвердил: 0.11–6.05% в четырёх замерах подряд. Те 228% были шумом
от эмулированного соседа. Значит **гасить сессию по простою можно**, и платить
надо за активные минуты, а не за сто включённых браузеров.

**Старт 9.5 секунды.** Нажал кнопку — досчитал до десяти — браузер твой. Это
делает гашение по простою не компромиссом, а нормой. Голый Chromium стартует за
1.56 с; разница в 8 секунд — цена полного десктопа внутри (supervisord, Xorg,
openbox, pulseaudio, WebRTC-пайплайн), и она же цена того, что человек видит
экран.

**Цена «человек видит и трогает» = +528 МиБ.** 743 против 215 МиБ. Это честная
строка в смете, а не накладные расходы, которые можно оптимизировать.

### 2.1 Побочные находки, которые сэкономят день

**Headful Chromium игнорирует `--remote-debugging-address`** и слушает CDP
только на loopback. Опубликованный наружу порт молчит при полностью живом
контейнере. Пробрасывать внутри пода (socat) — и наружу всё равно не отдавать
(§4.1).

**У MCP-порта neo нет авторизации.** `initialize` без заголовка `Authorization`
прошёл и вернул `serverInfo: browseros-neo 0.0.54`; в ответе
`access-control-allow-origin: *`. Граница безопасности у neo — «это один
человек и его localhost».

## 3. Почему neo на сервер не едет

Пакет распакован, собран и запущен. Браузер **работает**: `browserclaw`, 10
процессов, CDP отвечает `Chrome/151.0.8162.137`. А MCP-сервер — то
единственное, ради чего neo и берут, — не стартует вовсе:

    browseros-claw-server: /lib/x86_64-linux-gnu/libc.so.6:
      version `GLIBC_2.38' not found
      version `GLIBC_2.39' not found

В Debian 12 glibc 2.36. Пакет при этом **заявляет `Depends: libc6 (>= 2.31)`** —
то есть зависимость в `.deb` указана неверно. Вот чем «Linux-сборки нет» (слова
вендора в его же документации) оборачивается на практике: артефакт лежит,
ставится, наполовину работает и врёт о своих зависимостях.

Проверено дальше: бинарник MCP-сервера **исполняется** на Ubuntu 24.04
(glibc 2.39) — `browseros-claw-server --help` отвечает нормально. То есть
сломана именно декларация зависимостей, а не сам сервер. Но довести проверку до
конца — «MCP поднялся и слушает порт» — не удалось: на Ubuntu 24.04 под
эмуляцией упал уже сам браузер. **Вопрос остаётся недоказанным в обе стороны**,
и на выбор это не влияет: даже работающий MCP не даёт того, ради чего всё
затеяно, — канала, по которому человек видит свой браузер и берёт руль.

Плюс к этому: Chromium **151** против **153** у ванильного, образ 1.9 против
1.11 ГБ, лицензия AGPL-3.0 (сетевой сервис порождает обязательства по
исходникам), обновления — ждать, пока вендор выложит следующий неподдерживаемый
`.deb`.

**Что от neo забираем бесплатно: имена его инструментов.** Наш MCP-фасад
говорит `navigate`, `snapshot`, `act`, `read`, `run`, `screenshot`, `tabs`.
Тогда агентам всё равно, где браузер — локальный neo и наша комната
взаимозаменяемы, — а движок под фасадом меняется без единой правки у клиентов.

## 3.1 Linux в браузере — проверено отдельно

Идея «эмулировать Linux прямо в браузере клиента» технически реальна: WebVM на
CheerpX (x86→WASM JIT) поднимает Debian с shell, есть вариант с Xorg и i3, сеть
через Tailscale. Замерено в нём:

|                     | WebVM                    | нативно (M1) |
| ------------------- | ------------------------ | ------------ |
| Ядер                | **1**                    | 8            |
| Память              | **700 МБ на всю машину** | 16 ГБ        |
| awk, 3·10⁶ итераций | **4.086 s**              | 0.408 s      |

700 МБ — меньше, чем Chromium просит **в покое** (215 МиБ и 16 процессов), и
втрое меньше, чем под нагрузкой (730 МиБ). Браузер внутрь не помещается, и
упрётся он в память раньше, чем в скорость.

Но верная половина идеи остаётся и стала основой решения: **пользователь должен
видеть свой Linux в своей вкладке.** Просто Linux крутится в контейнере, а во
вкладку идёт картинка — §1.

## 4. Безопасность

### 4.1 Правило 1. Порт браузера не смотрит наружу. Никогда

Измерено: у MCP neo авторизации нет. У CDP — тем более: кто дотянулся до CDP,
тот читает все куки и действует от имени человека. Наружу смотрит только
брокер, по токену сессии. Между брокером и подом — приватная сеть.

### 4.2 Правило 2. Один клиент = один под = один профиль

Общий браузер ради экономии — это утечка кук между клиентами, то есть чужой
аккаунт в руках чужого человека. Под гибнет вместе с сессией, том шифрованный,
при удалении сессии затирается.

### 4.3 Правило 3. Браузер не видит нашу сеть

Выход только через egress-proxy. Закрыты RFC1918, `169.254.169.254`,
приватная сеть Railway, Postgres, наши API. Агент читает страницы, а страница —
недоверенные данные; текст на ней, говорящий «сходи по внутреннему адресу», не
должен иметь физической возможности сработать.

### 4.4 Правило 4. Пароль не видит ни агент, ни мы

**В этой схеме правило выполняется по построению, а не по регламенту.**

Клиент открывает свою комнату, видит браузер и **сам** вводит логин, пароль и
код из SMS — а через провод идёт **только видео**. Куки остаются внутри
контейнера и на нашу сторону не пересекают границу вообще. Это свойство самого
neko («sensitive data like cookies are not transferred — only video is
shared»), а не наша договорённость, которую можно нарушить правкой кода.

Мы храним **зашифрованный профиль**, а не пароли. Исходная постановка — «юзер
передаёт креды через агента» — была опасна ровно тем, что пароль шёл бы через
контекст модели, логи провайдера, стенограмму и скриншоты. Здесь этой дороги
просто нет.

Остаётся честно понимать: **храня куки клиента, мы храним его аккаунты.**
Шифрование на покое, ротация ключей, отдельный доступ к хранилищу и план на
компрометацию нужны до первого платящего клиента.

### 4.5 Агент — доверенное лицо, и этим пользуются

| Класс действия      | Примеры                                                                                | Кто разрешает                                                |
| ------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| чтение              | открыть, прочитать, найти                                                              | агент, в пределах списка доменов                             |
| изменение состояния | черновик, фильтр, настройка вида                                                       | агент, запись в аудит                                        |
| **необратимое**     | отправить, опубликовать, заплатить, удалить, сменить настройки аккаунта, выдать доступ | **только человек**, кнопкой, с показом что именно произойдёт |

CAPTCHA не решаем ни сами, ни сервисами. Обход антибота не обещаем. Вход в
чужие аккаунты не поддерживаем — только свои.

### 4.6 Аудит и рубильник

Append-only журнал на сессию: каждый вызов инструмента, URL, класс действия,
кто подтвердил необратимое, скриншоты «до/после». Клиент видит свой журнал и
может переиграть сессию. Когда клиент скажет «ваш бот написал это моим
клиентам», ответом должна быть запись, а не воспоминание.

Рубильник в одно нажатие: погасить сессию, стереть профиль, разлогинить везде.
Такой же — у оператора, на одного клиента и на всех сразу.

### 4.7 Юридическое, что нельзя откладывать

- **AGPL** у neo — ещё одна причина не брать его в основу; у neko Apache-2.0.
- **152-ФЗ / GDPR**: мы обрабатываем персональные данные и фактически средства
  доступа. Согласие, политика, срок хранения, юрисдикция профилей.
- **Правила сайтов.** Автоматизация соцсетей и банков нарушает их условия;
  устойчивость здесь обещать нельзя. Датацентровый IP = баны аккаунтов клиента.

## 5. Деньги

Считать надо не браузер, а **простой**.

    цена ≈ активные минуты × (тариф ГБ·мин + тариф vCPU·мин)
         + хранение профиля × все клиенты, всегда

Профиль ~65 МБ на клиента после пяти сайтов — хранится всегда. Машина — только
пока работает. При старте 9.5 с и CPU в простое около нуля гашение через 10
минут превращает «сто всегда включённых браузеров» в «пять одновременно
работающих». Сто постоянно живых комнат по 743 МиБ — это 74 ГБ памяти 24/7 за
воздух; пять активных — 3.7 ГБ.

Отсюда тариф клиенту: не «браузер в месяц», а **минуты активной сессии**, из
того же кошелька `user_tokens` (см. `single-wallet-decision.md`).

## 6. Где это живёт

**Пульт — Railway** (брокер, аудит, биллинг, выдача iframe): там уже всё.

**Браузеры — не Railway**, и теперь причина не абстрактная: neko требует
диапазон UDP-портов под WebRTC (в его же compose — 52000-52100), на Railway его
не пробросить; плюс нет API эфемерных машин, том привязан к сервису, а все
сервисы проекта видят друг друга по приватной сети — ровно то, чего браузеру
видеть нельзя (§4.3). Плоскость браузеров — площадка с API машин, по
совокупности **Fly Machines**.

## 7. План

**Ф1 — одна комната для владельца.** Ничего не храним.

1. Образ `ghcr.io/m1k1o/neko/chromium` + включённый CDP внутри (наружу не
   отдавать никогда).
2. Брокер на Railway: Telegram initData → токен сессии → поднять машину →
   отдать iframe.
3. Вкладка в мини-аппе с этим iframe.
4. Владелец сам заходит в свой аккаунт руками, в видео. Проверяем, что агент
   через MCP-фасад видит его залогиненным.

Если пункт 4 работает — всё остальное достраивается поверх и основу не трогает.

**Ф2 — действия.** Классы действий, подтверждения необратимого в мини-аппе,
аудит с переигрыванием.

**Ф3 — многоарендность.** Пул машин, гашение по простою, шифрованный профиль в
объектном хранилище, списание минут, рубильник, лимиты.

**Ф4 — хранилище кредов.** Только если Ф1–Ф3 покажут, что личный вход задачу не
закрывает. Конвертное шифрование, подстановка внутри пода, редактирование в
аудите.

## 8. Чего мы не делаем

- Не выставляем CDP и MCP-порт наружу — ни «временно», ни «за паролем nginx».
- Не делаем один браузер на нескольких клиентов.
- Не пропускаем пароли через контекст модели и не просим прислать их в чат.
- Не решаем CAPTCHA и не продаём обход антибота.
- Не строим на neo-Linux как на поддерживаемой платформе.
- Не пытаемся запускать браузер внутри WASM-Linux в браузере клиента.

## 10. Ф1, пункт 2 — брокер, 2026-09-20

`POST|GET|DELETE /api/browser/session` в render-сервере. Четыре модуля, ни один
длиннее 214 строк, вся логика чистая и проверяемая без докера:

| файл                        | что делает                                               |
| --------------------------- | -------------------------------------------------------- |
| `src/browser/routes.ts`     | кто спросил, есть ли у него браузер, поднять если нет    |
| `src/browser/sessions.ts`   | одна строка на человека в `browser_sessions`             |
| `src/browser/pod-driver.ts` | интерфейс площадки + драйвер docker                      |
| `src/browser/wire.ts`       | единственное место, знающее про `process.env` и оболочку |

Четыре решения, которые несут вес:

**Одна строка на человека — это PRIMARY KEY, а не дисциплина.** `telegram_id`
первичный ключ `browser_sessions`, поэтому «один клиент = один под = один
профиль» держит база, а не память программиста. Второй под тому же человеку —
второй набор кук к тем же аккаунтам; общий под — куки одного в руках другого.
Схема отказывает обоим.

**Адрес пода не уезжает клиенту.** Ответ несёт `viewUrl` — путь через нас и
токен, — и никогда `podId`, `host:port` или админский токен. Проверено тестом,
который сериализует ответ и ищет в нём эти строки.

**Два разных токена.** Токен просмотра — это и есть пароль человека в комнате,
так что «смотреть» и «держать токен» — одно и то же, общего пароля нет.
Админский токен другой и остаётся на сервере: клиент не должен перенастраивать
браузер, за который отвечаем мы. Проверено живьём: чужой токен получает 401.

**Строка в базе — это утверждение, а не факт.** Перед тем как повторить
клиенту «live», брокер спрашивает драйвер, жив ли под. Иначе мини-апп показал
бы человеку окно в несуществующий браузер, а вопрос «есть ли у меня браузер»
отвечал бы «да» вечно.

### Проверено

- 16 тестов, все зелёные; полный прогон render — **218 файлов, 2307 тестов**.
- **Семь мутаций в `routes.ts` — все пойманы** (снят чек личности, утёк
  `podId`, утёк админский токен, перестал переиспользоваться живой под, мёртвый
  под выдан за живой, осталась строка при провале старта, рубильник начал
  падать на ошибке драйвера). Файл после прогона восстановлен побайтово.

## 11. Ф1, пункт 3 — прокси `/live/:sessionId`, 2026-09-20

Дыра закрыта: путь, который выдавал брокер, теперь существует и охраняется.

| файл                        | что делает                              |
| --------------------------- | --------------------------------------- |
| `src/browser/live-proxy.ts` | решение: кто стучится и можно ли ему    |
| `src/browser/live-pipe.ts`  | байты: HTTP, апгрейд WebSocket, подмены |

Разделение намеренное: решение чистое и проверяется мутациями, труба — та
часть, которую без сокетов не проверить.

### Путь, а не поддомен

Замерено на живом поде: neko просит ресурсы **относительными** путями, а адрес
сокета и базу REST строит от `location.pathname`:

    location.protocol.replace(/^http/,"ws") + "//" + location.host
      + location.pathname.replace(/\/$/,"") + "/ws"

Значит страница, отданная по `/live/<id>/`, сама просит `/live/<id>/ws`. Ни
переписывания, ни wildcard-DNS, ни сертификата на сессию.

### Токен живёт один переход

Он приходит один раз в строке запроса и сразу меняется на куку, привязанную к
`/live/<id>`, с редиректом на чистый адрес. Токен, повторённый в адресе каждого
ресурса и сокета, осел бы в истории браузера, в `Referer` и в каждом логе по
дороге — а он открывает чужой залогиненный браузер.

### Пароль пода человек не вводит и не видит

Здесь вскрылось то, чего в планах не было. neko требует **свой** пароль, и
человеку пришлось бы вводить токен, которого он в глаза не видел. Решение:

1. Редирект ведёт на `?usr=you&pwd=<заглушка>` — в адресе **заглушка**.
2. Прокси подменяет её настоящим токеном по дороге к поду.

Причём подменять пришлось **не тело POST**, как я сделал сначала, а строку
запроса сокета: страница отправляет пароль как
`new WebSocket(url + "?password=...&username=...")`, а `/api/login` neko зовёт
сам у себя. В его логе это видно буквально — `agent: Go-http-client`,
`module=legacy`. Обе подмены оставлены: REST-вход тоже существует.

И отдельная мелочь, которая стоила бы поддержки: neko вычищает `pwd` из адреса,
как только прочитает, поэтому **перезагрузка страницы возвращала форму пароля**.
Параметры выдаются теперь на каждую загрузку документа.

### Что ещё переписывается на лету

- **вверх** — наша кука `blive_<id>` срезается: она подтверждает человека НАМ, и
  поду незачем держать токен, открывающий его самого;
- **вниз** — куки пода перепривязываются с `Path=/` на путь сессии, чтобы вторая
  сессия в том же браузере не получила куку первой.

### Картинка: почему её сначала не было

Сигнализация через прокси пошла сразу, а изображения не было. Лог пода:

    ICE connection state changed: failed
    undeclaredMediaProcessor failed to open SrtpSession

Под предлагал ICE-кандидатов на своём адресе внутри контейнера. Лечится не
прокси, а драйвером: поду выдаётся **один мультиплексированный порт**,
публикуется на хосте **тем же номером** (номер уходит в кандидата) и
сообщается, какой адрес объявлять:

    NEKO_WEBRTC_UDPMUX=<порт>  NEKO_WEBRTC_TCPMUX=<порт>
    NEKO_WEBRTC_NAT1TO1=<адрес>       -p <порт>:<порт>/udp  -p <порт>:<порт>/tcp

После этого — «Подключено» и живой рабочий стол пода в браузере.

### Проверено

- Сквозной прогон против настоящего пода (`scripts/browser-live-e2e.ts`) —
  **10 из 10**: редирект, кука `HttpOnly`, адрес без токена, страница, ресурс по
  относительному пути, **апгрейд WebSocket 101**, отказ без куки (401), отказ с
  чужим токеном (404), отказ сокету без куки.
- Глазами: страница, «Подключено», поток рабочего стола.
- Юнит-тесты: 47 в двух файлах; полный прогон render — **218 файлов, 2337
  тестов**.
- **24 мутации за сессию, все пойманы.** Среди них: снят чек личности, утёк
  `podId`, утёк админский токен, мёртвый под выдан за живой, разрешён обход
  `..`, кука расширена на весь сайт, имя куки перестало зависеть от сессии,
  наша кука ушла поду, пароль перестал подменяться, набранный руками пароль
  затирался токеном, поду перестали сообщать адрес, медиа-порт опубликован
  другим номером.

### Чего всё ещё нет

- Простаивающие поды не гасятся.
- Профиль между сессиями не сохраняется: остановка теряет логины.

## 12. Ф1, пункт 4 — профиль переживает сессию, 2026-09-20

Без этого всё предыдущее бессмысленно: человек логинился бы заново каждый раз,
и «свои логины» оставались бы словами.

### Профиль принадлежит человеку, а не визиту

Отдельная таблица `browser_profiles`, а не колонка в `browser_sessions` —
потому что строка сессии **намеренно удаляется** при остановке пода, и
удалённый вместе с ней идентификатор профиля оставил бы на диске кучу чужих кук,
которую больше нечем назвать.

Идентификатор профиля **непрозрачный**, а не telegram_id: он попадает в имя
тома, в листинг бэкапа, в вывод `docker volume ls` — туда, куда оператор
смотрит мимоходом. Telegram_id там говорит, ЧЬИ это куки; случайный id не
говорит ничего. Связь остаётся в базе, где она и так под защитой.

### Две разные двери

|                               | что делает                                                |
| ----------------------------- | --------------------------------------------------------- |
| `DELETE /api/browser/session` | закрыть браузер, **логины оставить** — обычное действие   |
| `DELETE /api/browser/profile` | «забудьте меня»: погасить и **стереть диск** — необратимо |

Слить их в одну значило бы либо терять логины при каждом закрытии, либо иметь
красную кнопку, которая тихо оставляет куки на месте.

Порядок в «забудьте меня» тоже несущий: под гасится **до** стирания (иначе
стирание гонится с записями самого Chromium и оставляет полпрофиля — хуже обоих
исходов, потому что выглядит залогиненным и не является), а строка в базе
удаляется **после** (иначе при сбое остаётся безымянная куча чужих кук).

### Остановка обязана быть мягкой

`docker rm -f` — это SIGKILL. Chromium дописывает сессионные куки на диск при
**штатном** завершении, поэтому убитый браузер теряет ровно то, ради чего
профиль и существует. Драйвер теперь делает `docker stop -t 15`, и только потом
удаляет контейнер. Это не аккуратность, это и есть механизм сохранения.

### Проверено на настоящих подах

`scripts/browser-profile-check.ts` — под поднимается, ходит на страницу, гасится
мягко, поднимается **новый контейнер** на том же томе:

    ok  the first visit happened
        (stopped gracefully, container removed)
    ok  THE BROWSER STATE SURVIVED into a brand new container  -- matches in History: 2
    ok  the cookie store came with it
    ok  a different profile knows nothing about this person's browsing  -- matches: 0
    ok  wiping the profile removes the disk

Последняя проверка сверху — **контрольная**: свежий профиль ничего не знает о
чужом. Без неё «переживает» доказывалось бы и на сломанной изоляции.

Свидетель — собственная `History` Chromium, а не кука со стороннего сайта.
Причина измеренная: headful Chromium слушает CDP только на loopback **внутри**
контейнера, поэтому публикация 9222 ни к чему не ведёт и все команды идут через
`docker exec`; а кука требует сайта, который её выставит, то есть тянет в тест
интернет. `History` лежит в том же каталоге профиля и сбрасывается тем же
штатным завершением, что и `Cookies` — чьё наличие проверяется рядом.

### Мутации

7 правок, 6 пойманы сразу. **Одна выжила и оказалась ценнее остальных:** подмена
`ON CONFLICT DO NOTHING` на `DO UPDATE SET profile_id = ...` — в Postgres это
перезаписывало бы профиль при каждом визите, то есть теряло логины. Тест не
заметил, потому что **фейк базы не моделировал действие при конфликте**. Чинить
надо было двойника, а не тест; после этого мутация ловится.

Там же нашлась вторая слепота: фейк не знал про `UNIQUE (profile_id)`, который
Postgres обеспечивает, и пропустил бы коллизию — двух людей, указывающих на одну
кучу кук.

### Чего всё ещё нет

- Вкладка в мини-аппе и живая проверка владельцем — последние пункты Ф1.
- Простаивающие поды не гасятся.
- Сторона агента (MCP-фасад над CDP) не выставлена.
- **Шифрование тома на покое — не наше.** Код ничего не шифрует; это свойство
  площадки. Написано прямо в шапке `profiles.ts`, чтобы никто не решил иначе.

## 13. Ф1, пункт 5 — вкладка в мини-аппе, 2026-09-20

`/browser` в плеере. Три файла кода и три файла тестов:

| файл                                | что делает                                     |
| ----------------------------------- | ---------------------------------------------- |
| `player/src/pages/Browser.tsx`      | экран: состояние, запуск, просмотр, две кнопки |
| `player/src/lib/remoteBrowser.ts`   | одна дверь к `/api/browser/*`                  |
| `player/src/lib/remoteBrowserUi.ts` | два решения, вынесенные из JSX (см. ниже)      |

### Блокер, найденный до того, как он стал багом

`proxy_pass` в nginx плеера **нет**: мини-апп живёт на своём домене, рендер —
на `vibee-render-production.up.railway.app`. Значит кука сессии `SameSite=Lax`
в iframe **не отправляется вовсе** — рамка загрузилась бы и тут же получила
отказ. Ослабить до `SameSite=None` не помогает: Telegram на iOS — это
WKWebView, он сторонние куки режет по умолчанию.

Поэтому: `canEmbed()` сравнивает origin. Свой — показываем прямо в странице;
чужой — открываем **верхним уровнем**, где кука первой стороны и работает
везде. Функция начнёт возвращать `true` сама, как только приложение станет
проксировать `/live/` под своим origin, и менять в коде ничего не придётся.

**Следующий шаг по этой линии:** `location /live/` в
`apps/vibee-editor/nginx/default.conf.template` с проксированием на рендер и
заголовками апгрейда. Тогда браузер появится прямо во вкладке.

### Экран не спрашивает пароль. Это проверяется

Вся конструкция держится на том, что человек логинится сам, внутри картинки.
Поле пароля на этом экране — или строка, приглашающая прислать его — тихо
перевело бы учётные данные к нам и в контекст модели. Поэтому тест читает
**исходник страницы** и падает на `<input>`, на `type="password"`, и на
пропаже обещания «вы заходите сами» из любого из двух языков.

### Слепой грep, пойманный мутацией

Первая версия тестов грепала исходник на имена функций. Две мутации **выжили**:

- кнопка «закрыть», перепаянная на стирание профиля — оба имени в файле
  остаются, грep доволен, а логины пропадают при каждом закрытии;
- убранное подтверждение — слово `confirmForget` в файле остаётся, грep
  доволен, а одно нажатие стирает всё.

`@testing-library/react` в этом приложении нет **намеренно** (написано в
`src/test/setup.ts`), тащить его ради двух тестов неправильно. Вместо этого оба
решения вынесены из JSX в `remoteBrowserUi.ts`: `BROWSER_BUTTONS` (две кнопки —
две разные двери) и `tapWipe` (**первое нажатие никогда не стирает**). Теперь
это обычные функции с обычными тестами, а контрактный тест страницы проверяет,
что экран ходит через них, а не мимо.

После правки **8 из 8 мутаций ловятся**.

### Найдено глазами, а не тестом

Страница открылась в обычном браузере и показала человеку фразу сервера:
**«no X-Api-Key and no Telegram initData»**. Технически верно, для человека —
мусор. 401 теперь такое же состояние, как 503: «откройте эту страницу из бота,
сначала нужно понять, кто вы». Тест на это добавлен, но нашёл это только
запуск.

### Проверено

- 19 тестов в трёх файлах; полный прогон плеера — 92 файла, 924 теста.
- `check:player-types` — **0 ошибок при пороге 0**.
- Все 15 строк интерфейса есть в обоих языках; проверяется тестом, а не глазами.

**Отдельно:** 6 тестов в `feed-card-text-clears-the-action-rail.test.ts` падают

### Чего всё ещё нет

- `location /live/` в nginx — после него iframe включится сам.

## 14. Вкладка в панели и слежение за агентом, 2026-09-20

`Браузер` с иконкой глобуса встала **сразу после «Агента»**: смотреть за

## 15. `/live/` под своим origin, и свечение агента, 2026-09-20

### nginx

`location /live/` в `apps/vibee-editor/nginx/default.conf.template` проксирует
зрителя на рендер-сервер **под origin самого приложения**. Это снимает то, ради
чего городился обходной путь: кука первой стороны, iframe работает, отдельная
вкладка больше не нужна.

Четыре вещи, которые пришлось знать:

**`map` можно объявить прямо здесь.** `Connection` обязан становиться
`upgrade` на апгрейде и не становиться на обычном запросе. `map` нельзя внутри
`server{}` — но файл кладётся в `conf.d/`, который nginx включает **внутрь
`http{}`**, поэтому объявление легло рядом.

**Подстановка переменных уже обезврежена до меня.** `envsubst '${PORT}'` идёт с
явным списком; без него `$scheme` и `$http_upgrade` были бы стёрты и директивы
молча осыпались. В entrypoint это написано прямым текстом — цена уже уплачена
кем-то раньше.

**Таймаут по умолчанию убил бы сессию.** Зритель молчит между нажатиями
минутами, а `proxy_read_timeout` по умолчанию 60 секунд. Поставлен час,
буферизация выключена — буфер добавляет задержку каждому кадру.

**Порядок блока имеет значение.** `location /live/` объявлен **после**
`location = /index.html`, потому что `tri-frame-ancestors.test.ts` в своём
отрицательном контроле называет «строку 2» и имеет в виду копию политики из
`/index.html`. Поставленный раньше, блок сдвигал нумерацию и ломал чужую
защиту.

Счётчик строк CSP в том тесте поднят с 2 до 3 и **оставлен счётчиком**: именно
он ловит УДАЛЕНИЕ строки, после которого половина маршрутов тихо перестала бы
пускать рамку.

Конфиг проверен `nginx -t` на настоящем образе nginx, а не на глаз.

### Клиент

Адрес зрителя теперь разрешается относительно **своего** origin. Тот же
маршрут добавлен в дев-прокси vite — иначе разработчик тестировал бы другую
форму, чем видит пользователь: здесь iframe, там отдельная вкладка.

`canEmbed` сохранён и остался честным: он ловит случай, когда сервер вернёт
абсолютный адрес на чужой origin. Такой не встраивается никогда — открывается
верхним уровнем.

### Свечение

Аура по краям кадра, когда в браузере работает агент, плюс плашка «Здесь
работает агент. Коснитесь экрана, чтобы взять управление».

**Рамка, а не накладка.** Смысл экрана — видеть каждый пиксель того, что делает
агент; затемняющий слой прятал бы ровно то, о чём сообщает.

**Гаснет от первого касания.** С этого момента управляет человек, и свечение,
продолжающее утверждать обратное, было бы ложью экрана. Проверяется тестом.

**Уважает просьбу о меньшем движении.** При `prefers-reduced-motion` цвет
остаётся, анимация выключается: движущаяся рамка рядом с человеком, который
попросил систему не двигать вещи, — не милая деталь, а триггер симптома.

**Честный триггер.** Свечение означает то, что приложение действительно знает:
появилась сессия, которую **этот экран не запускал**. Чего оно не знает —
кликает ли агент прямо сейчас; посекундного сигнала нет и не будет до
MCP-фасада над CDP. Это написано в шапке `agentWorking.ts`, чтобы свечение
никто не продал дороже, чем оно стоит.

Плашка сначала растягивалась во всю ширину телефона из-за `white-space: nowrap`
и длинной русской фразы — замерено на 375×812, исправлено, снято повторно.

## 16. Гашение простаивающих подов, 2026-09-20

Это вся экономика затеи: под держит ~743 МиБ в покое и поднимается за десять
секунд. Сто человек с постоянно живым подом — 74 ГБ памяти ни за что; те же
сто с гашением — столько, сколько реально работают.

### Ловушка, заложенная мной же двумя разделами раньше

Первая версия считала признаком жизни `last_seen_at`, который обновлялся в
GET-обработчике. **А мини-апп опрашивает этот маршрут каждые десять секунд**,
чтобы заметить начавшего работу агента. То есть у любого человека с открытым
приложением под жил бы вечно, и сборщик не нашёл бы ни одного кандидата.
Ошибка была в определении «простоя», а не в сборщике.

Теперь признак жизни — **открытый сокет зрителя**: он несёт клавиатуру и живёт,
пока открыта вкладка. Отметка ставится при апгрейде, раз в минуту пока сокет
жив, и один раз при закрытии — чтобы простой считался от момента, когда
смотреть перестали. Статусный опрос не считается использованием, и на это
написан тест.

### Что не гасится никогда

Сессия моложе двух минут, что бы ни говорили её отметки: под отвечает через
десять секунд, а человек может собраться минуту. Гашение в этом окне делает
«открыть мой браузер» неработающим по причине, которой не видно.

И **профиль не трогается**. Гашение закрывает браузер, оно никого не
разлогинивает — ради этого различия профили и живут в своей таблице.

### Мутации

6 правок. Одна выжила и оказалась поучительной: снятие защиты «слишком молод»
ничего не сломало, потому что при пороге в десять минут она **избыточна** —
`max(lastSeen, created)` спасает и без неё. Она нужна только тому, кто уменьшит
порог. Тест переписан так, чтобы проверять именно этот случай, плюс
отрицательный контроль, что защита не охраняет вечно.

Вторая выжившая — возврат `touchSession` в GET. Теста на «опрос не является
использованием» не было; теперь есть, вместе с отрицательным контролем, что
явный запуск использованием является.

### Проверено

- 10 тестов сборщика; полный прогон рендера — **219 файлов, 2359 тестов**,
  дважды подряд чисто.
- 6 из 6 мутаций ловятся.

## 17. Диагностика MCP: почему Королева этого не видела

По просьбе владельца. Ответ измерен, а не предположен.

### Что сломано

    BROKEN    inngest-dev    http   20 инструментов, 3 из 4 проверенных падают
    BROKEN    inngest-prod   stdio  13 инструментов, 3 из 3 падают
    OK        browseros-neo  http   20 инструментов

Оба Inngest отвечают `REST API v2 returned HTTP 401` на любой запрос данных.

**Причина — не проводка переменной, как казалось.** Ключ `INNGEST_SIGNING_KEY`
лежит в `.env` (77 символов, форма `signkey-prod-…`), в окружение MCP он не
попадает — но это не важно: взятый напрямую, он **отвергается тем же 401** во
всех трёх стандартных формах (как есть, без префикса, sha256 от hex). При этом
сервер жив: `/health` и публичный `/api/v2/operations` отдают 200, а
`/api/v2/apps` и `/api/v2/events` — 401 и с ключом, и без него.

Значит этот self-hosted Inngest не принимает наш ключ для REST v2 вовсе.
Починка — не переменная, а доступ от того, кто держит тот экземпляр.

### Почему Королева не увидела

Её доска — это **issues репозитория `gHashTag/t27`** (проверено: `/queen/public-board`
отдаёт `repo: gHashTag/t27` и карточки с номерами issue). У неё нет ни одного
канала про здоровье инструментов, и этот репозиторий — не её.

Она не проглядела. **У неё не было органа чувств.**

### Орган

`scripts/mcp-doctor.mjs`, `npm run mcp:doctor`. Спрашивает у каждого
настроенного сервера три разных вопроса, потому что три разные поломки снаружи
выглядят одинаково:

1. отвечает ли вообще;
2. отдаёт ли список инструментов (сервер может подняться и не дать ни одного);
3. **работают ли инструменты** — тот самый случай «перечислены и мертвы».

Зовёт только читающие инструменты: имя начинается с get/list/health/status/…
**и** нет обязательных аргументов. Эвристика названа прямо в шапке, потому что
она эвристика. Для серверов, у которых все читающие инструменты требуют
аргументы, есть карта объявленных проб — добавление записи туда есть
утверждение «этот инструмент не пишет».

`--json` даёт машинный отчёт: это то, что можно отдавать Королеве. Код возврата
1 при мёртвом или сломанном сервере — чтобы заметил и CI.

## 18. Бот сообщает, что агент начал работать, 2026-09-20

Самая дорогая из недостающих деталей. Сторож в мини-аппе замечает агента
**только пока приложение открыто** — а на телефоне оно закрыто почти всегда.
Агент мог десять минут работать в чужих залогиненных аккаунтах, и человек не
узнал бы. Всё построенное до этого было видно только тому, кто и так смотрит.

Теперь брокер отправляет сообщение с кнопкой «👁 Смотреть за агентом», ведущей
прямо во вкладку браузера.

### Только когда запустил НЕ человек

Сообщение через секунду после того, как человек сам нажал «открыть», — это шум,
а шум глушит канал вместе с тем единственным сообщением, которое было важным.

Различие настоящее, не угаданное: брокер знает, **через какую дверь** пришёл
вызов. Ключ агента — агент; подпись мини-аппа или сессия — человек.

Ради этого `chatIdentity` разделён на `identityWithSource` и обёртку над ним.
Порядок дверей (подпись → сессия → ключ) остался **в одном месте**: соседний
файл прямо предупреждает, что две копии проверки разойдутся, и однажды уже
разошлись.

### Отправка не может уронить браузер

Человек просил браузер, а не уведомление. Заблокированный бот, недоступный
Telegram — всё это не должно превращать работающий под в ошибку на экране.
Проверено тестом.

Сообщение уходит **после** того, как под поднялся: иначе кнопка вела бы в
браузер, которого ещё нет.

### Мутации

4 правки. Одна выжила и была поучительной: переименование `inline_keyboard` —
Telegram такую клавиатуру отвергает, кнопка исчезает молча, а тест смотрел
только на наличие адреса внутри JSON. Теперь проверяется форма: массив,
первая кнопка, `url` и непустой текст.

## 19. Сторона агента: инструменты в том же `/mcp`, 2026-09-20

Владелец спросил, почему агент не знает про браузер. Ответ был: **ему никто
его не предлагал**. Всё построенное до этого смотрело на человека.

Восемь инструментов — `browser_status`, `browser_open`, `browser_read`,
`browser_screenshot`, `browser_click`, `browser_type`, `browser_evaluate`,
`browser_close_tab` — добавлены **в тот же реестр `TOOLS`**, который каждый
агент и так читает через `/mcp`. Не второй сервер: агент, подключённый вчера,
видит их сегодня, ничего не настраивая. Отдельная точка входа была бы ещё одной
вещью, о которой никто не знает.

Агент водит ТОТ ЖЕ браузер, который смотрит человек. Не копию, не невидимого
близнеца: каждый клик виден, руль забирается в любой момент. Поэтому тут нет
«скрытого режима» и не будет.

Инструменты дотягиваются только до сессии **своего** `telegram_id`: аргумента
«чей браузер» не существует, поэтому назвать чужой нельзя.

### Три ловушки, каждая стоила прогона

**Политика Chromium запрещала отладчик.** В образе neko лежит
`"DeveloperToolsAvailability": 2`. Симптомов три, и ни один не называет
причину: HTTP-ручки CDP отвечают, `Browser.getVersion` отвечает,
`Target.attachToTarget` возвращает `Not allowed`, а сокет страницы принимает
подключение и молчит. Значение меняется на 1 правкой файла, чтобы остальные
ограничения образа остались.

**Сокет страницы не отвечает, браузерный отвечает.** Ходить надо на
`/devtools/browser/…` и прикрепляться `Target.attachToTarget({flatten:true})`,
адресуя вкладку по `sessionId`.

**CDP отдаёт адрес, по которому до него не достучаться** — свой loopback внутри
пода. Всякий адрес сокета переписывается на тот мост, через который пришли.

### Проверено живьём

    ok  the pod answers CDP through its bridge
    ok  browser_status sees a running browser
    ok  browser_open opened a page
    ok  browser_read reads the page the agent opened
    ok  browser_screenshot returns an image   -- 20 KB
    ok  browser_evaluate runs code in the page
    ok  click and type are accepted by the live browser

`scripts/browser-agent-check.ts`. Плюс 11 юнит-тестов на отказы и на то, что
агенту не выдаётся ни адрес пода, ни токен.

### Чего в фасаде нет, и это написано в его шапке

Ничего не спрашивает разрешения перед необратимым действием. Отправить,
заплатить, удалить — это один `browser_click`. Канал подтверждений (§4.5) не
построен, и до тех пор агент с этими инструментами доверен ровно настолько,
насколько человек ему доверяет.

## 20. Тормоз, которого агент не объедет, 2026-09-20

`browser_ask_permission` — тормоз, который агент тянет сам. Этот — тот, мимо
которого он не проедет.

### Правило о МЕСТЕ, а не о действии

Клик — это точка на экране, и снаружи страницы никак не узнать, написано на
ней «Далее» или «Отправить 120 000». Классифицировать действия значило бы
гадать, а гадающий страж хуже отсутствующего: он отказывает в безобидном и
пропускает разорительное, и люди учатся его обходить.

**Где мы находимся — знать можно.** Поэтому на почте, в банке, на странице
оплаты нажатие, набор текста и выполнение кода требуют разрешения, выданного
человеком в последние пять минут. На остальном вебе — а это почти весь веб —
агент работает свободно.

Чтение не ограничено нигде: смотреть, как агент читает, никого не пугает.

**Нечитаемый адрес считается чувствительным.** «Мы не знаем, где мы» не должно
быть ответом, который разрешает действовать.

**Отказ называет следующий шаг.** Агент, которому сказали просто «нет»,
попробует снова, попробует иначе и в конце концов попробует что-нибудь хуже.

### Чего это не обещает

Это не граница безопасности против враждебного агента: у кого есть
`browser_evaluate`, тот уйдёт куда угодно. Это защита от обычной беды —
уверенной модели в одном клике от «отправить не то и не тому» — и от страницы,
которая уговорила агента действовать.

### Мутации

6 правок. Одна выжила и показала слабость теста: расширение окна разрешения до
суток прошло, потому что тест брал срок **из самой константы** и рос вместе с
ней. Добавлен абсолютный предел и проверка «полчаса назад — уже не да».

## 21. Картинка на Railway: почему нужен TURN, 2026-09-20

Под на Railway создан, переменные заданы, TCP-прокси поднят:
`iriguchi.proxy.rlwy.net:19409 → 52000`. И тут документация neko отвечает
прямо:

> «expose the same ports to the host machine, **without any remapping**»

Прокси Railway именно ремапит, а `NAT1TO1` задаёт адрес и **не задаёт порт** —
номер уходит в ICE-кандидат, и клиент стучится не туда. Это не настройка,
которую мы забыли, а свойство площадки.

**Ответ — TURN.** Браузер и под оба подключаются НАРУЖУ к нему, и ни одному не
нужно быть доступным по предсказуемому порту. Это стандартное решение ровно
для такой сети. Конфигурация готова: `deployment/remote-browser/coturn.*`.

**Сборка пода на Railway при этом падает** мгновенно и логов не отдаёт —
ни через `railway logs --build`, ни по идентификатору развёртывания. Вслепую
это не чинится; нужен взгляд в панель.

## 23. Рабочий стол принимает форму устройства, 2026-09-20

Владелец прислал снимок: телефон стоймя, и на нём ландшафтный рабочий стол —
марка в чёрном поле, буквы втрое мельче нужного. В стилях стояло
`aspect-ratio: 16 / 10`, прибитое к поду, который всегда работал 1280x800.

**CSS тут не помогает.** Уменьшить картинку — не значит сделать текст на ней
читаемым. Поэтому меняется сам рабочий стол: телефону — высокий, планшету —
поквадратнее, ноутбуку — широкий. Страницы внутри верстаются под эту форму
своим размером шрифта, и поток приходит почти один к одному вместо двойной
пересборки.

### Направление важнее самого правила

Коробку задаёт **таблица стилей**, под подстраивается под неё. Наоборот было
бы дурной бесконечностью: коробка меняется вслед за подом, новая коробка
требует новой формы пода, и они гоняются друг за другом.

### Что измерено на живом поде, а не предположено

- API берёт **любой** размер, не только те, что перечисляет
  `/configurations`. Список — меню, не забор.
- X округляет ширину до кратной 8: просили 420 — стало 416, просили 375 —
  стало 384.
- **Ответ на POST — это повтор запроса.** Он сказал 420x880, когда экран был
  416x880. Правду говорит только последующий GET.
- Часть размеров отклоняется **молча**: 393x852 ответил 200 и оставил экран
  на месте.
- Часть — **честным 422** «cannot set screen size», и закономерности в этом
  нет. При высоте 852: 352 да, 360 нет, 368 нет, 376 да, 384 да. При ширине
  384: 600 нет, 640 нет, 664 да, дальше всё да.

Поэтому размер — не лотерея: сначала пробуется точная форма, а когда под
отказывает, берётся ближайшая из **его собственного** списка. Ближайшая **по
форме**, не по площади: чёрные поля — это целиком вопрос соотношения сторон.
Две попытки, без гадания.

### Проверено глазами и замером

| устройство      | просили  | под стал           | чёрного поля |
| --------------- | -------- | ------------------ | ------------ |
| телефон стоймя  | 360x664  | 800x1600 (портрет) | **0%**       |
| телефон на боку | 760x320  | 640x360            | **0%**       |
| планшет         | 888x504  | 864x486            | —            |
| ноутбук         | 1440x800 | 1440x800 точно     | —            |

## 24. Окно в нашем стиле, 2026-09-21

Человек открывал свой браузер и попадал на чужой продукт: кот, слово «n.eko»
и палитра другого проекта. Окно всё это время было нашим — наш домен, наше
приложение, наш человек, — просто его никто не одел.

**Краска, а не форк.** Переписывается только документ, и только его `head`.
Поток, канал ввода, скрипты и все файлы идут насквозь: буферизовать трафик
браузера, чтобы его покрасить, и медленно, и не наше дело. Если neko завтра
поменяет разметку, худший случай — панель снова выглядит простой.

**Имя и знак берутся из шапки самого приложения** (`Header.tsx`: `/t27-mark.svg`
30px и «Trinity S³AI»), а не придумываются здесь. Первый заход оделся в
словомарку другого проекта — так человек и узнаёт, что его браузер принадлежит
чему-то ещё. Владелец поправил: **это Trinity, t27.ai.**

**Ссылкой, не встройкой.** В любом настоящем развёртывании документ и знак —
один домен: nginx отдаёт приложение на `/` и проксирует `/live/` рядом. Встроить
знак в страницу значило бы завести ему второй дом, а два логотипа рано или
поздно расходятся.

**Кредит движка остаётся.** neko под Apache-2.0: лицензия не требует имени на
экране и не разрешает пользоваться их знаками — поэтому кот уходит, а **слова**
остаются, рядом с нашим знаком, и ссылка по-прежнему ведёт в их репозиторий.
Снять имя движка с окна, которое он рисует, было бы и не нужно, и некрасиво.

**Сжатый документ не трогается.** Прочитать gzip как utf8 — значит вернуть
кракозябры с заголовком `content-encoding: gzip`, и страница не откроется
вовсе. Пустое окно куда хуже неокрашенного.

## 25. Замок, из-за которого браузер не открывался больше никогда

Нашлось при проверке оформления, и это не косметика.

Под сняли жёстко, подняли новый на том же профиле — и Chromium отказался:

```
The profile appears to be in use by another Chromium process (9)
on another computer (dc597a44e921).
exited: chromium (exit status 21; not expected)
gave up: chromium entered FATAL state, too many start retries too quickly
```

`dc597a44e921` — имя **прошлого контейнера**, оставшееся в `SingletonLock`.
supervisord сдаётся окончательно, и окно человека чёрное столько, сколько живёт
под, и ничто на экране не объясняет почему. Сюда приходит **каждое** жёсткое
снятие: гашение простоя, передеплой, OOM, перезагрузка хозяина.

**Почему снимать замок безопасно, а не срезать угол.** Замок нужен, чтобы два
Chromium не делили один профиль и не испортили его. У нас этого быть не может:
у `browser_sessions` первичный ключ — `telegram_id`, значит у человека самое
большее один под, а том профиля монтирует только он. Гарантия стоит слоем выше,
в базе. То, от чего защищает замок, невозможно по устройству; то, что он делает
на самом деле, — кирпичит профиль после сбоя.

Поэтому `unlock-profile.sh` снимает его — и **только если** замок называет не
этот контейнер. Живой замок от самого себя всё ещё что-то значит.

Проверено на том самом профиле, который уже был сломан: до — 0 процессов и
FATAL, после — «clearing a singleton lock left by dc597a44e921», **8 процессов
Chromium** и замок, принадлежащий живому контейнеру.

## 26. TURN на Railway не спасает, и это проверено

Прошлая запись предлагала поднять TURN. **Не поднимать.** 2026-09-21, по
ответам самого railway CLI:

```
railway --help           → domain, tcp-proxy. Больше ничего.
railway tcp-proxy --help → «Create a TCP proxy for an APPLICATION PORT»
```

Один TCP-порт на прокси и никакого UDP во всём продукте. Это смертельно, но не
по той причине, что была записана раньше:

**TURN не просто принимает соединение на 3478.** Он ВЫДЕЛЯЕТ relay-адрес на
эфемерном порту и отдаёт этот адрес собеседнику, которому туда слать. Railway
опубликует ровно один порт, выбранный заранее. Собеседнику слать некуда.

То есть TURN на Railway переносит ту же недостижимость на шаг дальше и стоит
одного сервиса, чтобы это выяснить. Работать будет coturn на хозяине с UDP и
диапазоном портов (`--min-port/--max-port`) — это обычный VPS, а не эта
площадка. Флаги и переменные пода записаны в `deployment/remote-browser/
coturn.railway.toml`, который теперь озаглавлен «не разворачивать».

Сборка пода на Railway при этом всё ещё падает мгновенно и без логов —
ни через `railway logs --build`, ни в режиме `--ci`. Образ весит **2.2 ГБ**;
разумный следующий шаг — не собирать его на площадке вовсе, а публиковать
готовый и разворачивать образом.

**Шрифт убил иконки.** `#neko *` с Outfit перебил Font Awesome, и каждая

Решение владельца 21.09.2026. Это допустимо: Apache-2.0 вешает обязанности по
уведомлениям на **распространение** работы, а размещение её как услуги — не оно.

а `deployment/remote-browser/Dockerfile` прямо говорит, из чего собран. Знаки
движка не используются — эта часть и не обсуждалась.

Ссылка убрана вместе с текстом: якорь ведёт в репозиторий движка, а href из CSS
не меняется, поэтому кредит, убранный из текста, но доступный по нажатию, не
убран вовсе.

**Честный предел:** это видимая поверхность. Кто прочтёт исходник страницы,
имена бандлов или протокол сокета — всё равно поймёт, что внизу. Это не маскировка
и продавать это так нельзя.

## 28. Флаги, которые не доходили до Chromium

Найдено сразу после починки замка, и это поломка, которую внёс я сам.

Флаги жили в `command=` у supervisord, и перед ними поставили шелл, чтобы
сначала снять замок: `/bin/sh -c "unlock; exec chromium <флаги>"`. supervisord
разобрал строку по-своему, и **флаги не дошли**: Chromium поднялся с профилем по
умолчанию и без порта отладки. Замерено в живом поде — у процесса были только
собственные `CHROMIUM_FLAGS` образа и пустой `"$@"`.

Это хуже той беды, ради которой правка делалась: профиль человека не
использовался вовсе, а агенту некуда было подключаться. И ничто об этом не
сообщало — под выглядел здоровым, поток шёл.

**Ответ:** supervisord запускает ровно один путь без аргументов и кавычек
(`start-chromium.sh`), а всё, что нужно сказать, сказано в шелле, который
действительно шелл.

**Страж:** `verify-pod.sh` теперь проверяет, что у живого процесса есть
`--user-data-dir` и `--remote-debugging-port`. Отрицательный контроль прогнан по
той самой строке поломанного процесса — ловится; по пустой — ловится; на живом
поде — ok.

## 32. Всё в одной полосе, и одна ось, 2026-09-21

Владелец: кнопки из футера — в шапку, больше места, минимализм. И: «выровни
по оси, иначе кривой дизайн».

**Футер прибит в шапку.** CSS не умеет переносить узел, но умеет вынуть его из
потока: `.room-container` встаёт в верхнюю полосу. Узлы остаются там, где их
поставил движок, — поэтому перестановка его разметки это переживёт. Плеер
получает всё остальное: `calc(100vh - var(--t27-bar))`.

**Аватары переехали, а не спрятались.** Они единственное на экране, что
говорит: **смотрит кто-то ещё**. Это не украшение, которое убирают ради
опрятности; они ужаты до 24px и стоят рядом с кнопками.

**Слаб «нажмите, чтобы включить звук» убран** из центра картинки: тот же
переключатель есть в полосе значком на 15px, а слаб закрывал ровно то, что
должно быть видно.

### Одна ось: три причины, все измеренные

1. **Три разных числа высоты.** Полоса, вынесенный в неё ряд и остаток для
   картинки были тремя литералами и разошлись: элементы ряда центрировались на
   24, собственные значки полосы — на 22. Теперь одно свойство `--t27-bar`,
   которое читают все трое.
2. **Рамка съедала пиксель.** Полоса — `border-box` с волосяной линией 1px,
   значит её _содержимое_ на пиксель ниже: 23.5 против 24 у ряда полной
   высоты. Ряд сделан на пиксель короче — `calc(var(--t27-bar) - 1px)`.
   Попытка перенести линию на контейнер сделала хуже (18.5 и 24) и отменена.
3. **Аватар центрировался не на всех уровнях.** `.members` центрировался, а
   `.members-container` был блочным, список сидел у его верха, и у `.member`
   был свой `margin-top: 10px`. Аватар выходил на 5px выше всех — один
   кругляш не в строку, а это глаз ловит первым.

Итог замера: **все 12 элементов на 23.5** при широком окне, **все 10 на 21.5**
на телефоне.

Отдельно: ссылка логотипа растягивалась до 235px при видимом знаке 22px —
невидимая коробка поперёк половины полосы. `flex: 0 0 auto`.

### Телефон

Десять органов управления и словомарка в 375px не помещаются — они налезали на
логотип и друг на друга. На узком экране полоса оставляет то, чем на телефоне
пользуются, и прямо называет, что убрано:

- **остаётся** знак, кто смотрит, клавиатура, звук и меню (там живут настройки
  движка);
- **уходит** словомарка (знак её несёт), справка, чип языка, пауза, эмодзи и
  **ползунок** громкости — на телефоне нужен выключатель звука, а не попадание
  пальцем в дорожку 150px.

Ничто из убранного не становится недостижимым, и ничто не убирает признак,
что смотрит кто-то ещё.

**Отступ справа больше не угадан:** `--t27-menu` — это арифметика трёх значков

## 33. Матовое стекло и ноль полей, 2026-09-21

Владелец: без чёрных краёв по бокам, полный экран, а шапку — матовым
прозрачным стеклом, чтобы под ней было видно браузер.

## 34. Агент владеет всеми инструментами браузера, 2026-09-21

Владелец: «подключи к агенту, чтобы он владел всеми инструментами браузера, и
в главные правила про это напиши! это супер-фича».

Инструменты были в общем реестре `TOOLS` с самого начала — и всё равно агент
их не видел. Причина нашлась замером, а не чтением:

```
COMPACT_TOOLS = /^(crm_|tg_|soul_)/     ← browser_* сюда не попадал
комплект компактной модели: 5998 токенов из 6000
браузерные девять:           998 токенов
```

Модель с окном 16k получает **только** комплект. Браузерных в нём не было —
значит для неё браузера не существовало вовсе.

**Решение: взять все девять и поднять потолок с 6000 до 7000**, а цену
назвать прямо: 16k минус промпт ~5k минус 7k схем оставляет около 4k на
разговор. Агент, который не умеет открыть браузер, не умеет главного, ради
чего всё это есть.

**Подмножество было бы той же поломкой, что и ничего.** Агент, который умеет
нажимать, но не умеет спросить разрешения, — это агент, которого страж
останавливает без пути дальше.

Если 4k окажется тесно, рычаг — **описания**: один
`browser_ask_permission` стоит 254 токена прозы. Не выбрасывать инструменты.

## 35. Лицо в полосе — своё, 2026-09-21

neko рисует инициалы на диске: «YO» для всех, чьё имя так начинается. На
экране, показывающем **ваш** браузер, это заглушка чужого человека.

`/live/<id>/__avatar` отдаёт фотографию из Telegram того, чья это сессия.

**Почему не существующий помощник.** `avatarUrlViaBotApi` в `agent/tools.ts`
берёт то же фото и **публикует** его в хранилище — его вызывающему нужен
публичный адрес для картиночной модели. Полосе нужны байты и больше ничего;
заливать чужое лицо в бакет ради диска 24px было бы и медленнее, и лишней
копией, которую мы не обязаны делать.

**Берётся САМЫЙ МАЛЕНЬКИЙ размер**, а не самый большой: тот помощник берёт
большой, потому что кормит модель. Здесь большой — это мегабайт, скачанный
ради того, чтобы его выбросить.

**Отсутствие кэшируется тоже.** Человек без фотографии иначе стучался бы в
Telegram при каждой загрузке страницы, вечно, чтобы снова услышать «нет».

**Красится только `.self`.** Остальные диски в полосе принадлежат другим
зрителям, и нарисовать на них это лицо было бы хуже инициалов — это была бы
ложь о том, кто смотрит.

Ошибка любого рода — «нет картинки», инициалы остаются, окно работает.

## 36. Карточка входа, которая просила чужой пароль, 2026-09-21

neko показывает карточку всякий раз, когда не подключён. В первый раз он
входит сам, по адресу (`?usr=you&pwd=proxied-by-the-broker`), и тут же
стирает эти параметры из адреса. Пароль он запоминает в `localStorage`
**только после успешного** подключения. Значит, если первая попытка
сорвалась — под перезапустился, у телефона пропала сеть, или (до #2674)
сокет портил второй обработчик upgrade — карточка возвращается уже с
формой «Пожалуйста, войдите»: имя и пароль. Пароль — сгенерированный токен,
которого человек не видел никогда. Форма была тупиком, да ещё и с котом.

**Теперь карточка наша** (`skin.ts`): наш знак, «Trinity S³AI», палитра
приложения, кнопка-пилюля. Все селекторы начинаются с `#neko`: карточка
живёт внутри него, а правило пилюль для кнопок написано против того же id —
классовый селектор ему проигрывал бы.

**И формы больше нет** (`CONNECT_SCRIPT`). Переподключиться — это снова
встать на адрес входа: прокси сам подменит заглушку на настоящий токен.
Скрипт делает это сам до трёх раз с растущей паузой, потом останавливается,
снимает загрузчик и даёт одну кнопку «Подключить снова». Три осторожности:

- Форма мелькает на **каждой** загрузке — в первом рендере, до того как neko
  начал входить. Считается только форма, провисевшая дольше 1,2 с.
- Счётчик живёт в `sessionStorage` вкладки и стирается в момент, когда
  карточка исчезла, то есть neko подключён. Хранилище, которое не работает,
  считается «попытки кончились»: лучше без цикла, чем цикл.
- Собственная отправка формы neko гасится раньше, чем сработает: она
  отправила бы то, что в полях, а ничто из того, что человек может туда
  ввести, паролем не является.

Поля прячутся **только** когда скрипт взял карточку (`data-t27`). Без
скрипта карточка всё равно наша по виду и всё равно neko по поведению.

Тексты карточки и загрузчика — по-русски, если браузер просит русский (тот
же признак, по которому neko выбирает свои слова), иначе по-английски.
Раньше загрузчик говорил по-русски всем.

Проверено в `browser-reconnect.test.ts` на заглушке страницы, без DOM-библиотеки:
10 мутаций скрипта и стиля — все пойманы.

## 37. Окно входит под именем из Telegram, 2026-09-21

Вход и так идёт через Telegram: адрес окна брокер выдаёт только тому, чьи
initData проверены, пароль пода со стороны сервера не уходит, а cookie
живёт на пути сессии. Не хватало **имени**. neko входит с тем именем,
которое ему дала страница, а страница говорила «you»: человек сидел в
собственном браузере как «you», на диске с буквами «YO».

Имя (`telegram-name.ts`) берётся из `getChat` Bot API — `first_name`, а если
его нет, `username` — и подставляется **на нашей стороне**, там же, где
прокси уже подменяет заглушку пароля на настоящий токен: в адресе сокета
(`swapLoginQuery`) и в теле REST-входа (`rewriteLoginBody`). Страница
по-прежнему говорит «you», поэтому имя человека не попадает ни в адрес, ни
в журнал доступа, ни в Referer.

- Только **наш** вход, тот, что несёт заглушку. Чужой ввод не трогается.
- Кэш 6 часов, как у лица. Таймаут 2 с: вход ждёт ответа, и Telegram,
  который молчит, стоит человеку имени на это подключение, а не самого
  подключения. Таймаут **не** запоминается как «имени нет».
- Управляющие и направляющие символы (U+202E переворачивает строку)
  вырезаются, длина не больше 32 символов, режется по символу, а не
  посередине суррогатной пары.

Проводка в `render-server.ts` проверяется по тексту: цель прокси там
перечислена по полям, и дважды поле, добавленное в модуль, молча терялось
на этом шаге, пока все модульные тесты были зелёными.

## 38. Чёрные поля, мёртвые кнопки и три одинаковых диска, 2026-09-21

Владелец прислал два снимка: приложение на телефоне и окно в браузере
компьютера. На обоих — кусок Википедии в чёрной рамке, три диска «DM» друг
на друге и кнопки, которые не нажимаются.

**Чёрные поля — это два разных дефекта.**

1. _Окно Chromium не следовало за экраном._ Подгонка меняла размер
   X-экрана, а окно оставалось прежним: замер в работающем поде — экран
   800×1600, окно 945×1060. Шире экрана (правый край страницы срезан) и на
   540 px короче (нижняя треть картинки — голый чёрный рабочий стол).
   Теперь после каждой подгонки `fitWindowToScreen` (`cdp.ts`) ставит каждое
   окно в `normal`, потом ровно в 0,0 × размер экрана — тот, что экран
   **реально** получил. Явные размеры, а не «развернуть»: оконный менеджер —
   как раз то, что не заметило смены экрана. Обе подгонки (вкладка
   приложения и само окно) идут через `fitDesktop` (`screen.ts`).
2. _Экран брал размер из меню другой формы._ Точный размер под отказал, и
   брался ближайший из `/configurations` — 800×1600 для рамки с отношением
   0,7, отсюда поля по бокам. Теперь между точным размером и меню пробуются
   соседи на 8 и 16 px (до 12 штук, ближайшие первыми): замер показывал, что
   отказ у 360 и 368 соседствует с согласием у 352 и 376.

**Кнопки не нажимались, тоже по двум причинам.**

- Плашка «Здесь работает агент» лежала на верхнем крае кадра — ровно на
  полосе окна с её кнопками — и забирала их нажатия. Теперь это строка
  **под** кадром, с точкой цвета свечения. Поверх картинки ничего нет.
- «Во весь экран» звал `requestFullscreen` у div, а WebView Telegram на iOS
  умеет это только для видео. Теперь это запись в истории (`?view=full`):
  кадр ложится поверх приложения, таббара и кнопок, начинаясь под плавающими
  кнопками Telegram (`--app-top-inset`). Выход — родная «Назад» Telegram или
  браузера; своих кнопок поверх картинки нет.

И «коснитесь, чтобы взять управление» не работало вовсе: события внутри
iframe не всплывают в родительский документ, так что `onPointerDown` на
обёртке слышал только её 3 px свечения. Теперь `listenForTouchInside`
(`frameTouch.ts`) слушает окно кадра напрямую (он того же источника) на
каждой загрузке, а запасной путь — `blur` родителя с кадром в фокусе.

**Аватарки.** Фото из Telegram загружалось, рисовалось — и стиралось нашим
же CSS: `background: зелёный !important` — сокращение, которое сбрасывает
`background-image` и бьёт встроенный стиль. Теперь только
`background-color`, а лицо — CSS-переменная на корне, которую стиль
применяет к диску `.self`: Vue перерисовывает диск, и стиль, записанный на
старый элемент, уходил вместе с ним.

Три диска — это три экрана одного человека (телефон, ноутбук, забытая
вкладка): один под на человека, и все, кто входит через брокер, входят под
его Telegram-именем. Теперь диск один, с его лицом, а число остальных экранов
— счётчик «+N» на нём. Знак, что смотрит кто-то ещё, сохранён — числом, а не
копиями того же лица.

Проверено: 12 мутаций сервера, все пойманы; плеер — контракты на «ничего
поверх картинки», «касание в кадре слышно» и полноэкранный режим без
`requestFullscreen`.

## 39. Каждая подгонка перезапускала видео, 2026-09-21

Замер по логу пода после §38: **одна** подгонка дала 12 отказов
`cannot set screen size error="unsupported screen rate 30"` и 31 запуск
видеоконвейера за минуту. Две вещи, которых раньше не знали:

- **Любое обращение к размеру экрана перезапускает видео**, даже неудачное.
  neko гасит конвейеры захвата до смены экрана и поднимает после, каков бы
  ни был исход (в логе destroy/create вокруг каждого 422). Каждая попытка —
  мгновение замёрзшей или чёрной картинки. Перебор соседей из §38 умножал
  это на 12. Убран.
- **«Отказ без закономерности» (§22) был отказом по частоте.** neko строит
  новый размер через CVT на запрошенных 30 Гц, а X считает частоту режима
  из пиксельной частоты и округляет: у одних размеров 30, у других 29 или 31. Просьба 30 на режим, который X числит 29, — BadValue
  (`server/pkg/xorg/xorg.go`, `ChangeScreenSize`). Но режим после неудачной
  попытки **уже создан** и лежит в меню со своей настоящей частотой — и
  выбор из меню берёт именно его: точная форма.

Правила теперь (`applyScreen`, `fitDesktop` в `screen.ts`):

1. Экран уже нужной формы (±16 px) — **не трогать**. Каждая загрузка окна
   просит подгонку; раньше каждая перезапускала видео.
2. Одна попытка точного размера, затем меню. Без слепых повторов.
3. **Одна подгонка за раз на под.** Вкладка приложения и окно внутри неё
   просят форму почти одновременно и с разницей в несколько пикселей; по
   очереди вторая находит экран готовым и ничего не делает.

## 41. Новый режим живёт на 29 Гц, и меню о нём не знает, 2026-09-21

После §39 владелец снова прислал поля по бокам. Лог пода: один отказ
`unsupported screen rate 30` — и откат к 800×1600. §39 рассчитывал, что
отказанная попытка создаёт режим и меню его покажет. Первое верно, второе
нет: neko читает список размеров **один раз, при старте**
(`server/internal/desktop/manager.go`), режим, созданный потом, в меню не
попадает никогда.

А частота всегда на герц меньше: CVT округляет пиксельную частоту **вниз**,
реальная частота режима чуть ниже 30, X округляет до целого — 30 у большого
экрана, 29 у телефонного (шаг частоты — большая доля маленькой частоты).
Поэтому после отказа (422) тот же размер спрашивается на 29 Гц — режим уже
создан, и это попадает. После вежливого 200 без изменений повтора нет: это
не частота, и лишний вопрос — лишний перезапуск видео. Итого не больше трёх
вопросов: точный, точный на 29, меню.

## 42. Профиль на томе, переводчик выключен, Bitwarden, 2026-09-21

**У пода не было тома.** Профиль Chromium — все входы и cookies — жил в
файловой системе контейнера, и любой редеплой или перезапуск пода стирал его.
«Закрыть ≠ забыть» ломала сама площадка. Теперь профиль на томе Railway
(`/home/neko/.config/chromium`). Том монтируется от root, а Chromium работает
от `neko`, поэтому `own-profile.sh` запускается первым, от root, отдаёт том
`neko` и дальше становится штатным CMD образа (`supervisord`).

**Политика правится jq и проверяется.** Chromium игнорирует нечитаемый файл
политики **целиком**, вместе с запретами, поэтому никаких sed по JSON:
правка jq и `jq -e` на результат в сборке.

- `TranslateEnabled: false` — пузырь «Russian | English» посреди картинки.
- **Bitwarden** установлен и разрешён. Перенос паролей скопом не должен идти
  через нас: правило — секреты человек вводит сам, внутри потока, и они
  доходят только до пода. Менеджер паролей, который человек разблокирует
  внутри окна, делает это для всех паролей сразу.
- **Собственное хранилище паролей Chromium остаётся выключенным**, как в
  апстриме: на Linux без keyring оно держит пароли за фиксированным ключом,
  и тот, кто ведёт браузер — агент тоже, — открыл бы
  `chrome://password-manager` и прочёл их.

## 43. Окно открывается быстро, и ещё быстрее во второй раз, 2026-09-21

- **Вкладка не выгружается.** Уход на другую вкладку приложения размонтировал
  страницу, а с ней окно: возврат = документ, бандлы, сокет, ICE, первый
  кадр, 3–5 с каждый раз. Теперь страница живёт скрытой 5 минут после ухода
  (`lib/keptBrowser.ts`), возврат мгновенный; дальше отпускается, чтобы не
  стримить в пустоту. При каждом возврате сессия перечитывается — адрес окна
  у сессии постоянный, кадр не перезагружается.
- **Бандлы движка — на год.** У них хэш в имени (`js/app.48a1d8f5.js`), под
  не присылал политики кэша вовсе, и каждая перезагрузка окна (а оно
  перезагружает себя, переподключаясь) тянула ~700 КБ заново — через два
  прокси, а после переезда пода в Сингапур ещё и дважды через океан.
- **Документ — никогда из кэша** (`no-cache`, без `Last-Modified`): иначе
  браузер вправе эвристически держать вчерашний скин.
- **`emoji.json` отвечаем сами**, пустым набором той формы, что читает движок:

## 44. Перенос входов скопом, 2026-09-21

Просьба владельца: входить на каждый сайт заново, руками, в браузере,
который вроде бы твой, — это то, из-за чего им не пользуются. Две дороги:

- **Пароли** — через Bitwarden, установленный в поде (§42). Человек сам
  входит в него внутри окна; пароли подставляются сами и не проходят через
  нас. Правило «секрет вводит человек, и он доходит только до пода» цело.
- **Входы (cookies)** — файлом: человек выгружает их у себя на компьютере
  (Cookie-Editor → Export → JSON, «Get cookies.txt LOCALLY» сразу для всех
  сайтов, или `storageState` Playwright) и загружает во вкладке «Браузер» →
  «Перенести входы». `POST /api/browser/cookies` разбирает три формата
  (`cookie-import.ts`) и одним `Storage.setCookies` кладёт их в браузер пода.

Cookies — ключи сессий, и они ПРОХОДЯТ через брокер на пути внутрь —
в памяти, на время одного запроса. Поэтому: только человек (ключ агента —
403); ничего не хранится и не пишется в лог; ответ — сайты и счётчики, не
значения; лимит 2 МБ и 5000 штук; битое пропускается и считается, а не
угадывается (имя с пробелом, значение с переводом строки, домен с путём,
уже истёкшее). Host-only остаётся host-only (ставится по `url`, не по
`domain`). Google и банки могут попросить войти заново — привязка сессии к
месту; интерфейс так и говорит.

**Страж догнал хранилище.** С менеджером паролей разблокированное хранилище —
страница самого браузера (`chrome-extension://`), а страж считал всё не-http
безопасным. Теперь действия на настройках, менеджере паролей, расширениях и
DevTools требуют разрешения человека, а `browser_open` агента открывает
только http(s) и `about:blank` (`agentMayOpen`).

## 45. Режим «смотреть»: кадры вместо видео, где видео не нужно, 2026-09-21

**Задача владельца:** «в UI всё виснет медленно, может скриншоты работы
отправлять реалтайм?» Замер: видео — WebRTC по TCP, и до первой картинки
идут сокет, offer/answer, ICE, DTLS и ключевой кадр — секунды. Chromium
умеет сам отдавать кадры: `Page.startScreencast` шлёт JPEG, когда страница
меняется, по обычному WebSocket, который поднимается за один круг.

**Дизайн — гибрид, и граница между частями — правило №1.**

|                | видео (neko, WebRTC)                     | кадры (CDP screencast)          |
| -------------- | ---------------------------------------- | ------------------------------- |
| старт          | секунды                                  | один круг                       |
| сеть           | нужен ICE, на мобильных бывает не пройти | обычный WebSocket               |
| трафик в покое | идёт всё время                           | ноль, пока страница не меняется |
| что видно      | весь экран пода, с панелями Chromium     | только страница                 |
| ввод           | прямо в под, мимо нас                    | **нет и не будет**              |

Кадры — **только картинка в одну сторону.** Всё, что человек нажимает и
печатает, идёт по каналу видео прямо в под — так пароль доходит до пода и
больше никуда. У модуля кадров нет пути для ввода вовсе. За той же дверью,
что видео: кука `/live/` собственной сессии человека.

**Прототип (`frames.ts`), шаг 1 — мост, пока подключается видео.** Под
загрузчиком — живые кадры страницы с первой секунды; заиграло видео —
загрузчик уходит и закрывает сокет. Не дольше 2 минут; окно, которое не
успевает, получает меньше кадров, а не растущую очередь; каждый кадр
подтверждается (без `screencastFrameAck` Chromium больше не шлёт).

**Шаги дальше:** 2. **Запасной режим.** ICE не прошёл — кадры остаются, с пометкой «только
просмотр: видео не подключилось». Человек видит работу агента на любой
сети. 3. **«Смотреть» по умолчанию, пока работает агент** — кадры легче видео и
для телефона, и для батареи; «взять руль» переключает на видео, потому
что вводу место только там. 4. Лента шагов агента с миниатюрами из тех же кадров.
