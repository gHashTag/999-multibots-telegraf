# Один кошелёк: `user_tokens` живёт, `payments_v2` уходит в архив

**Решение владельца, 2026-09-20.** Дальше — один кошелёк. Второй замораживается
и хранится только для аудита.

|         | Живая система                     | Архив             |
| ------- | --------------------------------- | ----------------- |
| Таблица | `user_tokens` (+ `star_payments`) | `payments_v2`     |
| База    | Postgres рендера (`getPool()`)    | облачный Supabase |
| Единица | токен                             | звезда (`stars`)  |
| Продукт | цифровой клон, мини-апп           | боты 1..12        |

Курс переноса **1 звезда = 1 токен** — не выбран, а измерен:
`creditStarsPayment` (`apps/vibee-editor/render/src/stars-credit.ts`) кредитует
оплаченную звезду в `user_tokens.balance` один к одному.

## Почему выживает именно `user_tokens`

Не потому, что он больше — он меньше: 9 файлов против 222. А потому, что там
находится продукт, который продаётся: цифровой клон. `payments_v2` обслуживает
старую витрину ботов, чей прайс владелец признал устаревшим (см.
`digital-clone-real-price`).

## Что «архив» значит буквально

1. `payments_v2` становится **read-only**: новых строк не пишем, старые не
   трогаем. Леджер append-only, вся история остаётся проверяемой.
2. Баланс и списания идут только через `user_tokens`.
3. Отчётность и аудит продолжают читать `payments_v2` — это и есть смысл архива.

**Удалять `payments_v2` нельзя.** В нём лежит единственная запись о реальных
деньгах, которые люди заплатили; часть возвратов и споров ещё возможна.

## Перенос балансов

Правило владельца: реальные оплаты переносятся, админские начисления — нет.

    перенос = min(реально оплачено, текущий баланс)

Первый предел отсекает админские начисления. Второй не возвращает уже
потраченное; потраченное списывается сначала с начисленного, то есть в пользу
плательщика.

### ✅ ВЫПОЛНЕНО 2026-09-20

**94 человека, 212 939 токенов** зачислены в `user_tokens`. Из них @playom —
102 251 (владелец подтвердил перенос, несмотря на админский статус).

Состояние базы рендера: было 30 строк / 38 683 токена → стало **114 строк /
251 622 токена**. Арифметика сходится: 38 683 + 212 939 = 251 622.

Перенос **идемпотентен**: каждая запись помечена `star_payments.charge_id =
'carry-2026-09-20-<telegram_id>'`, а `charge_id` — первичный ключ. Повторный
запуск даёт `0 users, 0 tokens` (проверено). Это тот же замок, которым
`creditStarsPayment` защищается от повторной доставки платежа Telegram — не
изобретён заново, а переиспользован.

Каждый пользователь переносился **своей транзакцией**: строка дедупа и движение
баланса коммитятся вместе, поэтому сбой не мог оставить отметку о переносе без
самого переноса.

212 939, а не 212 955: дробные остатки округлены вниз (`user_tokens.balance` —
целочисленная колонка), разница 16 токенов на всех.

Не переносится: **968 068⭐** админских начислений (по правилу) и корзина

Клиентских оплат в корзине нет ни одной. Перенос исключил её правильно.

### ✅ Админские начисления сняты 2026-09-20

**19 человек, 852 839⭐** списаны строками `MONEY_OUTCOME` в `payments_v2`

Ни один баланс не ушёл в минус: списывается `min(начислено, баланс)`.
Результат каждого из 19 сверен с живым RPC `get_user_balance`.

Перенесённые токены в `user_tokens` снятием **не затронуты** — перенос брал
`min(оплачено, баланс)`, поэтому админских денег там нет по построению.

Запись в `payments_v2` здесь не нарушает архивный режим: заморозка — это
шаг 4, и она ещё не выполнена. Чистка обязана пройти **до** заморозки.

## Узкое место переключения

Записи в `payments_v2` сосредоточены в `src/core/supabase/`, а не размазаны по
всем 222 файлам, которые упоминают таблицу (остальное — тесты, отчёты,
аналитика). Переключать нужно здесь:

    updateUserBalance.ts      directPayment.ts        setPayments.ts
    createSuccessfulPayment.ts  payments.ts           refundUser.ts (src/price/helpers)
    getUserBalanceStats.ts    checkPaymentStatus.ts   getPaymentsInfoByTelegramId.ts
    getTelegramIdFromInvId.ts  sendPaymentInfo.ts     createUser.ts
    getUserDetailsSubscription.ts

Чтение баланса идёт через RPC `get_user_balance`, **тело которого существует
только внутри Supabase** — в репозитории его нет. Это отдельный риск: логику
придётся воспроизвести на стороне `user_tokens`, а не перенести.

## Чего нельзя сделать одним движением

Заморозка `payments_v2` без перевода списаний **ломает 13 живых ботов** —
они сегодня берут деньги только оттуда. Порядок обязателен:

1. ✅ **касса включена** — `TOKENS_PAYMENT_BOT_TOKEN` задан на `vibee-render`
   (проверено 2026-09-20, длина значения 46). Кассиром работает `t27ai_bot`
   = BOT_TOKEN_12: он отвечает только на `pre_checkout_query` и
   `successful_payment`. Более ранний вывод «касса выключена» устарел;
2. ✅ **балансы перенесены** — см. раздел выше;
3. ✅ **боты тратят из `user_tokens`** — `getUserBalance` читает живой
   кошелёк, `updateUserBalance` в нём же списывает и начисляет. Строка в
   `payments_v2` остаётся, но это уже аудит, а не деньги;
4. ⬜ только после этого закрыть `payments_v2` на запись.

Остался шаг 4.

## Шаг 3: чем именно заменено

`src/core/wallet/tokenWallet.ts` — весь доступ к живому кошельку: чтение
баланса, начисление, списание. Берёт `TOKENS_DATABASE_URL` (или
`RENDER_DATABASE_URL`), **не** `DATABASE_URL`: последний в оболочке
разработчика указывает на localhost, и кошелёк молча привязался бы к пустой
базе, отчитавшись о здоровье.

**Гонка двойного тапа закрыта не аккуратностью, а базой.** Было:
`get_user_balance` → сравнение → запись. Два нажатия в паре миллисекунд
проходили проверку оба и тратили одни и те же звёзды (#999). Стало — один
оператор:

    UPDATE user_tokens SET balance = balance - $2
     WHERE telegram_id = $1 AND balance >= $2 RETURNING balance

Ноль строк в ответе = отказ: денег не хватило, ничего не списано, откатывать
нечего. `withUserBalanceLock` остаётся, но гарантия больше от него не зависит.

**Недоступный кошелёк не равен нулевому балансу.** `getTokenBalance` бросает
`WalletUnavailableError`, `getUserBalance` превращает её в
`BalanceUnavailableError`. Списание при недоступном кошельке отклоняется, а не
разрешается «на всякий случай». Это строже прежнего поведения: у RPC таймаут
проваливался в `return 0`, то есть заплативший человек видел «недостаточно
средств».

**Порядок для начислений обратный.** Списание идёт ДО строки в `payments_v2` и
откатывается (`reverseDebit`), если строка не сохранилась. Начисление — ПОСЛЕ:
токены, которые человек может потратить в ту же секунду, откатывать нечем. Если
начисление не прошло, в лог уходит `error` с пометкой «деньги получены, звёзды
не зачислены» — это как раз тот случай, который должен будить владельца.

**Требуется переменная.** Сервису `999-multibots-telegraf` нужен
`TOKENS_DATABASE_URL` = внутренний адрес Postgres рендера
(`postgres-nfrq.railway.internal`). Без неё боты откажут в каждом списании —
громко, а не тихо в ноль.

## Правила переноса теперь код, а не скрипт в /tmp

Перенос и снятие считал одноразовый скрипт во временной папке: логика, которая
подвинула реальные деньги, жила там, где её никто не прочитает и ничто не
проверит. Теперь она в репозитории:

- `src/core/money/ledgerClassify.ts` — как строка леджера попадает в корзину
  (`paid` / `admin` / `refund` / `test` / `other`) и обе формулы:
  `carry = min(paid, balance)`, `remove = min(admin, balance)`;
- `src/__tests__/money/ledgerClassify.test.ts` — 16 тестов, каждый пришит к
  реальному случаю (@tatizaharova, @Kaya_Kaa, @elvira_ernst), а не выдуман;
- `scripts/money/carry-to-user-tokens.ts` — перенос;
- `scripts/money/clawback-admin-grants.ts` — снятие админских начислений;
- `scripts/money/reconcile-wallets.ts` — сверка, только чтение;
- `scripts/money/debit-archive-after-carry.ts` — вторая половина переноса,
  **ещё не запускалась** (см. ниже).

Все они читают базу через `RENDER_DATABASE_URL`, а **не** `DATABASE_URL`: в
рабочей оболочке разработчика второй указывал на локальный Postgres, и денежный
скрипт свёл бы баланс с пустой базой и отчитался об успехе. Локальный хост
теперь отвергается явно.

Запуск сверки:

```bash
bun run scripts/money/reconcile-wallets.ts
```

`payment_method`. У трёх аккаунтов тестовые строки помечены как `Telegram` и
`Robokassa`, поэтому тестовые данные засчитались оплатой и переехали в живой
кошелёк:

| --------------------- | ---------- | ---------- | ------- |
| 435572800 @playom     | 102 251    | 517        | 101 734 |
| 6419070693            | 8 730      | 22         | 8 708   |
| 144022504 @neuro_sage | 2 289      | 46         | 2 243   |

Все трое — админы, ни один клиент не получил лишнего. Токены реальны и лежат в
`user_tokens` сегодня. Сверка печатает это каждый запуск строкой `KNOWN` и не
падает: снимать их или оставить — решение владельца, а не скрипта.

## Двойная трата: 89 человек, 203 607⭐

Перенос сделал только половину работы. Он **начислил** токены и не **списал**
звёзды: боты по-прежнему тратят из `payments_v2`. Пока шаг 3 не сделан, одна и
та же оплата тратится дважды. Сверка измеряет дыру каждый запуск.

Вторая половина написана — `scripts/money/debit-archive-after-carry.ts`, —
но **не запущена намеренно**. В тот момент, когда она отработает, у 88 человек,
которые реально заплатили, баланс в ботах станет нулём, а их токены будут
доступны только через мини-апп. Пока боты остаются входной дверью, это отнимет
деньги у платящего клиента, которому пока негде их потратить.

Правильный порядок — сначала шаг 3 (перевести `getUserBalance` /
`updateUserBalance` на `user_tokens`), и тогда скрипт не понадобится вовсе. Он
существует потому, что это одна команда, а шаг 3 — нет.
