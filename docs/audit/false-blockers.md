# Мнимые блокировки: что я записал в «ждём владельца» напрасно

Прошлая итерация показала, что «нужен ключ ElevenLabs» было неверным диагнозом:
два рабочих ключа лежали в истории коммитов. Это повод перепроверить **все**
задачи, которые я записал как заблокированные.

## Итог перепроверки

| задача | было записано | оказалось |
|---|---|---|
| ключ ElevenLabs | «нет ключа, ждём» | **ключи есть, аккаунт активен** — нужен перевыпуск |
| доступы к S3 для зеркалирования | «ждём учётные данные» | **не нужны** — Supabase Storage работает текущими ключами |
| `RAPIDAPI_INSTAGRAM_KEY` | «не задана» | подтверждено: не задана |
| `API_SERVER_URL` | «не задана» | подтверждено: не задана |
| пересчёт балансов `TEST_DATA` | решение владельца | верно |
| ротация ключей | действие владельца | верно |
| подключение сторожа обучений | меняет данные | верно |

**Две из семи были мнимыми.** Обе — там, где я заключил «отсутствует» по
переменным окружения, не проверив, нет ли другого пути.

## Живая диагностика вместо догадок

У приложения есть эндпоинт, отдающий доступность поставщиков. Запрос к проду:

| поставщик | состояние |
|---|---|
| fal.ai | доступен |
| replicate | доступен |
| **openai** | **недоступен — HTTP 401** |
| **elevenlabs** | **недоступен — HTTP 400** |

То есть два поставщика не работают **прямо сейчас**, и это видно одним
запросом. Раньше я выяснял такое чтением кода.

Для ElevenLabs это смыкается с находкой из истории: рабочие ключи существуют,
а настроен — нерабочий.

## Но сама эта диагностика была открыта всем

Проверяя доступность, я обнаружил, что эндпоинт отвечает **без авторизации**.
Дальше проверил соседние — и оказалось, что открыто гораздо больше:

| адрес | что отдаёт |
|---|---|
| `GET /api/billing` | **финансы по всем ботам**: расходы на ИИ, поступления от людей |
| `GET /api/billing/:botName` | то же по одному боту |
| `GET /api/models/:telegramId` | **чужие обученные модели** по номеру |
| `GET /api/diagnostic/trainings/:telegramId` | **чужие обучения** по номеру |
| `GET /api/diagnostic/trainings-recent` | последние обучения по всем |
| `GET /api/diagnostic/training-config` | настройки, включая начала двух ключей |

Номер в Telegram не секрет и легко перебирается, поэтому «знать адрес» защитой
не было.

Все шесть закрыты служебным ключом `SECRET_API_KEY` в заголовке `x-secret-key`
— механизмом, который в проекте уже есть: им наш же код подписывает запросы к
AI-серверу. Заводить второй ради этого не стал.

**Отказ закрытый:** если ключ не настроен, маршрут не открывается, а отвечает
503. Иначе забытая переменная тихо вернула бы всё как было, и починка выглядела
бы сделанной.

## Закрыто тестом

`src/__tests__/api/protected-routes.test.ts`, четыре проверки:

1. разбор находит монтирования (страховка от самого себя);
2. роутеры с внутренними данными закрыты ключом;
3. **каждый открытый роутер назван с причиной** — новый открытый должен быть
   решением, а не забывчивостью;
4. в списке открытых нет тех, кого уже закрыли.

Проверено мутацией: при снятии защиты с биллинга тест падает и называет роутер
с причиной, почему он должен быть закрыт.

## Урок

**«Ждём от владельца» — это диагноз, и он тоже требует проверки.** Дважды я
записал задачу заблокированной, потому что проверил одно место (переменные
окружения) и не проверил другие (историю коммитов, альтернативное хранилище).

Признак мнимой блокировки: формулировка вида «нет X». Прежде чем записывать,
стоит спросить — «нет нигде или нет там, где я посмотрел?»

И побочное, но важное: **проверяя одно, смотри, чем проверяешь.** Эндпоинт
диагностики я использовал как инструмент — и он оказался самой крупной находкой
итерации.
