# Карта денег: что на самом деле меняет баланс

Я трижды подряд ошибся в предположениях об этом пути. Каждый раз причина одна:
рассуждал по коду, не проверив данные. Этот документ закрывает вопрос фактами.

Замер: `scripts/probe-money-map.cjs` (только SELECT).

## 1. Баланс — это сумма по строкам реестра

```
баланс = Σ stars, где status = 'COMPLETED'
         MONEY_OUTCOME вычитается, все остальные типы прибавляются
```

Проверено на шести самых активных счетах — совпадение с функцией базы **6 из 6**,
до копейки. Ничего другого в расчёте не участвует: ни таблица `users`, ни
отдельный счётчик, ни кэш.

Из этого следует всё остальное.

## 2. Перевод строки в `COMPLETED` и есть начисление

208 строк лежат в `PENDING` и держат **1 104 664 звезды**, которых нет ни в
одном балансе. Смена статуса на `COMPLETED` — это и есть момент, когда человек
получает деньги.

**Отсюда моя ошибка в PR #532.** Я счёл начислением вызов `updateUserBalance` и
переставил его перед отметкой статуса. На деле отметка — первична, а вызов —
вторичен (он делает то же обновление по номеру счёта, сбрасывает кэш и пишет
журнал). Перестановка лишала звёзд тех, у кого нет профиля. Отозвано в PR #533.

## 3. Номер счёта уникален

16 680 строк с номером счёта, **16 680 разных номеров, дублей ноль**.

Вторую строку с тем же номером база не примет — код `23505`, который в коде
обрабатывается отдельно и намеренно игнорируется. Поэтому попытка «начислить
ещё раз» через вставку не срабатывает, и двойного начисления не происходит.

## 4. Способов пополнения — двадцать два

| способ | строк | звёзд |
|---|---:|---:|
| `System` | 580 | 195 923 974 |
| `balance` | 266 | 852 831 |
| `Telegram` | 363 | 224 678 |
| `Admin` | 34 | 185 991 |
| `System_Balance_Migration` | 278 | 158 950 |
| `Robokassa` | 75 | 65 617 |
| … ещё 16 значений | | |

Среди них `SYSTEM`, `System`, `Admin`, `admin`, `Admin Action`, `admin_topup`,
`ADMIN_OVERRIDE` — одно и то же разными словами. Для отчётности это значит, что
любая группировка по способу оплаты **неверна**, пока значения не приведены к
единому виду.

## 5. Опасная деталь: новый тип операции автоматически становится начислением

Ветка расчёта устроена так: `MONEY_OUTCOME` — вычесть, **всё остальное** —
прибавить.

Сегодня типов четыре: `MONEY_OUTCOME` (15 222), `MONEY_INCOME` (1718),
`REFUND` (195), `BONUS` (1).

Любой **новый** тип попадёт в ветку «прибавить» и станет начисляющим — молча.
Именно так `SERVICE_PAYMENT` мог бы стать источником бесплатных звёзд, если бы
проходил валидацию записи (он не проходил, PR #506).

## 6. Нарушение, оставшееся в данных

**114 строк `MONEY_OUTCOME` с отрицательными звёздами.** По формуле они
не списывают, а **начисляют**: 1026 звёзд одному аккаунту (июнь 2025).

В коде запрет добавлен (PR #506), в данных строки остались — это правка данных,
решение владельца.

## Что из этого следует для правок

1. **Хочешь начислить — переведи строку в `COMPLETED`.** Не ищи «функцию
   начисления»: её нет, есть смена статуса.
2. **Хочешь списать — создай строку `MONEY_OUTCOME` с положительными
   звёздами.** Минус не «списывает сильнее», он начисляет.
3. **Не добавляй новый тип операции**, не изменив функцию расчёта в базе. Её
   определения нет в репозитории — она живёт внутри Supabase.
4. **Не полагайся на группировку по способу оплаты** без нормализации.

## Как это проверяется

`src/__tests__/money/money-invariants.test.ts` стережёт то, что можно проверить
по коду:

- список типов операций фиксирован — новый нельзя добавить незаметно;
- места, где код переводит платёж в `COMPLETED`, перечислены поимённо: каждое
  такое место начисляет деньги, и появление нового должно быть осознанным.
