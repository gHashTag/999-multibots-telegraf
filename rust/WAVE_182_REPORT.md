# Wave 182 — Security Hardening Report

**Date:** 2026-06-16  
**Scope:** trios-mb Rust monorepo — trait crate deserialization, Robokassa webhook input validation, server-error info-disclosure sanitization

## Executive Summary

Three distinct defensive fixes were implemented across the traits crate, the server webhook handler, and the edge-hardening middleware. All changes are backward-compatible, add no runtime cost for the deserialization work, and close active or latent vulnerabilities in inbound data handling and error response sanitization.

---

## Fix 1 — `deny_unknown_fields` on GOLD-RING-TR00 structs (5 items, 2 files)

### Finding
Five deserialization structs/enums in `trios-mb-traits` (`GOLD-RING-TR00`) lacked `#[serde(deny_unknown_fields)]`:
- `Job` (job queue entry)
- `JobStatus` (job state machine enum)
- `EnqueueRequest` (job enqueue payload)
- `PaymentInit` (payment initiation data)
- `PaymentVerification` (payment callback verification)

These structs cross crate boundaries (traits → DB implementations, traits → payment gateway implementations). Silent field truncation could cause state mismatches (e.g., a missing `max_attempts` field silently defaulting, or a missing `status` field causing invalid payment state transitions).

### Literature
**OWASP API Security Top 10 (2023) — API6: Unrestricted Access to Sensitive Business Flows.** Deserialization ambiguity allows attackers to craft payloads that appear valid but silently drop critical fields, bypassing business-logic checks. `deny_unknown_fields` is the canonical serde defense: it converts silent truncation into an explicit deserialization error that fails closed.

### Implementation
- Files: `rings/GOLD-RING-TR00/src/job_queue.rs`, `payment_gateway.rs`
- Added `#[serde(deny_unknown_fields)]` to all 5 Deserialize definitions
- No ordering regressions (attribute follows derive as required)

### Verification
```bash
cargo check --package trios-mb-traits   # OK
cargo check --package trios-mb-app        # OK
```

## Fix 2 — Length caps on `RobokassaCallbackForm` fields

### Finding
`RobokassaCallbackForm` in `BRONZE-RING-SRV/src/payment_webhooks.rs` received untrusted form-data fields from the public internet without per-field length validation:
- `inv_id` — passed to DB lookups and idempotency checks
- `signature_value` — passed to HMAC verification
- `out_sum` — parsed to `f64` after string conversion

The only upstream boundary was the global 2 MB Axum body limit. An attacker could send megabyte-sized fields, causing memory pressure, log injection (via `truncate_for_log`), and potential downstream parser issues.

### Literature
**CWE-20 — Improper Input Validation.** "The product receives input or data, but it does not validate or incorrectly validates that the input has the properties that are required to process the data safely and correctly." Per-field length caps are the standard defense: reject oversized input at the boundary before any processing or storage.

### Implementation
Added constants and validation immediately after deserialization, before logging or parsing:
```rust
const MAX_INV_ID_LEN: usize = 128;
const MAX_SIGNATURE_LEN: usize = 512;
const MAX_OUT_SUM_LEN: usize = 32;
```

Each oversized field triggers an early return with a generic error string and a `tracing::warn!` log entry (length only, not the full field content, to prevent log injection).

### Verification
```bash
cargo check --package trios-mb-app   # OK
```

## Fix 3 — Extend body sanitization to 5xx server errors in `edge_hardening`

### Finding
The `edge_hardening` middleware in `router.rs` sanitized 4xx client-error bodies to prevent information disclosure (leaked field names from deserialization failures, stack traces, etc.). However, 5xx server-error bodies were left untouched. A database outage, panic, or unhandled exception could return a raw error message containing SQL details, file paths, or internal identifiers to the client.

### Literature
**CWE-209 — Information Exposure Through an Error Message.** "The product generates an error message that includes sensitive information about its environment, users, or associated data." Sanitizing both 4xx and 5xx response bodies ensures that external consumers never see internal implementation details, regardless of whether the error originated from client misuse or server failure.

### Implementation
Changed the sanitization condition from:
```rust
if code.is_client_error() && code != axum::http::StatusCode::TOO_MANY_REQUESTS
```
to:
```rust
if (code.is_client_error() || code.is_server_error()) && code != axum::http::StatusCode::TOO_MANY_REQUESTS
```

The 429 exemption is preserved because rate-limit responses are already generated by a dedicated Tower layer and carry no internal details.

### Verification
```bash
cargo check --package trios-mb-app   # OK
```

## Next-Wave Variants (3 candidates)

1. **Payment gateway response validation** — Add per-field length caps to `PaymentInit` and `PaymentVerification` when they are constructed from gateway responses (Robokassa, TON, x402, Telegram Stars). Prevents poisoned gateway responses from injecting unbounded strings into dialogue state and the database.
2. **FSM state-size limits** — Add `#[serde(deny_unknown_fields)]` to the `scene_state!` macro or bound the serialized size of `InMemStorage` dialogue state to prevent memory exhaustion from oversized state fields (e.g., a 10 MB `payment_url`).
3. **Integration test coverage** — Write integration tests for the three fixes in this wave (deny_unknown_fields rejection, Robokassa oversized field rejection, 5xx sanitized response bodies) to ensure regressions are caught in CI.
