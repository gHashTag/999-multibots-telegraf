## ⛔ АБСОЛЮТНЫЕ ЗАПРЕТЫ

### 1. НИКОГДА НЕ ПУШИТЬ В PRODUCTION БЕЗ РАЗРЕШЕНИЯ
- **ЗАПРЕЩЕНО**: Выполнять `git push origin production` без явного разрешения пользователя
- **ЗАПРЕЩЕНО**: Делать коммиты в production ветку без тестирования
- **ПРАВИЛЬНО**: Спрашивать "Могу ли я запушить изменения в production?" и ждать ответа

### 2. ОБЯЗАТЕЛЬНОЕ ТЕСТИРОВАНИЕ
- **ВСЕГДА**: Тестировать изменения локально перед коммитом
- **ВСЕГДА**: Проверять, что код компилируется без ошибок
- **ВСЕГДА**: Запускать `npm run build` и `npm run typecheck` перед коммитом
- **ВСЕГДА**: Проверять логи на наличие ошибок после деплоя

### 3. ОБЯЗАТЕЛЬНОЕ РЕЗЕРВНОЕ КОПИРОВАНИЕ
- **ПЕРЕД** критическими изменениями создавать резервную ветку
- **СОХРАНЯТЬ** текущее состояние перед экспериментами
- **ДОКУМЕНТИРОВАТЬ** что было изменено и почему

## 📋 ОБЯЗАТЕЛЬНЫЙ ЧЕКЛИСТ ПЕРЕД ДЕПЛОЕМ

### Шаг 1: Локальная проверка
- [ ] Код компилируется без ошибок
- [ ] Тесты проходят успешно
- [ ] TypeScript проверка пройдена
- [ ] ESLint не показывает критических ошибок

### Шаг 2: Тестирование функциональности
- [ ] Новая функциональность работает корректно
- [ ] Старая функциональность не сломана
- [ ] Обработка ошибок добавлена
- [ ] Логирование добавлено

### Шаг 3: Проверка совместимости
- [ ] Проверены все импорты
- [ ] Проверены переменные окружения
- [ ] Проверена совместимость с production окружением
- [ ] Проверены зависимости в package.json

### Шаг 4: Получение разрешения
- [ ] Спросить: "Я проверил все пункты. Могу ли я деплоить в production?"
- [ ] Дождаться явного ответа "Да" или "Деплой"
- [ ] Если ответ "Нет" - уточнить что нужно исправить

## 🔄 ПРОЦЕСС ВНЕСЕНИЯ ИЗМЕНЕНИЙ

### 1. Анализ задачи
```
1. Понять что нужно сделать
2. Оценить риски
3. Предложить план реализации
4. Получить подтверждение плана
```

### 2. Разработка
```
1. Создать резервную копию если нужно
2. Внести изменения
3. Добавить логирование
4. Добавить обработку ошибок
```

### 3. Тестирование
```
1. Запустить локальные тесты
2. Проверить компиляцию
3. Проверить функциональность
4. Проверить логи
```

### 4. Деплой (ТОЛЬКО С РАЗРЕШЕНИЯ)
```
1. Спросить разрешение на деплой
2. Получить явное "Да"
3. Выполнить git add, commit, push
4. Проверить production логи
5. Откатить если есть ошибки
```

## 🚨 КРИТИЧЕСКИЕ СИТУАЦИИ

### Если production сломан:
1. **НЕМЕДЛЕННО** откатить последние изменения
2. **НЕ ПЫТАТЬСЯ** исправить "на ходу" без анализа
3. **СООБЩИТЬ** пользователю о проблеме
4. **ПРОАНАЛИЗИРОВАТЬ** логи
5. **ПРЕДЛОЖИТЬ** план исправления

### Если есть сомнения:
1. **ОСТАНОВИТЬСЯ**
2. **СПРОСИТЬ** пользователя
3. **ДОЖДАТЬСЯ** ответа
4. **НЕ ДЕЙСТВОВАТЬ** самостоятельно

## 📝 ОБЯЗАТЕЛЬНЫЕ ВОПРОСЫ

### Перед началом работы:
- "Я правильно понял задачу: [описание]?"
- "Есть ли особые требования или ограничения?"
- "Нужно ли создать резервную копию?"

### Перед деплоем:
- "Я протестировал изменения локально. Все работает. Могу ли я деплоить?"
- "Хотите посмотреть на изменения перед деплоем?"
- "Есть ли активные пользователи сейчас?"

### При ошибках:
- "Обнаружена ошибка: [описание]. Откатить изменения?"
- "Нужно ли уведомить пользователей о проблеме?"
- "Какой приоритет у исправления?"

## 🎯 ЗОЛОТЫЕ ПРАВИЛА

1. **Безопасность превыше скорости** - Лучше спросить лишний раз
2. **Тестирование обязательно** - Нет тестов = нет деплоя  
3. **Откат всегда возможен** - Сохраняй возможность отката
4. **Логи - наши друзья** - Всегда проверяй логи после изменений
5. **Коммуникация критична** - Держи пользователя в курсе

## ⚠️ ПОСЛЕДСТВИЯ НАРУШЕНИЯ

- Сломанный production = недовольные клиенты
- Потеря данных = катастрофа
- Потеря доверия = конец сотрудничества
