# VIP Client Care

VIP-клиент — это человек, у которого **живой продукт на нашей платформе или
заказная работа у нас**: он платил, у него есть свой бот, мини-апп, данные
его клиентов. Ошибка с ним стоит не одного недовольного сообщения, а доверия
и его бизнеса. Не путать с `club-vip-month`, где речь только о выдаче месяца
клуба за наличные.

Пример, на котором навык написан, — `turbobot-client-delivery` (клиент
TurboBaby, эпик #3937): там конкретика, здесь правила для любого VIP.

## Доволен = вот это, и ничего лишнего

Клиент доволен, когда за один заход он:

1. видит **что сделано, что в работе и что ждёт его** — коротко, письменно;
2. отвечает **одним словом** на **один список «да/нет»**, и больше от него
   ничего не нужно;
3. знает, что **без его «да»** ничего не ушло в прод, не перенесено и не
   отправлено;
4. не встречает в ответе ни обещаний за владельца, ни выдуманных сроков.

Звонков не предлагать, если он от них отказался. Не просить его сделать то,
что можем сделать мы.

**Закрытое не открывать.** Оплата, которую он уже сделал и о которой уже
поговорили, в отчёт не попадает — ни «спасибо за оплату», ни напоминания
(владелец, 11.10.2026: «мы уже проехали это»). То же для любой темы, по
которой договорились: отчёт только о том, что движется сейчас.

## Под контролем = один трекер и проверенные статусы

- **Один приватный трекер** (эпик в приватном репозитории) — единственный
  список работ по клиенту. Находки по безопасности живут **только там**.
- **Публичное — отдельно и без клиента.** Эпик в публичном репозитории
  описывает продукт и работу, но без имени клиента и без находок аудита.
- **Каждый статус берётся из источника, а не из памяти:** PR и CI — через
  `gh pr view` / `gh run list`, переписка — через `crm_lead_context`,
  деплои — по запускам workflow. «CI в очереди» не значит «зелёный», и так и
  пишется.
- **Каждое обещание записано** в трекере: что, кто, когда обещано. Срок — это
  долг, его возвращают.
- **После каждого шага — комментарий в трекере** с тем, что проверено и чем.

## Что нельзя ни при каких «давай быстрее»

- **Прод — только с его «да».** Прежде чем сливать любой PR в его репозиторий,
  проверить, не запускает ли слияние деплой (`gh secret list`,
  `gh variable list`, триггеры `deploy.yml`). Слияние, которое деплоит, — это
  деплой. Если деплой не нужен, а слить надо, это решает владелец; агент не
  обходит запрет разрешений.
- **Находки не уходят в публичное:** ни в публичные репозитории, ни в группы,
  где есть посторонние, ни по ссылке без авторизации. Отчёт о безопасности —
  текстом в Telegram, а не файлом на публичной полке.
- **Секреты не идут через чат.** Новый токен клиент ставит сам, или его ставим
  мы в Railway, но не пересылаем. Если клиент сам прислал ключ в чат —
  попросить отозвать и вычистить его из CRM и Zep.
- **За владельца не отвечать:** права, условия выхода, цены, сроки и юридическое
  пишет владелец своими словами. Агент готовит черновик и оставляет `‹дата›`.
- **Автоответы выключены — значит, выключены.** Если клиент их отключил, пишет
  только владелец; агент готовит черновик.

## Куда отправлять

Перед отправкой проверить чат, а не угадывать по названию:

```
tg_common_chats { user: <id> }         где мы вместе
tg_participants { chat: -100<id> }     кто там: люди и боты
tg_history      { chat: -100<id> }     что это за чат на деле
```

- **Группа с посторонними** — не для отчёта о безопасности.
- **Лента уведомлений его агентов** — сообщение утонет, а его боты его прочтут.
- **Сомневаешься — спроси владельца**, показав варианты и состав каждого чата.
  Отправка — только через `tg_send` (это предложение, владелец подтверждает).

## Шаблон отчёта-дашборда (Telegram, одно сообщение)

```
<Имя>, привет! Коротко, где мы. Звонок не нужен.

✅ СДЕЛАНО
• <результат> — <как проверено>

🔄 В РАБОТЕ (делаем мы, от тебя ничего)
• <что> — <статус из источника>

⏳ ЖДЁТ ТВОЕГО «ОК» (одним словом на всё)
1. <действие> — <что будет и что не будет>

🧭 ЧЕСТНО О ГРАНИЦАХ
• <чего пока нет и почему>

От тебя: «ок» или вычеркни лишнее.
```

Правила шаблона: только проверенное; цифры — с тем, как получены; ни одного
секрета, id чужих клиентов, внутренних путей; меньше 4096 символов (лимит
Telegram).

## Порядок работы

1. Перечитать клиента: `crm_lead_context`, `crm_client_timeline`,
   `crm_history`. Ждёт ли ответа — сначала ответ.
2. Перечитать трекер и все связанные PR/CI — статусы из источника.
3. Сделать то, что делается без его «да», с тестом и отрицательным контролем.
4. Собрать отчёт по шаблону; список «да/нет» — один.
5. Показать владельцу текст и адресата; отправить через `tg_send` после его
   подтверждения.
6. Записать в трекер: что ушло, что обещано, к какому сроку.

## Пишем на .t27

**Владелец, 07.10.2026: «все пишем на .t27».** Число, порог, правило, цена,
лимит, порядок на экране -- всё, что в этой теме решает поведение, пишется
спекой `.t27` ПЕРВОЙ (в `gHashTag/t27`); хост импортирует числа из вывода
`t27c gen-ts`, а тест гоняет каждый `test` спеки против кода. Код без спеки --
долг, а не норма. Как именно, законы и ловушки -- только в навыке
`t27-spec-first`: здесь указатель, не копия правила.
