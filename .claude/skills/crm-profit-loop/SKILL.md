# Виток CRM → прибыль

## When to Use This Skill

- Автономный цикл «исследуй слабые места CRM, конкурентов, реализуй» (крон 15 мин).
- Любая правка того, что решает «клиент заплатил», «что ему писать дальше»,
  «сколько он принёс».
- Перед тем как сказать «это у нас уже есть»: сначала `tri paid-sources` и
  таблица ниже.

## Quick Diagnosis

```bash
tri loop                 # память цикла: что в работе, чего не трогать
tri paid-sources         # каждое «кто платил» читает живой кошелёк? (✗ = только архив)
git log --oneline -8 origin/main   # параллельные сессии льют в main постоянно
```

## Главное правило денег (не забывать)

**Живой кошелёк — `token_ledger` / `user_tokens`. `payments_v2` — архив, в него
никто не пишет с 20.09.2026.** Любой код, решающий «заплатил ли», обязан читать
`token_ledger` (kind `'purchase'`, `delta > 0`; `grant` — не деньги).
`whoPaid(scope, pool)` — со вторым аргументом; без него — только архив.
Сторож: `render/paid-reads-the-live-wallet.test.ts` падает на голом вызове.

## Карта слабых мест (аудит 27.09.2026) и статус

| #   | Слабое место                                                                                               | Влияние        | Статус                                                                                                       |
| --- | ---------------------------------------------------------------------------------------------------------- | -------------- | ------------------------------------------------------------------------------------------------------------ |
| 1   | Оплата через `crm_offer` (звёзды → `token_ledger`) не делала клиента «платившим» — его снова уговаривали   | высокое        | ✅ `tokenBuyers` + все вызовы `whoPaid` с пулом                                                              |
| 2   | После 3 дней охлаждения неоплаченный счёт превращался в НОВЫЙ счёт                                         | высокое        | ✅ `unpaidInvoicesSince` → шаг `talk`, «спросить, получилось ли»                                             |
| 3   | Молчание после НАШЕГО сообщения невидимо в «Кто ждёт» (`waitingOn` без касания `written` не даёт `theirs`) | высокое        | ⏳ частично закрыто шагом `talk` в обходе; списка в приложении нет                                           |
| 4   | Нигде нет выручки / LTV / конверсии по стадиям                                                             | высокое        | 🟡 выручка клиента в сводке карточки (⭐ N, дата последней оплаты); общей выручки нет                        |
| 5   | `crm_summary` (воронка по стадиям) и `crm_winback` не показаны в приложении                                | средне-высокое | ⏳                                                                                                           |
| 6   | `toWaiting` в приложении выбрасывает `next_why`, `move`, `urgency`; кнопки только пишут касание            | среднее        | ✅ строка показывает `next_why`; «✍ Подготовить» — задача агенту в ветке клиента (клиенту ничего не уходит) |
| 7   | Карточка клиента показывает другую стадию, чем список (`crm_history` без времён сообщений)                 | среднее        | ✅ `crm_history` читает время последних сообщений (мутация убита)                                            |
| 8   | Обучение ходов (`crm_move_stats`) не видит оплат звёздами — вес «купил» ≈ 0                                | средне-низкое  | ⏳ (после #1 можно брать `token_ledger`)                                                                     |

Мелкое: пустые состояния без «что делать»; порог winback в трёх местах разный
(60 / 30 / «месяц»); владелец не получает уведомления, когда клиент оплатил.

## Разрыв с конкурентами (исследование 27.09.2026)

Что есть у amoCRM/Kommo, SaleBot, BotHelp, Pipedrive, Close, HubSpot, CRMchat —
и чего нам не хватает, по убыванию денег для соло-продавца:

1. Дожим молчащих по расписанию (день 1/3/7).
2. Ссылка на оплату прямо в чате, которая сама двигает стадию в «купил».
3. Реактивация сегментов (бывшие покупатели, «остыли»).
4. Утренний дайджест «кому писать» и тревога «сделка гниёт» (Pipedrive).
5. Скоринг / вероятность покупки.
6. Причины отказа + конверсия по стадиям.
7. Реферальная механика (SaleBot, BotHelp).
8. LTV, средний чек, повторные покупки.

**Где мы сильнее (не терять):** агент пишет из НАСТОЯЩЕЙ лички владельца
(Telegram Business), каждый дожим — из всей переписки, а не шаблон, и каждое
сообщение уходит только по нажатию владельца. Конкуренты продают автоматизацию,
которую надо собирать руками, и прячут ИИ за дорогими тарифами.

## Solution Steps (порядок витка)

1. `tri loop`, `git fetch && git log origin/main -8`: не делать чужое.
2. Выбрать верхний ⏳ из таблицы. Узко: одна правка, один PR.
3. Тест + мутация (`tri mutate`), двойник базы, который умеет бросать.
4. Коммит: pre-commit идёт ~4 мин (typecheck) — запускать в фоне и работать дальше.
5. PR → слить самому (постоянное поручение владельца), при конфликте — влить main.
6. Обновить таблицу статусов здесь и `tri loop-note`.

## Common Issues

- **Параллельные сессии правят те же файлы** (Королева: #3120, #3123 за час).
  PR ловит конфликт между отправкой и слиянием — влить main, прогнать
  затронутые тесты, отправить, слить сразу.
- **Счёт выпускается при подготовке карточки, а не при отправке.** «Счёт ушёл»
  = касание `written` (его пишет только нажатие) ПОСЛЕ `created_at` счёта.
- **`waitingOn` не выводит `theirs` из одних сообщений НАМЕРЕННО**: исходящее
  часто — бот, доставивший заказ. Не включать вслепую — очередь на тысячу строк.
- Чтение продовых данных из сессии может быть запрещено классификатором
  («Production Reads») — не обходить; спросить владельца или считать по коду.
- **Ожидалка `until ! pgrep -f "lefthook run"` ждёт САМУ СЕБЯ**: её собственная
  командная строка содержит эту строку, и цикл не кончается никогда (27.09:
  восемь зависших ожидалок). Искать по пути бинарника:
  `pgrep -f "lefthook-linux-x64/bin/lefthook run"`.
- Коммит идёт ~4 мин (tsc), отправка ~10 мин (связанные тесты). Не ждать в
  переднем плане: коммит/отправку — в фон, следующую задачу — сразу. Но файлы,
  лежащие в идущем коммите, не править до его конца.
