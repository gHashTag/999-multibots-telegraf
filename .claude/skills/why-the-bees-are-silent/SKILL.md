# Почему пчёлы молчат

Владелец смотрит на доску Королевы (`app.t27.ai/queen`, вкладка «Улей») и
пчёлы не шевелятся. Вопрос звучит как «почему пчёлы молчат?» / «улей стоит» /
«королева ничего не делает». Прежде чем сказать «сломалось» — проверь по
логам, потому что чаще всего **ничего не сломано**: движок жив и честно
говорит, что ему нечего дать в работу.

## Where the hive actually lives (не в этом репозитории)

- **Доска (кадр)** встроена в приложение из `vibee-render` по пути `/queen/`
  (сборочная стадия `queen`, пин `QUEEN_REF` из `gHashTag/trinity`).
  Файлы этой стороны: `apps/vibee-editor/player/src/pages/Hive.tsx`,
  `apps/vibee-editor/player/src/lib/hive.ts`, `.../lib/queen.ts`.
- **Живые данные пчёл** отдаёт `trios-agent-server` (домен
  `trios-agent-server-production.up.railway.app`, он же `api.t27.ai`),
  проект Railway **999** (`564d9ebd-…`), сервис `40d67e62-…`. Движок Королевы
  (`queend`, Swift + Node) собирается из **`gHashTag/BrowserOS`**,
  подкаталог `trios/agent-server`. Это **не** `999-multibots-telegraf` — из
  сессии сюда только read-клон, пуш недоступен.
- `queen-proxy` (`db07da91-…`) — это лишь LLM-прокси воркеров (z.ai
  `glm-4.5-flash`), **не** путь данных доски. Его остановка доску не гасит.

## Diagnosis, по шагам (всё через Railway MCP — рендер из сессии закрыт сетью)

1. **Жив ли движок и что он решает каждый тик.**
   `mcp__Railway__get-logs` на проект `564d9ebd-…`, сервис `40d67e62-…`,
   окружение `e4d200ad-…`. Ищи строки `Queen round starting` /
   `Queen tick decided`. Здоровый простой выглядит так:

   ```
   Queen tick decided   chosen=null   refusal="nothing to choose"   candidates=496
   Ring-00 ... canStartAnother  running=0  freeSlots=4  answer=true
   ```

   Это **не поломка**. Движок тикает, у него есть свободные слоты
   (`freeSlots>0`) и сотни кандидатов — и он никого не выбирает. По
   комментариям самого движка (`queen-tick.ts`, ~стр. 825): ни одна задача в
   истории не написана самой Королевой; когда бэклог наполняют, она
   вычерпывает его за час и возвращается к «нечего выбрать» — **это
   отсутствие поставки, а не дефект планировщика**. 496 открытых issue ≠ 496
   пригодных: кандидат отсекается, если уже заявлен (claimed), не является
   делегируемой спекой (нет `acceptanceCriteria`), или состязательная
   проверка нашла, что сгенерированный код не компилируется.

2. **Отличи честную тишину от настоящей поломки.** Тревога — это НЕ
   `chosen=null`, а:
   - тик вообще не идёт (нет свежих `Queen round starting`) → движок мёртв,
     смотри `deploy`-логи на краш/рестарт-петлю;
   - `refusal` про ёмкость («N workers already running (limit N)») при
     `running`, которого на деле нет → фантомные `running`-строки держат
     слоты (историческая ловушка `awaitingReview`, `queen-tick.ts`);
   - `Ring-00 disagrees` → две реализации (Swift `queend` и Node Ring-00)
     видят разные доски.

3. **Что вернула единственная запущенная пчела.** Строка
   `Queen reviewed her own work`. `verdict=empty` с `criteria=0 specs=0
   t27c="absent" oracle="no witness" files=0` означает: пчела ничего не
   произвела и предъявить нечего — задача была без спеки/критериев.

4. **Проверь, что доска реально грузится (кадр, не движок).**
   `get-logs` тип `["http"]` на том же сервисе. Панели доски дергают
   `/queen/status`, `/queen/public-board`, `/queen/public-activity`,
   `/queen/public-research`, `/queen/public-hardware`. **200** = кадр жив и
   честно показывает простой. **404** на пути (замер 26.09.2026:
   `/queen/public-foundation`, `/queen/public-modules`) = отдельная беда:
   эти подвкладки пустые, потому что маршрута нет в задеплоенной ветке
   (`fix/queen-worker-provider-and-prompt-size`). Это тишина панели, а не
   тишина пчёл.

5. **Есть ли незадеплоенные правки.** `mcp__Railway__describe-service` →
   поле `staged`. `changeCount>0` со свежим `createdAt` = кто-то (владелец
   или его инструмент) уже правит именно этот сервис. **Не** делай
   `accept-deploy` без подтверждения владельца — это видимое наружу
   необратимое действие, а правки могут быть недоделаны.

## The exact predicate (queend choose, BrowserOS)

Для КАЖДОГО открытого issue по порядку (queend `main.swift` `case "choose"`,
c25e1b0) кандидат пропускается, если:

1. **claim** — на issue уже есть живая/сделанная задача
   (`QueenDelegationPolicy.claimOnIssue`);
2. **нет тела** — issue без body;
3. **не делегируемая спека** — `QueenSpecQuality.judge(body)` даёт
   `delegatable == false`, ТО ЕСТЬ нет секции `## Boundary` (или `## Границы`)
   хотя бы с одним путём. Это капитальный отказ: без границы Королеве нечего
   зарезервировать, и бегун нашёл бы столкновение, врезавшись в него;
4. **конфликт границ** — пути уже держит идущая задача.

Первый, кто прошёл все четыре, — выбран. `delegatable` решает ТОЛЬКО граница;
остальные три раздела (сценарии Given/When/Then, `## Requirements` с
`FR-NNN … MUST`, `## Success Criteria` с измеримым исходом) — это `isSpec`,
качество, а не право на запуск. Замер в самом коде: «24 of 27 open issues were
not specs, which is why the swarm had one candidate and looked idle». На доске
26.09 — 496 открытых, 0 пригодных: у беклога нет `## Boundary`.

## The honest answer, and the cure

Пчёлы молчат не потому что улей сломан, а потому что **Королеве нечего
строить**: среди открытых issue нет делегируемых спек. Лекарство — не ослаблять
её ворота (это вернёт задокументированные столкновения), а **дать поставку**:
issue с `## Boundary` и тремя разделами в репозитории `TRIOS_GITHUB_REPO`
(дефолт `gHashTag/trios`). Это ровно миссия из `CLAUDE.md` — код рождается из
спеков.

**Инструмент — `tri spec`** (та же проверка, зеркало `QueenSpecQuality`):

```
tri spec check <файл.md>   возьмёт ли Королева этот issue: разбор по 4 разделам,
                           exit 1 если не делегируем (нет ## Boundary)
tri spec new "<заголовок>" печатает готовый делегируемый спек-шаблон
```

Так поставку можно ПРОВЕРИТЬ до того, как завести issue: `tri spec new` →
заполнить существом → `tri spec check` → exit 0 → завести. Реализация:
`apps/vibee-editor/render/src/agent/spec-quality.ts` (+ `spec-quality.test.ts`),
CLI `render/scripts/spec-check.ts`.

**Глубже (в движке, вне пуш-скоупа сессии):** Королева НИКОГДА не пишет спеки
сама — по её же коду ни один issue не написан ею. Настоящая автономия — шаг
«спек-писатель» перед выбором, в `gHashTag/BrowserOS trios/agent-server`. Это
не делается вслепую ночью в чужом репозитории с веткой-фиксом в полёте — нужен
push-доступ и слово владельца.

## Чего НЕ делать

- Не объявлять «улей упал», не проверив тик (п.1). Простой Королевы —
  штатное состояние.
- Не пушить правки в `gHashTag/BrowserOS` вслепую: репозиторий вне пуш-скоупа
  сессии, и там обычно уже есть ветка-фикс в полёте — легко столкнуться.
- Не `accept-deploy` чужие staged-правки без слова владельца.
- `curl` на рендер/`api.t27.ai` из контейнера сессии не пройдёт (сетевая
  политика). Только Railway MCP.
