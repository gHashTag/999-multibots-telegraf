# Экономная проверка

## Зачем

Проверки в этом репозитории различаются по цене в **тысячу раз**. Один
XCUITest идёт минуту, один vitest — доли секунды. Привычка «прогнать всё»
съедает смену: за один заход я потратил больше двадцати минут на полные
прогоны iOS, где хватило бы трёх запусков по секунде.

Дорогой прогон вместо дешёвого — не осторожность. Это трата времени, которое
должно идти в работу, и она ничего не добавляет к уверенности: тест, который
не может упасть на этом дефекте, не становится полезнее оттого, что он
медленный.

## Цена, замеренная в этом репозитории (06.09.2026)

| проверка | время | чем платим |
|---|---|---|
| `npx vitest run <файл>` (render) | **0,2–0,8 с** | ничем |
| `npx vitest run` весь render (78 файлов) | 11–53 с | ничем |
| `npx vitest run` весь player | 4–20 с | ничем |
| `npx tsc --noEmit` | 5–20 с | ничем |
| `xcodebuild build` | 30–90 с | диск (DerivedData) |
| `xcodebuild test -only-testing:VibeeTests` | 40–60 с | сборка + диск |
| **один** XCUITest | **35–75 с** | симулятор занят целиком |
| весь `VibeeUITests` | **5–6 мин** | то же |
| `bun run verify` | 3–15 мин | всё сразу |

## Правило

**Бери самый дешёвый вид проверки, который СПОСОБЕН упасть на этом дефекте.**

1. Логика, формула, разбор строки → **юнит-тест одного файла**. Секунда.
2. Проводка (помощник написан, но не вызван) → **тест по исходнику**
   (`fs.readFileSync` + регулярное выражение). Тоже секунда, и ловит ровно тот
   класс, который юнит-тесты пропускают.
3. Согласие двух списков (клиент против сервера) → **тест, читающий оба**.
   Секунда.
4. **Только то, что видно ИСКЛЮЧИТЕЛЬНО на экране** → XCUITest. Это подписи,
   зависящие от состояния экрана, и порядок проверок в интерфейсе.

Если сомневаешься между уровнями — бери нижний и проверь мутацией: вернул
дефект, тест покраснел? Значит уровень выбран верно.

## Что делать вместо полного прогона

- **Во время правки** — только затронутый файл: `npx vitest run <файл>`,
  `-only-testing:VibeeUITests/КлассTests/testИмя`.
- **Мутацию** проверяй ОДНИМ тестом, а не набором. Мутация — это вопрос «этот
  тест ловит этот дефект», и остальные тесты к вопросу не относятся.
- **Полный прогон — один раз перед PR**, и то по затронутым пакетам. Трогал
  только `render` — не гоняй player и iOS.
- **iOS собирается один раз**: `-only-testing` с несколькими тестами дешевле,
  чем несколько запусков `xcodebuild` подряд, — сборка не повторяется.
- Долгое пускай **в фоне** (`run_in_background`) и работай дальше, а не жди.

## Чего НЕ делать

- Не гонять `VibeeUITests` целиком, чтобы проверить один новый тест.
- Не гонять `bun run verify` в середине работы: он для готовности к релизу, а
  не для обратной связи.
- Не пересобирать iOS ради правки, которой в iOS нет.
- Не повторять зелёный прогон «на всякий случай». Один зелёный — уже ответ;
  повторять стоит только при подозрении на мигание, и тогда повторять надо
  ИМЕННО мигающий файл.

## Мигающие тесты

Замечено за смену: `autopilot-poster-record.test.ts` и
`noBareBuiltinInMockFactory` падают под нагрузкой и проходят в одиночку
(таймаут 5000 мс при занятой машине). Прежде чем чинить такое, запусти файл
ОТДЕЛЬНО — это две секунды и обычно снимает вопрос.

## Место на диске

`xcodebuild` растит DerivedData на каждый прогон. `bin/tri ios` чистит за
собой; ручной `xcodebuild test` — нет. После серии прогонов iOS —
`bash .claude/loop-opus/free-disk.sh`.
