# VIBEE stack: hard-won lessons

Everything here was paid for once. Do not re-derive it.

## THE RULE THAT MATTERS MOST

**A green build proves nothing. Verify on the live deploy.**

Every real defect in this stack passed `npm run build`. Every one was caught by
loading the deployed page and measuring it. If a change is not verified against
the running service, it is not done.

## Dead code that looks alive

This codebase has a repeated pattern: a component is built, committed, and wired
to nothing. Three separate fixes landed in such files before anyone noticed.

Confirmed dead or previously dead:
- `VerticalTabs`, `BottomNavigation` — exported, rendered nowhere. Superseded by
  `TelegramTabBar`.
- `components/AssetBrowser/AssetBrowser.tsx` — **not imported anywhere**.
  `Timeline` has its own inline browser instead.
- `assetBrowser.ts` exports a `CATEGORIES` array that nothing reads. `Timeline`
  declares its **own local** `CATEGORIES` at ~line 588.
- Four RPC wrappers in `getUserBalanceStatsOptimized.ts` call functions that do
  not exist in the database and have zero callers.

**Before editing a component, prove it renders:** grep for its import outside its
own folder, then confirm the element exists in the live DOM.

## Traps by area

### Railway
- `railwayConfigFile` resolves against the **repo root**; service-level
  `dockerfilePath` resolves against the **Root Directory**. Two conventions.
- A service's **first** deployment races the Root Directory setting and builds
  the repo-root Dockerfile. Push a commit to a watched path to get a correct one.
- Root `.dockerignore` patterns are context-root anchored — they do not match
  `apps/**`.
- Applying staged changes needs 2FA; the API cannot. Use the dashboard via
  BrowserOS neo.
- Serve **both** `/health` and `/healthz`: which config wins is not obvious.

### Supabase → Railway Postgres
- `SUPABASE_SERVICE_KEY` is **misnamed**: its JWT decodes to `role=anon`. The
  real one is `SUPABASE_SERVICE_ROLE_KEY`. `getSupabaseKey()` prefers the former,
  so the bot has been querying as anon.
- `DATABASE_URL` in the bot's variables is a dead local placeholder.
- PostgREST serves a full swagger at `GET /rest/v1/` with exact column types —
  authoritative, better than any inference.
- Fetch numerics as `::text`. `JSON.parse` collapses `"30.00"` to `30` and the
  scale is gone. `payments_v2.stars` is `numeric(12,2)`.
- `storage_path`, `trigger_word`, `type` are **NOT NULL** in `assets`.
- Cutover happens in **Infisical, not Railway**: `core/infisical/index.ts:172`
  overwrites `process.env` with every secret at boot.

### The editor
- `supabase-js` always appends `rest/v1` to the base URL (`SupabaseClient.js:78`).
  A bare PostgREST needs a path-stripping gateway.
- `response.statusText` is **empty on HTTP/2**, which is all Railway serves.
  Always include the status code and body in error messages.
- `--touch-target: 44px` exists in `index.css`. Nine controls set height through
  `padding` alone and measured 28px. Use explicit lists, never
  `button { min-height }` — it inflates the dense editor panels.
- Media in `public/` resolves against the **editor's own origin**
  (`MEDIA_ORIGIN`), never the render server, which has no `public/`.

### The render server
- `getPool()` throws **synchronously**. Outside a `try` it escapes an async
  handler and Node 20 kills the process — a one-request DoS.
- `type` in `assets` holds the **model name** (`veo3_fast`), not the media kind.
  Derive video/audio/image from the URL extension.
- The bot does **not** call `vibee-render` — но причина НЕ та, которую я
  записал здесь раньше. Прошлая версия этой строки утверждала, что всё дело в
  захардкоженном несуществующем хосте в `render-server-client.ts`. Это было
  неверно: функция, которая туда ходит (`sendDirectToRenderServer`), **нигде не
  вызывается**. Мёртвый код.

  Настоящая цепочка: визард → `sendRenderAvatarVideoEvent` → Inngest
  (инстанс RENDER, ключи заданы) → `renderRiddleFunction` внутри самого бота.
  Она рабочая: функция зарегистрирована, бот отдаёт `/api/inngest`, health 200.

  Обрыв — в самом конце. Последний шаг шлёт событие **`render/execute`, у
  которого нет ни одного подписчика**: строка встречается во всём `src/` ровно
  один раз (сам `send`), а из 33 подписок render-события это `render`,
  `render-riddle` и `render/avatar-video`. Пайплайн тратит деньги у четырёх
  провайдеров и возвращает `success:true`, не отрендерив ничего.

  Причина архитектурная: путь рассчитан на ферму nexrender с шаблонами After
  Effects по SSH (`.aep`, `server_url/port/user`,
  `composition_name='Instagram_Story'`), а `vibee-render` — это Remotion с
  единственной композицией `SplitTalkingHead`. Две половины не соединяли.

## Сервис может врать о самом себе

`GET /compositions` на рендер-сервере отдавал захардкоженный список из шести
шаблонов. В `render/src/Root.tsx` зарегистрирован **один** — `SplitTalkingHead`.
Пяти из шести не существовало.

Обнаружилось только когда я впервые реально дёрнул рендер:

    POST /render {"compositionId":"TextOverlay"}
      -> 202 {"success":true,"renderId":"e0db6704-..."}
    ...через 15 секунд
      -> {"status":"failed","error":"Could not find composition with ID
          TextOverlay. Available compositions: SplitTalkingHead"}

Два отдельных дефекта в одной цепочке, и оба класса «принять и упасть позже»:

1. **Список возможностей, написанный руками, расходится с кодом.** Он не может
   не разойтись — ничто их не связывает. Списки надо выводить из источника
   (`getCompositions(bundleLocation)` читает тот самый бандл, которым рендерят).
2. **Проверка на входе была только на непустую строку.** Существование
   проверял воркер — асинхронно, когда клиент уже показал человеку прогресс.
   Всё, что можно проверить в момент приёма задачи, надо проверять в момент
   приёма.

Отдельно: `defaultProps` у `SplitTalkingHead` ссылаются на `/public/b-rolls/*`
и `/public/lipsync/lipsync.mp4` — каталога `public/` в приложении рендера нет
вообще, все пять путей отдают 404. Продакшн это не задевает: бот идёт через
`/api/inngest` (`render-riddle`) и передаёт абсолютные URL в payload. Прежде чем
чинить «сломанное», проверь, ходит ли туда продакшн — иначе чинишь декорацию.

## «Сузим позже» не наступает

Я сам написал `scripts/postgrest-roles.sql` с `GRANT ALL ... TO anon` и
комментарием, что сузить это — отдельная задача. Через несколько циклов
проверка показала: `GET /rest/v1/payments_v2` без единого заголовка отдаёт 200
и `content-range 0-0/17135`, `users` отдаёт telegram_id и почты, а анонимный
OpenAPI объявляет `DELETE` и `PATCH` на 11 таблицах. `information_schema`
подтвердил напрямую: у `anon` были DELETE, INSERT, UPDATE и **TRUNCATE** на 14
таблицах.

В PostgREST `anon` — это роль запроса **без токена**, то есть любой человек в
интернете. Балансы считаются суммированием `payments_v2`; один анонимный
DELETE обнулил бы баланс каждого клиента.

Правило: привилегию, которую нельзя обосновать сейчас, не выдают «на время».
И `REVOKE` в идемпотентном скрипте пишут безусловно — иначе повторный прогон
оставит уже выданное на месте.

## Внешний catch съедает твой throw

`getUserBalance` возвращал 0 при ошибке RPC — и ещё раз 0 из внешнего `catch`.
Я добавил `throw` внутри `if (error)`, typecheck прошёл, всё выглядело
сделанным. Бросок ловился двумя кадрами ниже и снова превращался в 0.

Проверять надо не «компилируется ли», а «доходит ли эффект до вызывающего».
Дешёвый способ: удалить свою же строку и убедиться, что тест падает. Здесь —
3 из 6 падают без пробрасывания, 6 из 6 с ним. Тест, который проходит и до
правки, ничего не доказывает.

## Severity меряют по данным, а не по коду

Отчёт называл двойное списание в `modelTrainingV2` «деньгами, утекающими из
бизнеса прямо сейчас». В коде — да. По факту: все 105 платежей за тренировку
имеют `service_type = digital_avatar_body` (v1), ни одного `..._v2`; join на
пары двойных списаний даёт 0 строк; возвратов `Refund for model training` — 0.
Путь ни разу не выполнялся.

Ошибка настоящая и чинить её стоит — но называть латентный дефект активной
утечкой значит потратить чужое доверие. Перед словом «эксплуатируется» сходи
в таблицу и посчитай.

## Не доверяй собственной прошлой записи

Я записал в этот файл как факт, что рендер бота «шлёт задачи в никуда» из-за
несуществующего хоста. Следующий цикл потратил время, идя по этому следу, и
выяснил, что функция с тем хостом вообще не вызывается, а обрыв совсем в другом
месте.

Записанный неверный факт хуже отсутствия записи: он выглядит как проверенное
знание и экономит ровно ту проверку, которая бы его опровергла. Если запись
опирается на чтение кода, а не на живой запрос — так и помечай. И проверяй,
вызывается ли вообще функция, прежде чем объяснять через неё поведение
системы.

## Self-hosted Inngest на Railway: три отдельные причины 502

Сервис `inngest/inngest` крутился в петле перезапуска. Три разные ошибки
подряд, каждая видна только после починки предыдущей:

1. `signing-key must be valid hex string: invalid byte U+006D 'm'` —
   `INNGEST_SIGNING_KEY` был 32-символьной случайной строкой. Inngest требует
   именно hex. `openssl rand -hex 32`.
2. `at least one event-key is required` — `INNGEST_EVENT_KEY` не задан вовсе.
3. Деплой уже SUCCESS, но домен всё ещё 502: у домена `targetPort: null`, а
   Inngest слушает `INNGEST_PORT=8288`, которого Railway не знает. Помогает
   `PORT=8288` — прокси ищет именно его.

Вывод шире Inngest: «упало» на Railway — это часто очередь из нескольких
независимых причин. Смотри логи ПОСЛЕ каждой правки, а не после всех сразу, и
не считай зелёный статус деплоя ответом сервиса — статус был SUCCESS, пока
домен отдавал 502.

## Я написал инструмент, напечатал ответ и не прочитал его

Сверка отправляемых событий с подписками (`npm run check:events`) нашла
осиротевшее `neuro/photo.failed` — генерация падала, человек не получал ничего.
Я починил уведомление в `functions/generation/neuroImageGeneration.ts`,
typecheck прошёл, PR ушёл.

Функция не запускается. Она подписана на `neuro/photo.generate`, а это событие
встречается во всём репозитории только в двух объявлениях подписки —
отправителя нет. Живой путь другой: `neuroPhotoWizard` зовёт
`generateNeuroPhotoHybrid` напрямую, без Inngest.

Мой же скрипт напечатал `neuro/photo.generate` во второй половине вывода —
«подписка есть, но никто не шлёт». Я прочитал первую половину и правил файл,
считая его живым. Четвёртый раз в этом репозитории и первый — при наличии
инструмента, который прямо об этом сказал.

Из этого две вещи:

1. **Подписка без отправителя у ЗАРЕГИСТРИРОВАННОЙ функции важнее списка
   осиротевших событий.** Такая функция развёрнута, выглядит живой и не может
   быть запущена ничем. Скрипт теперь печатает её первой и словом
   «НЕДОСТИЖИМА». Таких — 16 из 23.
2. **Инструмент помогает, только если дочитать его вывод.** Прежде чем править
   файл с Inngest-функцией — найди отправителя её события. Одна команда grep.

Оговорка, которую скрипт печатает сам: он видит отправителей только внутри
репозитория. Вебхук или панель Inngest он не видит, поэтому его список —
кандидаты на проверку, а не приговор.

## Главное про Inngest в этом проекте: 16 из 23 функций недостижимы

Не единичный баг, а устойчивый паттерн. Inngest-функции написаны как ВТОРАЯ
реализация того, что бот уже делает прямым вызовом сервиса, и к событиям их
никогда не подключили. Функция зарегистрирована, развёрнута, выглядит рабочей —
и не запускается ничем.

Подтверждено трижды, каждый раз с живым двойником рядом:

| Inngest-функция (недостижима) | Что работает на самом деле |
|---|---|
| `neuro/photo.generate` | `generateNeuroPhotoHybrid`, прямой вызов из визарда |
| `broadcast/send-message` | `services/plan_b/broadcast.service.ts` |
| `model/training.v2.requested` | v1 `generateModelTraining` — все 105 платежей за тренировку это `digital_avatar_body`, ни одного `_v2` |

Отсюда следствия, которые уже стоили нескольких циклов:

- Правка в Inngest-функции по умолчанию НИЧЕГО не меняет. Сначала найди
  отправителя её события: `npm run check:events` или один grep по имени.
- «Функция есть и она в registerFunctions» — не доказательство, что она
  работает. Регистрация означает только, что Inngest о ней знает.
- Ошибку в поведении бота ищи в сервисах и сценах, а не в `inngest_app/`.

Оговорка: скрипт видит отправителей только внутри репозитория. Вебхук и панель
Inngest ему не видны, поэтому 16 — это кандидаты на проверку, а не
доказанный ноль.

## Мёртвый домен three-head-dragon.shop в цепочках fallback

`three-head-dragon.shop` резолвится в `188.137.250.69` — СТАРЫЙ сервер, с
которого проект переехал на Railway. Он не отвечает: HTTP 000 по https, по
http, по голому IP и по самому пути коллбэка.

Домен стоит последним элементом в десятках цепочек вида
`process.env.X || 'https://three-head-dragon.shop'`. Опасность не в самом
fallback, а в повторяющейся ошибке: **нужная переменная в проде задана, но её
забыли внести именно в ЭТУ цепочку.** Найдено трижды подряд:

| Цепочка | Что было не так |
|---|---|
| `BASE_PAYMENT_URL` | `BASE_WEBHOOK_URL` задана, но её не было в цепочке → ResultURL Robokassa (серверное подтверждение оплаты) уезжал на мёртвый хост |
| `botBaseUrl` в `inngest-provider.ts` | `BOT_INNGEST_BASE_URL` задана, в цепочке только `INNGEST_BASE_URL`, которой нет |
| `webhookUrl` в AI Reels, `urls.get/cancel` в lipsync | Зашито вообще без альтернативы |

Правило: увидел `env.X || 'literal-домен'` — проверь, какие переменные РЕАЛЬНО
заданы в Railway, а не какие выглядят правильными в коде. Одна команда:
`railway variables -s <сервис> --kv | grep URL`.

Трекер: `npm run check:dead-domain`. Он намеренно НЕ роняет сборку — деление
«зашито / fallback» грубое и даёт ложные срабатывания на тексте предупреждений
и многострочных цепочках. Ворота можно включить, когда список опустеет.

## grep по выводу tsc молча врёт

`npx tsc --noEmit ... 2>&1 | grep -c "error TS"` вернул **0** на прогоне, где
была настоящая ошибка. Причина: tsc раскрашивает вывод, между словом `error` и
кодом `TS2688` стоят ANSI-последовательности, и литерал `error TS` не совпадает.

Я на этом основании заявил себе «в тестах 0 ошибок типов». Настоящее число —
1230. Всегда `--pretty false` (или `NO_COLOR=1`), когда считаешь ошибки грепом.

Тот же класс: `grep -c` на пустом выводе даёт `0`, что неотличимо от «проверка
прошла». Смотри код возврата, а не только число.

## Тесты в этом проекте не проверялись НИЧЕМ

`tsconfig.json` исключает все тестовые пути (строки 70-76): `__tests__`,
`**/*.test.ts`, `src/tests`, `src/helpers/test`. Поэтому `npm run typecheck` с
его «0 ошибок» не говорит о тестах ровно ничего.

Что там на самом деле (`npm run typecheck:tests`, конфиг `tsconfig.test.json`):
1230 ошибок типов. Из них 30 — TS2305, импорт символа, которого в модуле нет.
Такой тест не проходил ни разу с момента написания, и никакой командой в
репозитории это нельзя было увидеть.

Плюс к этому: из 182 файлов тестов 21 запускался НЕ ТЕМ раннером — 11 импортов
из `bun:test` под vitest и 10 Playwright-спек из `apps/`, которые корневой
прогон подхватывал. Они падали на загрузке модуля, ни один assert не
исполнялся. При 99 красных файлах из 182 отличить новую поломку от постоянного
шума было нельзя, то есть прогон не нёс сигнала вообще.

Правило: прежде чем верить зелёному `typecheck` или списку падений — проверь,
что именно входит в прогон. `tsc --listFiles | grep -c test` и
`exclude` в конфиге отвечают на это за секунду.

## Прослеживай значение до конца, а не до второй строки

Я написал в PR, что `botBaseUrl` — «используется клиентом двумя строками ниже,
так что правка не декоративна». Неверно. `new Inngest({ name, eventKey })`
не получает `baseUrl` вовсе; поле кладётся в объект конфигурации и встречается
дальше только в трёх logger-вызовах. Отправка идёт через `config.client.send()`,
а общий клиент создан без `baseUrl`, поэтому SDK берёт своё умолчание
`https://inn.gs/` (`node_modules/inngest/helpers/consts.js:180`).

Я увидел `baseUrl: botBaseUrl` в литерале объекта и решил, что это аргумент
SDK. Разница между «положено в мой объект» и «передано в чужую библиотеку» —
как раз то, что делает правку настоящей или косметической. Дочитывай до вызова.

## Мёртвый домен: закрыто, с воротами

`three-head-dragon.shop` (188.137.250.69) убран из кода полностью — 19 мест.
`npm run check:dead-domain` теперь ПАДАЕТ при его возврате (проверено в обе
стороны: вернул в один файл — выход 1, откатил — 0). Намеренные упоминания
помечаются `// dead-domain-ok: причина` на строке выше; такое ровно одно —
детектор в `diagnostic.routes.ts`, который предупреждает, что webhook указывает
на мёртвый хост.

В самой Railway три переменные были ЗАДАНЫ на мёртвый домен: `ORIGIN`,
`SERVER_API_URL`, `WEBHOOK_DOMAIN`. Переставлены на Railway-домен, а не удалены:
удаление перевернуло бы ветки `if (!webhookDomain)`. И это обезвредило ловушку —
`SERVER_API_URL` не читается ничем, поэтому «очевидное исправление опечатки» в
`API_SERVER_URL` поставило бы мёртвый хост ПЕРВЫМ в платёжной цепочке Robokassa,
впереди рабочей `BASE_WEBHOOK_URL`.

Главный вывод: пустая строка в конце цепочки лучше мёртвого литерала. Мёртвый
хост превращает «ничего не настроено» в «настроено на сервер, которого нет», и
отказ становится молчаливым.

## TS2709 РЕШЕНО: `declare module 'vitest'` перекрывал настоящие типы

576 из 1230 ошибок в тестах давала ОДНА строка в `src/types/shims.d.ts`:

    declare module 'vitest';

Пустое объявление модуля делает его для TypeScript нетипизированным: каждое
импортированное имя становится namespace, а не типом. Поэтому
`import type { Mock } from 'vitest'` нельзя использовать как тип — сразу во всех
файлах. У vitest есть свои типы, и шим их не дополнял, а ЗАМЕЩАЛ.

## Коллбэк рендера не знал, каким ботом отдавать видео

`sendCallback` (`functions/render/helpers/renderSteps.ts:315`) шлёт ровно
`{ download_url }` — ни `bot_name`, ни `telegram_id`, ни metadata. А `render.ts`
и сам знает только `job_id` и `callback_url`, так что послать больше нечего.

Поэтому в обработчике `payload.bot_name || payload.metadata?.bot_name` был
undefined ВСЕГДА, и выбор бота падал на захардкоженную карту из пяти
владельцев. Остальным видео уходило через `defaultBot` — то есть не из того
бота, в котором его заказали.

Решение — не тащить значение через чужой payload, а положить его В САМ URL:
`?bot=<name>` собирается в `createRenderAvatarPayload`, где бот известен
достоверно. Ничего в рендер-сервере менять не пришлось, и потеряться по дороге
такое не может.

**Карта из пяти строк противоречила базе по КАЖДОЙ существующей строке**
(144022504: карта говорит `neuro_blogger_bot`, база — `HaimGroupMedia_bot`; и так
все четыре, пятого пользователя в базе нет). Значения выглядят перетасованными.
Какая сторона врёт — неизвестно, и это и есть довод: рукописная таблица из пяти
строк, расходящаяся с данными, не должна решать, кто получит видео.

Кто прав — выяснено по `payments_v2` (каким ботом человек РЕАЛЬНО платит):
**ни один источник не прав целиком.** Для 352374518 и 1254048880 права база,
для 7669741878 — карта, для 1852726961 оба неверны, а у 144022504 доминирующего
бота нет вовсе. Отсюда и вывод: достоверен только `?bot=` из самой задачи.

Общее правило: когда два справочника расходятся, не выбирай между ними — найди
третий источник, который отражает поведение, а не намерение. Здесь это платежи.

Отдельно: `users.bot_name` — это бот, через которого человек ЗАРЕГИСТРИРОВАЛСЯ,
а не бот, которым он владеет. Я сначала заменил карту на запрос к базе, считая
иначе; сравнение выше опровергло это ДО отправки. Прежде чем строить логику на
колонке — проверь, что она значит, на данных, а не по названию.

## AI Reels падает на ПЕРВОЙ строке, а не на render/execute

Несколько циклов я считал осиротевшее событие `render/execute` последним
обрывом. Это пятый обрыв, а не последний. Пайплайн умирает раньше всех трат:

`renderRiddle.ts:57` первой же строкой вызывает
`validateRenderRiddleEventData(event.data)`, и payload, который строит
`createRenderAvatarPayload` и шлют ВСЕ ЧЕТЫРЕ визарда, эту схему НЕ ПРОХОДИТ.
Проверено прогоном `RenderRiddleEventDataSchema.safeParse` — восемь причин, для
любого из трёх сервисов:

    kie_api_key            Invalid KIE API key
    eleven_labs_api_key    Invalid ElevenLabs API key
    avatar_gen_service     must be "hedra" or "heygen"   ← 'fal' схемой не принят

    avatar_settings.api_key         Required
    cover_url              Invalid cover URL   ← пустая строка не проходит .url()
    circle_position        Required
    circle_scale           Required

Отсюда правило: **прежде чем чинить звено, прогони вход через его собственную
схему.** Одна команда `safeParse` даёт больше, чем цикл чтения кода — и она бы
сэкономила несколько циклов, потраченных на звенья ниже по течению.

ПОЧИНЕНО (PR 440): сборщик payload расходился со схемой формой, а не мелочами.

никто — `renderRiddle` читает плоские `avatar_settings.avatar_speech` и т.д.,
ровно как объявляет `AvatarSettingsSchema`. Схема и потребитель были согласны
между собой; один сборщик выпадал. Правило выбора стороны: канонична та форма,
которую ЧИТАЕТ потребитель, а не та, которую пишет отправитель.

Мелочи, каждая стоила отдельного прогона `safeParse`:
- `circle_position` / `circle_scale` — это `z.tuple([number, number, number])`,
  а не `{x, y}`;
- `cover_url: ''` не проходит `z.string().url()` — нужно `undefined`;
- `heygen_api_key` требуется ОТДЕЛЬНЫМ полем верхнего уровня из-за `refine`,
  помимо `avatar_settings.api_key`.

Итог: hedra проходит схему полностью (было 8 ошибок, стало 0). heygen упирается

И следствие, которое дороже самого списка: раз готовое не подключено, рядом
почти наверняка написана ВТОРАЯ реализация того же. Так и оказалось —
`adminCommands.ts` имел СВОЙ захардкоженный список из четырёх ID под

435572800 был админом везде, кроме команд этого файла, получая отказ без
объяснения.

Правило: **найдя дубликат проверки, сравнивай не код, а ДАННЫЕ обеих сторон.**
Два списка админов выглядят одинаково правдоподобно, пока не сверишь значения.

Отсюда способ искать: **имя функции — это обещание, и его надо сверять с телом.**
Особенно у всего, что называется validate/sanitize/check и применяется к

## Что делать с заглушкой зависит от того, ВЫЗЫВАЕТСЯ ли она

За неделю нашлось пять заглушек, возвращавших успех. Правильное действие для
каждой оказалось разным, и решает его один вопрос — «кто её вызывает»:

| заглушка | вызывается | что сделано |
|---|---|---|
| `generateSpeech`, `transcribeAudio` (elevenLabs.ts) | да, но путь и так мёртв | **бросают** — молчаливая подделка хуже отказа |
| `validateLipSyncInput` (lipsync-schemas.ts) | НЕТ (`getLipSyncManager` без вызовов) | **бросает** — мина обезврежена, поведение не тронуто |
| `validateProjectInStep`, `ensureProjectsTableExists` | ДА, из двух зарегистрированных функций | **только комментарий** — бросок сломал бы живой поиск конкурентов |

Правило: **заглушка, которая врёт, плоха; заглушка, которая роняет живую
функцию, хуже.** Если код исполняется — сначала научи вызывающих читать ответ,
и только потом меняй тело.

Отдельно про `validateLipSyncInput`: её `true` использовался НЕ как признак
валидности, а как САМИ ДАННЫЕ — уходил в `cacheManager.generateKey()`, то есть
ключ кэша был бы один на всех пользователей. Компилятор молчал, потому что у
провайдера сигнатура `generate(input: any)`. **`any` в интерфейсе провайдера
прячет ровно такие ошибки** — ищи их там, где тип потерян.

ЗАКРЫТО: `generate(input: any)` заменён на `generate(input: UniversalLipSyncInput)`
(`core/lipsync/interfaces/lipsync-provider.interface.ts`). Тип слабый —
`{ [key: string]: any }`, — но булево ему уже не соответствует, и этого хватает.

Доказано пробником под конфигом ПРОЕКТА, а не рассуждением:

    p.generate(true)
    → error TS2345: Argument of type 'boolean' is not assignable to
      parameter of type 'UniversalLipSyncInput'

До правки тот же пробник компилировался чисто.

Приём общий: **чтобы проверить, ловит ли тип ошибку, напиши файл, который эту
ошибку делает, и посмотри на вывод компилятора.** Рассуждение «теперь-то
поймает» тут ничего не стоит — я дважды за эти циклы ошибался в том, что
компилятор увидит.

Оговорка честная: в том же интерфейсе осталось шесть `any` и сам
`UniversalLipSyncInput` — пустая индексная сигнатура. Правка закрывает
ПОКАЗАННУЮ дыру, а не весь класс.

## Self-hosted Inngest: почему в панели было пусто и как переключить

Панель показывала ноль функций и ноль прогонов не по ошибке: **бот слал события
в Inngest Cloud**, а не туда. SDK берёт `https://inn.gs/` по умолчанию, потому
что `baseUrl` не передаётся ни в `client.ts`, ни в `inngest-provider.ts`.

Переключение — три вещи, и все обязательны:

1. `INNGEST_BASE_URL` на сервисе бота. Эту переменную читает САМ SDK
   (`envKeys.InngestBaseUrl`), приложение её никуда не передаёт.
2. `INNGEST_EVENT_KEY` и `INNGEST_SIGNING_KEY` бота = ключи self-hosted. Пока
   они разные, сервер отвечает `Authentication failed` — ровно это и было видно.
3. Регистрация приложения. `POST /fn/register` на сервер требует `App ID` и
   отдаёт 400/401. **Работает обратное: `PUT` на `/api/inngest` САМОГО БОТА** —
   приложение синхронизируется само и отвечает
   `{"message":"Successfully registered","modified":true}`.

Проверка приёма событий до переключения, без риска:
`curl -X POST https://<inngest>/e/<EVENT_KEY> -d '{"name":"probe","data":{}}'`
→ `{"ids":["..."],"status":200}` значит ключ верный.

ПОДТВЕРЖДЕНО ЗАМЕРОМ, а не словами регистрации: `GET /v2/apps` с
`Authorization: Bearer <SIGNING_KEY>` показывает `telegram-bot-client` и
**functionCount: 28**. Это единственный работающий способ проверить —
`/v0/apps`, `/v1/apps`, `/v1/runs`, `/v1/functions` отдают 404 на этой версии,
а UI-пути возвращают 200 с HTML и ничего не говорят.

События смотреть так: `GET /v1/events?limit=50` с тем же Bearer.

ВАЖНО не спутать: ноль событий ≠ переключение не сработало. У меня после
переключения было ровно одно событие — мой собственный пробник, — потому что
бот шлёт события только из четырёх render-визардов, а ими за это время никто не
пользовался. Регистрация функций и трафик событий — РАЗНЫЕ вопросы, и
проверяются разными эндпоинтами.

Порядок важен: сначала ключи, потом проверка приёма, потом `INNGEST_BASE_URL`,
потом деплой, потом `PUT` для регистрации. Прежние ключи сохраняй перед заменой —
у меня они лежат в `/tmp/bot_inngest_backup.env`.

ПЕРВЫЙ НАБЛЮДАЕМЫЙ ПРОГОН. После переключения удалось послать настоящее
событие `render-riddle` и УВИДЕТЬ его выполнение — впервые за всю работу:

    POST /e/<EVENT_KEY>            → {"ids":["01M0D1E7SJ..."],"status":200}
    GET  /v1/events/<id>/runs      → прогонов: 1, статус Failed
    GET  /v1/runs/<runId>           → статус Running (ретраи)

Цепочка событие → Inngest → функция бота → выполнение работает и наблюдаема.
Раньше статусы приходилось выводить косвенно, по платежам в базе.

Полезные эндпоинты (все с `Authorization: Bearer <SIGNING_KEY>`):
`/v2/apps`, `/v2/apps/<appId>/functions`, `/v1/events?limit=N`,
`/v1/events/<eventId>/runs`, `/v1/runs/<runId>`.

Осторожно со статусом: список прогонов может показывать `Failed`, а карточка
того же прогона — `Running`. Это ретраи, а не противоречие; выводы делай по
финальному состоянию, а не по первому запросу.

ПРИЧИНА ОТКАЗА ЧИТАЕТСЯ ПОЛНОСТЬЮ — `?includeOutput=true` на `/v1/runs/<id>`
отдаёт сообщение и стек:

    Render-riddle event validation failed:
    intro_text_1: Required
    intro_text_2: Required
      at validateRenderRiddleEventData (/app/dist/index.js:40274)

Это ПЕРВЫЙ раз, когда причину отказа удалось прочитать напрямую, а не вывести
из кода. Раньше приходилось рассуждать по исходникам и ошибаться.

Результат оказался отрицательным, и это тоже ответ: неполон был МОЙ тестовый
payload, а валидация сработала верно. Все четыре render-визарда передают
`introText1` — проверено грепом по каждому. Продуктового дефекта здесь нет.

Урок для собственных проверок: **собирая тестовое событие вручную, бери поля из
`createRenderAvatarPayload`, а не из головы.** Иначе тест падает по своей вине,
а выглядит как находка — я едва не отчитался о ней.

ГРАНИЦА AI REELS ИЗМЕРЕНА, а не выведена. С payload, собранным самим
`createRenderAvatarPayload` (через `npx tsx`, а не руками), прогон:

    статус: Failed
    NonRetriableError: Рендер-бэкенд недоступен: ферма nexrender выведена из
    эксплуатации, а перевод на Remotion ещё не сделан. Работа остановлена ДО
    трат на озвучку, аватар, транскрипцию и b-roll.

То есть подтверждено ЖИВЫМ ПРОГОНОМ:
- валидация входа проходит (звено 1 работает);
- preflight, добавленный ранее, срабатывает и останавливает ДО трат у четырёх
  провайдеров — ровно как задумано;
- реальный обрыв — отсутствие рендер-бэкенда, а не что-то раньше по цепи.

Двадцать восемь итераций это утверждалось по чтению кода. Теперь измерено.

Приём, который к этому привёл: **генерируй тестовое событие тем же кодом,
которым его строит продакшн** — `npx tsx` с вызовом настоящего билдера,
результат в JSON, JSON в `/e/<EVENT_KEY>`. Ручная сборка payload дала ложный
отказ на предыдущей попытке.

Чего переключение НЕ чинит: 16 недостижимых функций не запускаются не из-за
адреса, а потому что событие-триггер никто не шлёт. И рендер видео оно тоже не
оживит. Даёт оно ВИДИМОСТЬ — впервые видно, какие события летят и где падают.

## Рендер Remotion принимает и стартует — упирается в МЕДИА

Прямая проверка `POST /render` с композицией `SplitTalkingHead` и минимальными
пропсами (`lipSyncVideo` + один сегмент `fullscreen`):

    HTTP 202  {"success":true,"renderId":"c617e2cd-..."}

То есть сам рендер-сервер РАБОТАЕТ: принимает задачу, валидирует композицию,

загрузки медиа», а не «выдаёт готовый файл». Полный ответ даст только рендер с
настоящим аватар-видео.

находка о продукте: неполный payload, устаревший конфиг, теперь нерабочий URL.

и не-ссылка теперь отклоняется с предупреждением. Эту проверку я добавил в
раннем цикле совсем по другому поводу — она закрыла дыру, о существовании
которой тогда не знал.

Строки НЕ удалял: там настоящие видео, возможно единственная копия, а удаление
данных без владельца — не уборка.

ПОЧИНЕНО (PR 498): `saveVideoUrlToSupabase` теперь скачивает файл и кладёт в
наш S3, а в `public_url` пишет СВОЮ ссылку. Одно место вместо десяти точек
вызова.

Ключевое в конструкции: **отказ зеркалирования не должен ломать сохранение.**
Весь блок в try, при любой ошибке пишется исходная ссылка провайдера с
предупреждением. Ссылка, которая может протухнуть, ценнее отсутствия записи —
поэтому правка не может сделать хуже, только лучше.

Не сделано и почему: 171 мёртвая строка невосстановима, а 1214 живых не
перезалиты. Перезаливка — это скачать и загрузить больше гигабайта, и ей место
в отдельном осознанном проходе, а не в пути записи.

Урок метода: **проверяя одно, смотри на данные, а не только на ответ.** Я
запрашивал URL для рендера, а таблица заодно показала, что четверть ассетов
мертва — этого вопроса я не задавал.

## В боевом реестре платежей лежат ТЕСТОВЫЕ данные

`payments_v2` — источник истины для баланса: баланс считается суммированием
строк. В нём **883 строки с описанием `TEST_DATA: System/Bonus/Testing` на
197 374 555 звёзд**, все типа `MONEY_INCOME`, датированы 2025-07-28.

Задет не только админ:

    1064902106    15 строк        240 041   ← обычный пользователь
    164609458      3 строки       150 039   ← обычный пользователь
    1483886716     4 строки       111 283   ← обычный пользователь

То есть три настоящих человека видят и могут потратить звёзды, которых не
покупали. Для продукта это не «мусор в таблице», а выданные деньги.

Отдельно: **114 строк ровно по −9 звёзд с типом MONEY_OUTCOME**. Знак в
`updateUserBalance` стирается через `Math.abs`, поэтому откуда взялись
отрицательные — вопрос открытый, но при суммировании реестра отрицательный
расход работает как приход.

УЩЕРБ ПОСЧИТАН — и он в 80 раз больше, чем я сначала сказал.

Сначала я посмотрел на ЧЕТЫРЁХ крупнейших держателей и доложил «2 853 звезды
у одного человека». Это было неверно по охвату: TEST_DATA получили **396
пользователей**. Проверено запросом:

    получили тестовые   396
    ушли бы в минус      87
    сумма минуса    232 552 звезды

То есть 87 живых людей потратили услуг на 232 552 звезды больше, чем когда-либо
оплатили. 287 не потратили ничего.

Ошибка была методической: я взял `ORDER BY … LIMIT 4` и рассуждал о найденном,
не спросив «а сколько их всего». **Прежде чем считать ущерб по образцам — узнай
размер множества.**

Так что «мусор в таблице» — это уже оказанные и неоплаченные услуги, пусть и в
небольшом объёме. Масштаб потенциального ущерба задаёт не потраченное, а
ОСТАТОК: 197 млн звёзд лежат доступными к трате.

НЕ УДАЛЯЛ и не буду: изменение чужих балансов — решение владельца, а не уборка.
Записано, чтобы решение принималось со знанием суммы.

Приём для оценки таких вещей: считай баланс ДВАЖДЫ — как есть и без спорных
строк. Разница и есть ущерб, а не размер самих строк.

ИСТОЧНИК ВБРОСА НЕ НАЙДЕН, и это отдельный вывод: во всём репозитории НЕТ кода,
который вставлял бы `TEST_DATA` в `payments_v2`. Есть только читающие скрипты
(`scripts/financial/ANALYZE_WITH_TEST_FILTERS.js` классифицирует такие строки
как известную категорию) и скрипты ОЧИСТКИ. То есть вброс сделан вручную или
скриптом, которого в репозитории нет; повториться сам по себе он не может.

РЕШЕНИЕ УЖЕ ПРИНИМАЛИ ДО МЕНЯ. В `sql/root/FINAL_CLEANUP_SQL.sql:69` прямым
текстом: «TEST_DATA — ПОМЕТИТЬ, НЕ УДАЛЯТЬ». Скрипт добавляет колонку
`is_test BOOLEAN DEFAULT FALSE` и проставляет её по описанию. Ничего не
удаляется, балансы не меняются.

Но и не чинятся: **`is_test` не читает никто.** Расчёт баланса суммирует все
строки подряд, поэтому одна пометка ничего не изменит — это первая половина
работы из двух. Вторая — научить расчёт баланса исключать помеченные, и вот она
УЖЕ меняет чужие деньги, то есть требует владельца.

В ТОМ ЖЕ ФАЙЛЕ ЕСТЬ ДВА `DELETE`, и один из них опасен СЕГОДНЯ. Скрипт писали
под другое состояние данных (комментарий обещает «Должно быть 11»), поэтому
перед запуском его надо мерить заново:

    DELETE … MONEY_OUTCOME AND currency='STARS' AND ABS(amount)>1000
      → сегодня 0 строк, безвреден

    DELETE FROM payments_v2 WHERE amount = 0
      → 373 строки у 332 человек, в них 430 975 звёзд

Второй выглядит уборкой мусора, но «нулевые» они только в поле `amount`: все
373 имеют тип `MONEY_INCOME` и ненулевые `stars`. Удаление **отняло бы 430 975
звёзд у 332 живых людей**. При этом 333 строки из 373 — тестовые, то есть
скрипт частично почистил бы TEST_DATA, а заодно снёс 40 законных начислений.

Общее правило: **`amount = 0` не значит «пустая запись».** В реестре с двумя
денежными полями проверяй ОБА, прежде чем удалять по одному.

Урок: **прежде чем предлагать решение по данным — поищи, не написано ли оно уже.**
Я готовился объяснять варианты, а готовый разбор с обоснованием лежал в
`sql/root/`.

Как искать такое: сравнивать не код, а ДАННЫЕ на границах —
`count(*) FILTER (WHERE …)` по нулям, отрицательным и выбросам. Одна строка SQL
нашла три аномалии в таблице, которую я тридцать шесть итераций считал
проверенной.

## Тип, которого нет в схеме записи, — это молчаливый отказ

`PaymentType.SERVICE_PAYMENT` был в TS-enum, но его НЕ БЫЛО в
`OperationTypeEnum`, по которому `CreatePaymentV2Schema` валидирует строку.
Три визарда (hedra, heygen, fal) годами звали `updateUserBalance` с этим типом:

    zod бросал -> catch -> return false -> возвращаемое значение никто не смотрел
    -> генерация шла дальше

В `payments_v2` **ровно 0 строк** с `service_type` = hedra_render,
ai_reels_heygen, fal_render. Списания не было ни разу.

Правило: **если функция возвращает boolean «получилось ли», проверяй его.**
Ненужный `await` без проверки результата — это `try/catch {}` в маскировке.

Правило: **значение enum, которое не проходит валидацию записи, не должно
существовать в enum.** Убирать из TS-типа, а не «не использовать» — иначе
кто-нибудь передаст его снова. Убрал SERVICE_PAYMENT из `PaymentType`:
typecheck 0 ошибок, 3 места правки.

## Знак задаёт type, а не минус у числа

Балансовая функция считает `income − outcome`. Значит `MONEY_OUTCOME` с
отрицательными звёздами **НАЧИСЛЯЕТ** деньги. В базе лежат 114 таких строк
(июнь 2025, один аккаунт, −9 звёзд каждая) — они прибавили 1026 звёзд вместо
списания.

Пять вызовов передавали минус. Два были безопасны СЛУЧАЙНО: `updateUserBalance`
подменяет сумму на положительную из `metadata.modePrice / paymentAmount /
stars`. Замысла в этом не было — просто совпало.

Теперь отрицательная сумма отклоняется явно. `Math.abs` здесь был бы ХУЖЕ
отказа: он превратил бы `updateUserBalance(id, -500, MONEY_INCOME)` в честное
начисление 500, и написавший никогда бы не узнал, что списание не сработало.

## Один недостающий префикс = 17 обучений, висящих полтора года

`generateModelTraining.ts` передавала Replicate адрес обратного вызова
`${API_URL}/webhooks/replicate`. Роутер смонтирован на `/api/webhooks`
(`api_server/index.ts:102`), других монтирований `/webhooks` в приложении нет,
а `API_URL` — голый origin. Ответ «обучение готово» не доходил НИКОГДА.

465 дней. У восьми рядом по времени есть оплата — **3410 звёзд за модели,
которых люди не получили**. Плюс 7 строк со статусом `SUCCESS` и пустым
`model_url`.

Соседние места собирали URL правильно (`createModelTrainingLocal.ts:218`,
`existing/generateModelTrainingFunction.ts:232`) — расходился ровно один файл.

**Как это доказать, а не предположить.** GET на оба пути даёт 404 в обоих
случаях (маршрут POST-only) — бесполезно. Разделяет их POST с БЕЗОПАСНЫМ телом:
в обработчике первым делом стоит ветка нетерминального статуса, которая отвечает
200 и выходит, не трогая ни БД, ни Inngest.

    POST /api/webhooks/replicate  {"id":"probe","status":"starting"}  -> 200 acknowledged
    POST /webhooks/replicate      то же                               -> 404 Cannot POST

Правило: **прежде чем стучать в живой обработчик, найди в нём ветку без
побочных эффектов.** Она почти всегда есть — валидация, ранний выход, отказ по
статусу. Это превращает догадку в замер, ничего не ломая.

Правило: **URL обратного вызова — это интеграционный шов, и он не проверяется
ни типами, ни сборкой.** Строка совпадает по форме, тест мокает fetch, деплой
зелёный, а данные копятся в подвешенном состоянии годами. Ищи такие швы
сравнением: если один и тот же адрес собирается в трёх файлах, сравни все три.

## Асимметрия проверок — верный признак дефекта

В `updateUserBalance` отсутствие профиля вело себя по-разному:

- списание (MONEY_OUTCOME) — **проходило**, ошибка только в лог

Правило: **если одна и та же предпосылка проверяется на входе строже, чем на
выходе, — это почти наверняка ошибка, а не замысел.** Смотри на пару
«зачисление / списание», «создание / удаление», «чтение / запись» и сравнивай
строгость.

## Сообщение в логе должно называть последствие, а не операцию

Было: «Пользователь не найден при создании транзакции». Формально верно, по
смыслу — обычная неудачная выборка, глазами дежурного не отличить от шума.

Стало: «ДЕНЬГИ ПОЛУЧЕНЫ, ЗВЁЗДЫ НЕ ЗАЧИСЛЕНЫ — нет профиля в users» плюс
`inv_id`, способ оплаты и сумма.

Правило: **в сообщении об ошибке пиши, что потерял пользователь, а не какой
запрос не удался.** По первому ставят оповещение, по второму — нет. Разница
между «увидели в тот же день» и «нашли через год при разборе данных».

## Событие в пустоту не даёт даже 404

Неверный адрес маршрута отвечает 404 — след есть. **Inngest принимает любое
событие** и просто не находит подписчика: отправка успешна, ошибки нет, работа
не выполняется. Следа нет вообще.

Нашлось этим способом:
- карта MCP-сервера — неверны были ВСЕ ДЕВЯТЬ имён, ни одну функцию из
  перечисленных запустить было нельзя
- `INNGEST_EVENTS` — 17 констант из 24 называли события без подписчика
- `instagram/scraper` против `instagram/scraper-v2`

Правило: **сверяй `createFunction({event})` с `inngest.send({name})` списком
против списка.** Никакой другой способ этот класс не ловит.

Ловушка разбора: имя может быть БЕЗ слэша. `renderRiddle` подписан на
`'render-riddle'`, а константа говорила `'render/riddle'`. Моя первая регулярка
требовала слэш и пропустила именно этот случай — самый важный.

## Константа «для типобезопасности» опаснее голой строки

17 из 24 значений `INNGEST_EVENTS` вели в никуда. Разработчик, поступивший
правильно и взявший константу вместо строки, отправлял бы в пустоту — с большей
уверенностью, чем если бы написал строку руками.

Правило: **карта имён без проверки против источника истины — это ложное
обещание.** Либо тест сверяет её с реальностью, либо карту лучше удалить.

## Тест, повторяющий значение из кода, зелёный всегда

Девять тестов вида
`expect(INNGEST_EVENTS.RENDER_RIDDLE).toBe('render/riddle')` были зелёными всё
время, пока константа указывала в пустоту. Они сверяли файл сам с собой.

Заменил на контракт: **каждое значение обязано совпадать с тем, на что реально
подписана хоть одна функция** — проверяется разбором исходников.

Правило: **если тест можно пройти, скопировав строку из проверяемого файла, он
не тест.** Спроси: «что этот тест поймает?» Если ответ «переименование» — он
ловит только опечатку, а не ошибку.

И обязательно страховка от самого себя: `expect(listeners.size).toBeGreaterThan(20)`.
Без неё сломавшийся разбор сделал бы все проверки зелёными и бессмысленными.

## Порядок «сначала деньги, потом работа» — всегда дефект

`generateInstagramScraping` не отправляла событие (строка закомментирована с
пометкой «ВРЕМЕННО»), но писала в лог «✅ успешно отправлено» и возвращала
`success: true` с текстом «анализ запущен, результаты через несколько минут».
Ложь в трёх местах сразу.

Обе вызывающие сцены списывали деньги ДО вызова и смотрели только на
`result.success`. Измерено: 28 списаний у трёх человек на 94 звезды при нуле
запусков. А ветка неудачи писала «💰 Средства не были списаны» — уже после
списания.

Правило: **списание идёт ПОСЛЕ подтверждённого запуска, а не до.** Это убирает
целый класс случаев без разбора каждого.

Побочный эффект переноса, который легко пропустить: возврат в `catch` был
безусловным. После переноса исключение может прилететь ДО списания, и тогда
безусловный возврат начислит деньги, которых никто не брал. Нужен флаг
`charged`.

## Проверяй, не воскресит ли включение вторую ошибку

Соблазн был «раскомментировать отправку». Но `RAPIDAPI_INSTAGRAM_KEY` в проде
не задана — функция всё равно упала бы, только уже ПОСЛЕ списания. То есть
очевидная правка перенесла бы отказ на шаг позже и сделала хуже.

Правило: **прежде чем включать отключённое, проверь всю цепочку до конца.**
Отключили обычно не просто так.

## Я сравнивал прогоны, разнесённые во времени, и называл это измерением

Несколько итераций подряд я отчитывался «регрессий нет: было 71 файл / 214
тестов красных, стало 71 / 214». Потом перепроверил: **тот же самый коммит**
при повторном прогоне дал **72 / 215**, а часом позже — 72 / 165.

Причина: часть тестов ходит в живую базу и по сети. Их результат зависит от
доступности внешних сервисов, лимитов и — что особенно неприятно — **от моих
собственных записей в базу**. Заведя 12 профилей, я сделал зелёными полсотни
чужих тестов.

То есть точность, которую я заявлял, была выдуманной. Направление ловилось
верно (скачок на +11 — настоящий сигнал, и он поймал две мои регрессии), но
«ровно как до начала» было неправдой.

Правило: **сравнивать прогоны можно только встык.** Baseline и HEAD подряд,
одной командой, без работы между ними:

    git stash -u && git checkout <base> && npx vitest run   # запомнить
    git checkout main && git stash pop && npx vitest run    # сравнить

Правило: **если в наборе есть тесты, ходящие в сеть и в базу, суммарный счётчик
— не метрика, а погода.** Либо сравнивай только детерминированное подмножество,
либо признавай, что мерить можешь лишь крупные скачки.

И отдельно: **не отчитывайся числом, которое не перепроверил в тех же
условиях.** «Регрессий нет» без встречного прогона — это надежда с точностью до
единицы.

## Счётчик может ВЫРАСТИ, когда регрессия есть

Продолжение прошлого урока про прогоны встык — и оно оказалось хуже, чем я
думал. Я специально сломал `sanitizeInput` и прогнал набор:

    зелёных тестов: 2253   (в снимке было 2252)
    стало зелёных больше на: 2
    ❌ РЕГРЕССИИ: 1 — sanitizeInput should remove dangerous characters

То есть суммарный счётчик показал **улучшение** ровно в тот момент, когда я
сломал санацию пользовательского ввода. Прежний способ отчитался бы «регрессий
нет, даже чуть лучше».

Правило: **сравнивай МНОЖЕСТВА, а не числа.** Регрессия — это конкретный тест,
который проходил и перестал. Тест, красный до и после, к правке отношения не
имеет. Тест, ставший зелёным, — улучшение.

Инструмент: `npm run test:gate` (снимок — `npm run test:gate:save`,
`.test-baseline.txt`). Разбор — docs/audit/test-gate.md.

Обязательная деталь: **перепроверка подозреваемых.** Тест мог упасть из-за
недоступности внешнего сервиса. Гоняем только подозрительные файлы ещё раз, и
регрессией считаем лишь то, что упало дважды. Без этого проверка будет врать в
другую сторону и её быстро начнут игнорировать.

## Диагностику пиши под тот механизм, который реально используется

Первая попытка отделить «живые» тесты от чистых: подменить `globalThis.fetch` в
setupFiles и записать, кто ходит в сеть. Перехвачено — ноль.

Причина: `axios` по умолчанию идёт через http-адаптер Node, а не через
`fetch`. Подмена ловила только тех, кто и так использует `fetch`.

Правило: **прежде чем ставить перехват, проверь, через что на самом деле идёт
трафик.** Иначе получишь пустой список и решишь, что проблемы нет.

И более общее: **если классификация не даётся, поменяй вопрос.** Мне не нужно
было знать, кто ходит в сеть — мне нужно было знать, что сломалось. Второй
вопрос решается сравнением множеств и не требует классификации вовсе.

## Починка, делающая путь платным, обязана закрыть возврат тем же движением

В PR #506 я починил списание в heygen-визарде: тип `SERVICE_PAYMENT` не проходил
валидацию записи, деньги молча не списывались. После правки списание заработало.

И тем самым я **открыл дыру, которой до меня не было**: ниже идёт отправка
события, и при её неудаче возврата нет — человек остаётся без видео и без
звёзд. Пока списание не работало, неудачная отправка ничего не стоила.

Соседний `hedra-render-wizard` был устроен правильно всё это время. То есть
образец лежал в файле рядом, и я его не посмотрел.

Правило: **когда чинишь неработавшее списание, пройди весь путь ДО КОНЦА и
проверь, что при каждом отказе деньги возвращаются.** Спроси себя прямо: «что
теперь стоит денег, чего не стоило вчера?»

Правило: **при правке одного из пары братьев-файлов открой второго.** Если он
устроен иначе — либо там дефект, либо у тебя.

## Слабая мутация врёт в обе стороны

Проверяя, что новый тест не декоративный, я убрал слово `Refund:` из текста
описания возврата. Тест остался зелёным — и это выглядело как «тест
бесполезен».

На деле детектор смотрит на `PaymentType.MONEY_INCOME`, а не на текст, и был
прав. Настоящая мутация (удалить вызов возврата целиком) уронила его сразу и с
точным адресом.

Правило: **мутация должна бить в то, что тест проверяет.** Слабая мутация
одинаково легко даёт ложное «тест работает» и ложное «тест бесполезен» — второе
опаснее, потому что подталкивает выбросить рабочую проверку.

## Списание раньше работы: 15 мест, 12 из них в порядке

Обход всех 856 файлов дал 15 мест, где списание идёт до рискованного вызова.
У двенадцати рядом есть возврат — это нормальный рабочий порядок, а не дефект.

Правило: **«списание до работы» само по себе не дефект.** Дефект — списание до
работы БЕЗ возврата. Инструмент, который этого не различает, утонет в ложных
срабатываниях и его перестанут запускать.

Из трёх без возврата один был живой (починен), один — мёртвый код (вызывающих
ноль), один — продуктовое решение о частичном возврате, которое не мне
принимать. Инструмент: `scripts/probe-charge-order.cjs`, разбор —
docs/audit/charge-order.md.

## Третий класс швов: имена таблиц

После маршрутов и событий остался последний. Результат: **27 имён таблиц из 46
в базе отсутствуют**, 78 обращений, 19 из них даже не смотрят на ошибку.

Хуже всего в `inngest_app/functions/render/steps.ts` — конвейер рендера
обращается к ДЕВЯТИ несуществующим таблицам. То есть пайплайн, который я
несколько итераций чинил по частям, пишет промежуточные результаты в никуда.

Инструмент: `scripts/probe-table-seams.cjs`, разбор — docs/audit/table-seams.md.

Полезное различение при разборе: **«мертво» и «опасно» — не одно и то же.**
Маркетплейс обращается к двум несуществующим таблицам, но `getItem` возвращает
пусто ДО списания — отказ закрытый, денег не теряет. А `voice_models` значит,
что результат обучения голоса сохранить некуда. Без этого различения список из
27 позиций читается как 27 пожаров.

## storage.from('images') — это бакет, а не таблица

Первый замер показал «48 обращений к несуществующей таблице images» — самая
крупная находка дня. Неверная: это бакет файлового хранилища, и он существует.
Регулярка `.from('...')` ловила и таблицы, и хранилище.

Цифру пришлось выбросить и пересчитать.

Правило: **инструмент, завышающий находки, обесценивает и настоящие.** Если бы
я отчитался про 48, доверие к остальным 78 было бы заслуженно нулевым. Прежде
чем нести число, проверь самое крупное слагаемое руками — именно оно чаще всего
и оказывается артефактом разбора.

## Тест на швы не должен ходить в базу

Соблазн был: пусть тест сам спрашивает у PostgREST, какие таблицы есть.
Тогда он зависел бы от доступности базы — ровно та болезнь, из-за которой
пришлось заводить `npm run test:gate`.

Сделал иначе: два зафиксированных списка (есть / нет), снятых отдельным
замером, и проверка, что не появилось имени вне обоих. Плюс проверка, что в
списках нет имён, которые больше нигде не используются.

Правило: **проверка на регрессию обязана быть детерминированной.** Если она
ходит в сеть, она будет врать, и её выключат.

## Я повторил ошибку, про которую сам же написал правило

В скилле давно записано: «три отдельные правки попали в файлы, которые никто не
рендерит». Через несколько итераций я сделал то же самое в другой подсистеме —
**трижды подряд**:

- PR #507 — правка в `training/generateModelTraining`. Не зарегистрирована.
  Зарегистрирована `existing/generateModelTrainingFunction`, и адрес вебхука в
  ней был правильным изначально.
- PR #508 — правка в `training/voiceTrainingRVC`. Не зарегистрирована.
- PR #510 — переименовал событие на `instagram/scraper-v2`. Подписчик
  ЗАКОММЕНТИРОВАН в registerFunctions.

Из 35 файлов с `inngest.createFunction` зарегистрированы **22**. Тринадцать
функций компилируются, импортируются, выглядят живыми — и не исполняются.

Правило: **записанное правило не срабатывает само.** Пока нет проверки, оно
живёт только в моей памяти, а память между итерациями не переносится. Каждый
урок обязан заканчиваться либо тестом, либо инструментом — иначе он украшение.

Правило: **перед правкой спрашивай не «компилируется ли», а «исполняется ли».**
Компиляция, импорт и приличный вид не значат ничего. Значит только присутствие в
точке регистрации: `registerFunctions.ts`, `app.use`, список сцен.

Проверка: `src/__tests__/inngest/registration.test.ts`. Инструмент обхода:
`scripts/probe-reachability.cjs`. Разбор — docs/audit/unregistered-functions.md.

## Потерянная работа находится там же, где мёртвый код

Среди тринадцати незарегистрированных нашлась `training/checkStuckTrainings` —
сторож зависших обучений с расписанием раз в 30 минут. Функция для РОВНО ТОЙ
задачи, которую я разбирал в PR #507, лежала в репозитории всё это время.

И `welcomeAvatarGeneration`, которой `createUserScene:188` шлёт событие: событие
уходит, обработчика нет, приветственные аватары не генерируются.

Правило: **список мёртвого кода читай не только как «что удалить», но и как
«что забыли включить».** Второе бывает дороже первого.

## Обход достижимости: сначала проверь самое неправдоподобное имя

Первая версия `probe-reachability.cjs` дала «368 файлов из 683 недостижимы» —
54 %. В списке оказались `scenes/index.ts` и `SceneRegistry.ts`, хотя визарды в
проде работают.

Причина: регулярка требовала `import` и `from` на ОДНОЙ строке, а половина
файлов пишет импорты многострочно. После правки — 187 недостижимых вместо 368.

Правило: **в обходе достижимости переоценка безопаснее недооценки.** Лишний
файл в «живых» — потерянная находка. Лишний файл в «мёртвых» — неверное
обвинение и, возможно, удаление рабочего кода.

Правило: **получив список, найди в нём самое неправдоподобное имя и проверь его
руками.** Одно имя (`scenes/index.ts`) обесценило бы весь отчёт, если бы я его
не проверил.

## Файл-бочка index.ts создаёт видимость использования

Обход достижимости сказал: все 27 несуществующих таблиц упоминаются в
ДОСТИЖИМЫХ файлах, мёртвых среди них ноль. Это было бесполезно как ответ.

Причина: `isLimitAi.ts` достижим, потому что его реэкспортирует
`core/supabase/index.ts`. Но саму функцию не вызывает НИКТО. Бочка тянет в
«живые» всё, что в ней перечислено.

Правило: **считай импортёров модуля БЕЗ файлов-бочек.** `importers.filter(f =>
!f.endsWith('index.ts'))` — одна строка, и картина меняется полностью: семь
модулей из двадцати семи имеют ноль настоящих импортёров.

Правило: **достижимость файла и достижимость символа — разные вопросы.** Первый
дешевле и отвечает «загрузится ли модуль». Второй отвечает «исполнится ли код».
Для вопроса «нужна ли таблица» нужен второй.

Итог разделения: 18 таблиц нужны (конвейер рендера и контент-функции живые),
**7 заводить не нужно — надо удалить код**, обращающийся к ним.

## Профиль отказов — это улика. Строй распределение до объяснения

Две итерации я защищал объяснение «обучения зависают из-за неверного адреса
вебхука». Опровергла его одна колонка — доля зависших по месяцам:

    2025-01..04   0 из 62     0 %
    2025-05       3 из 31    10 %
    2025-07       4 из 25    16 %
    2025-09       3 из 20    15 %

Успешные и зависшие ЧЕРЕДУЮТСЯ. Неверный адрес сломал бы ВСЕ обучения периода,
а не три из тридцати одного. Плюс видна смена режима: до мая 2025 зависших не
было вовсе.

Правило: **«все» и «примерно каждое десятое» — разные классы причин.** Первое
указывает на конфигурацию, второе — на отдельные сбои плюс отсутствие
механизма восстановления. Прежде чем объяснять, посчитай долю по времени: одна
колонка стоит дешевле двух итераций защиты неверной версии.

Настоящий дефект оказался в другом: любое обучение без терминального
уведомления остаётся в `running` навсегда, потому что `checkStuckTrainings` —
функция ровно для этого, с расписанием раз в 30 минут — не зарегистрирована.
А поле `error` у всех пятнадцати равно `null`: причину отказа не записывал
никто.

## Контрольный запрос спасает от вывода из пустоты

Хотел спросить у Replicate, чем кончились зависшие обучения. Ответ — 404 на
всех. Готовый вывод: «Replicate их не знает, значит что-то не так с записями».

Прежде чем его написать, запросил тем же способом три НЕДАВНИХ УСПЕШНЫХ
обучения. Тоже 404. Значит, 404 не говорит ни о чём: токен принадлежит другому
аккаунту.

Правило: **прежде чем делать вывод из отрицательного ответа, проверь тем же
способом заведомо положительный случай.** Если и он даёт отрицательный ответ,
метод измеряет не то, что ты думаешь.

## Секрет утёк из-за раскрытия переменной в шелле

Писал `${T:+есть}${T:-НЕТ}` — думал, что печатаю только факт наличия. Вторая
конструкция при непустой переменной раскрывается в САМО ЗНАЧЕНИЕ. Токен
Replicate попал в вывод.

Правило: **не подставляй переменную с секретом в строку вообще, ни в какой
форме.** Печатай только производные: `${#T}` (длина) или явное слово по
результату `[ -n "$T" ]`. Любая конструкция вида `${T:-...}`, `${T:=...}`,
`${T:?...}` раскрывается в значение.

И: **о таком надо сообщать владельцу сразу** — ключ считается
скомпрометированным и подлежит замене, даже если вывод видел только он.

## Пометить хуже, чем удалить, но лучше, чем молчать

Семь модулей с нулём настоящих импортёров я НЕ удалил. Часть из них —
похоже, незаконченная работа (маркетплейс, ограничитель запросов), а не мусор.
Удаление чужой незавершённой работы — решение владельца, не моё.

Вместо этого — заголовок в каждом файле: не исполняется, таблицы нет, ссылка на
замер, и почему не удалено.

Правило: **когда нельзя ни починить, ни удалить, сделай так, чтобы следующий
читатель не потратил то же время, что потратил ты.** Пометка в файле дешевле
любого документа: её увидят те, кто откроет файл, а документ никто не ищет.

## Считай людей, а не строки

Три итерации подряд я отвечал на вопрос «сколько строк зависло» и каждый раз
называл разное число: 17, потом 15, потом 3410 звёзд ущерба.

Правильный вопрос: **сколько ЛЮДЕЙ заплатили и не получили услугу.**

Ответ оказался другим по порядку величины:

    оплат обучения          117 на 41 036 звёзд
    разных людей            65
    людей без единой модели  1  — @Ludmila, 1210 звёзд

Пятнадцать зависших строк сворачиваются в девять попыток (шесть — повторы), и
семь из девяти закончились успехом после повтора. Система работала для 64
человек из 65.

Правило: **единица измерения должна быть осмысленной для ответа, а не удобной
для запроса.** Строки удобно считать; людей — трудно, потому что нужна
группировка и проверка «а получил ли он в итоге». Именно поэтому первое число
всегда неправильное.

Правило: **прежде чем называть ущерб, проверь, не закончилось ли всё хорошо с
повтора.** Неудачная попытка, за которой последовала удачная, — это переплата,
а не потеря услуги. Разница в тексте отчёта: «пятнадцать пострадавших» против
«один пострадавший и четверо переплативших».

## Отбрасывай свои же красивые версии

Была соблазнительная версия: до мая 2025 зависших нет, потому что в `index.ts`
лежит чистка `model_trainings`, которую потом закомментировали. Красиво и всё
объясняет.

Прочитал код: чистка ограничена одним `telegram_id` и одним
`model_name='fal-test'`. Нулей она дать не могла.

Правило: **версия, объясняющая всё, обязана пройти проверку на своём самом
узком месте.** У этой узкое место — область действия запроса, и одного взгляда
хватило.

Что осталось: единственное видимое различие мая — платформа стала
многоботовой. Это НЕ причина, это совпадение по времени, и написать надо
именно так. Придумать механизм всегда можно; удержаться — сложнее.

## «Затронуто» и «навредит» отличаются на порядок

Пересчитал свои прежние числа с единицей «человек» вместо «строка»:

    было: «DELETE отнимет 430 975 звёзд у 332 живых людей»
    стало: строки есть у 332, но в минус ушли бы ДЕВЯТЬ, и двое из них — ваши
           собственные аккаунты. Посторонних — семеро.

    было: «17 зависших обучений, 3410 звёзд потеряно»
    стало: один человек без модели, 1210 звёзд

Оба раза я называл число «сколько записей затронуто», подразумевая «скольким
людям стало хуже». Это разные величины, и первая систематически больше.

Правило: **посчитай, у скольких состояние реально ухудшится.** Для денег это
«сколько уйдут в минус», а не «у скольких есть такие строки». Разница между
семью и тремястами тридцатью двумя — это разница между разговором и авралом.

## Пересчёт даёт не только меньшее число, но и новое знание

Пересчитывая «171 ассет недоступен» по людям, я заодно посмотрел на даты — и
увидел, что период тянется до июня 2026. То есть это **не история, а текущая
утечка**: ссылки на временное хранилище провайдера продолжают сохраняться и
продолжают протухать.

Исходная формулировка «171 ассет навсегда 404» звучала как законченный ущерб.
На деле это счётчик, который растёт.

Правило: **при пересчёте всегда смотри на распределение по времени.** Оно
отвечает на вопрос, который в исходном числе не задан: закончилось это или
происходит прямо сейчас.

## Не пиши в комментарий факт, которого не измерял

В saveVideoUrlToSupabase моей рукой стояло: «Replicate свой CDN держит долго
(1214 ссылок живы, включая самую старую), поэтому проблема выглядела
несуществующей». Я это НЕ ПРОВЕРЯЛ — написал как довод, почему беда касается

Живой замер HEAD-запросами по выборке из каждого месяца:

Правило: **комментарий с числом — это утверждение о мире, и оно требует того же
доказательства, что и отчёт.** Если число не измерено, пиши «не проверено» прямо
в комментарии. Ложное соседство с проверенными фактами делает догадку
убедительной.

## Пока ждёшь доступов, поищи путь, который уже работает

Зеркалирование файлов было написано под S3 и всегда падало в откат: сначала
неверный регион, потом Access Denied. Я трижды отчитывался «ждём учётные данные

Сквозной прогон: скачал 3,3 МБ у провайдера, положил, прочитал обратно —
content-length совпал байт в байт.

Правило: **«нужны доступы» — это гипотеза, а не приговор.** Перебери, что уже
работает под текущими ключами. Ожидание чужого действия стоит дороже, чем час
проверки альтернатив.

## Одна дверь, иначе правка не закрывает дорогу

Зеркалирование добавили в saveVideoUrlToSupabase, а
videoGenerator/helpers/supabaseHelper.ts продолжал вставлять в `assets`
НАПРЯМУЮ. Правка в одном месте эту дорогу не закрывала.

Правило: **починив запись в таблицу, найди ВСЕ места, которые в неё пишут.**
`grep "from('таблица')" | grep insert` — одна команда. И закрепи тестом
«одна дверь», иначе вторая появится снова.

Починил `assets` (1496 ссылок) и отчитался «утечка остановлена». Потом прошёл

## Общий модуль вместо второй копии — и это не про красоту

Первую версию зеркалирования я написал ВНУТРИ saveVideoUrlToSupabase. Вторая
дверь в ту же таблицу осталась открытой, и правка не закрыла дорогу.

Теперь `core/supabase/mirrorToStorage.ts`, и его зовут все: и assets, и оба
пути сохранения промптов.

Правило: **если логику придётся звать из второго места — выноси СРАЗУ.** Копия
разъезжается молча, а «молча» здесь означает годы потерянных файлов.

## У функции-обёртки главное свойство — не потерять данные

Контракт `mirrorToOwnStorage`: при ЛЮБОЙ неудаче вернуть исходную ссылку.
Не бросить, не отдать пустоту. Ссылка, которая протухнет, лучше отсутствующей.

Проверено мутацией: замена отката на пустую строку роняет три проверки из
шести.

Правило: **для кода «попробуй улучшить» пиши тест не на успех, а на все виды
отказа.** Успешный путь очевиден и его напишут; отказ — нет, а именно он
определяет, теряются ли данные.

## Мёртвая ссылка на файл ещё не значит потерянные данные

Поднял тревогу: 101 ссылка в `model_trainings.weights` ведёт на мёртвый CDN —
не потеряны ли модели, за которые платили по 220–440 звёзд?

Не потеряны. Генерация использует не `weights`, а `model_url` — ссылку вида
`owner/slug:hash` в РЕЕСТРЕ Replicate. Это постоянный адрес, а не файл на CDN.
Выборка по каждому месяцу 2025-01…2025-10: модель 200, точная версия 200.

Правило: **прежде чем объявлять данные потерянными, посмотри, чем на самом деле
пользуется код.** Мёртвая колонка может оказаться побочным артефактом, а
рабочая ссылка лежать в соседней.

Заодно разъяснилась прошлая загадка: токен принадлежит аккаунту
`jalisawallet-coder`, а обучения запускались под `ghashtag`. Модели ПУБЛИЧНЫ и
читаются из-под любого аккаунта — поэтому проверка моделей удалась, а проверка
обучений давала 404.

## Формат ответа поставщика меняется, а формула остаётся

Ссылка на модель собиралась так:

    `${username}/${trainingRecord.model_name}:${output.version}`

Две ошибки наложились: `model_name` — это имя, которое ввёл ЧЕЛОВЕК («Anneya»,
«Мой аватар»), а `output.version` от Replicate — уже ПОЛНАЯ ссылка
`owner/slug:hash`. В базу писалось
`owner/Anneya:owner/anneya-1773937126432:hash` — путь, которого нет.

Старые записи исправны: раньше приходил голый хеш. **Формат ответа изменился, а
код остался.**

Правило: **если строишь идентификатор из чужого ответа, проверь, не готов ли он
уже.** Признак дешёвый: содержит ли значение разделители, которые ты собираешься
добавить. `if (v.includes('/') && v.includes(':')) return v` — одна строка,
которая ловит целый класс.

Правило: **имя, которое ввёл человек, и имя ресурса у поставщика — разные
вещи.** «Мой аватар» Replicate не примет вовсе: там только строчные буквы,
цифры и дефис.

## Тест-копия правила — снова я

Вынес правило в `core/replicate/buildModelUrl.ts`, тест зовёт настоящую функцию.

Правило: **«неудобно вызвать» — это причина вынести, а не причина копировать.**

## Импорт, вставленный скриптом, попал внутрь комментария

Автоматическая вставка `import` «в начало файла» положила строку после `/**` —
внутрь шапочного JSDoc. Код скомпилировался бы, если бы не использовал импорт;

Правило у меня записано давно — вставлять ПОСЛЕ закрытия блока импортов, — и я
снова его нарушил. Надёжный способ: найти последнюю строку, начинающуюся с
`import ` или `} from `, и вставлять после неё.

## Секрет попадает в базу не через поле «пароль», а через АДРЕС

В `users.photo_url` лежат **264 строки** с адресами вида
`https://api.telegram.org/file/bot<ТОКЕН>/<путь>`. Разных токенов 14, и
**шесть на момент проверки были действующими** — проверено вызовом getMe.
Токен даёт полное управление ботом.

Никто не писал `INSERT INTO users (token)`. Токен приехал внутри ссылки на
аватар — в поле, которое выглядит совершенно безобидно.

Правило: **ищи секреты не по именам колонок, а по содержимому.** Любое поле,
куда попадает построенный нами адрес к чужому API, — кандидат. Регулярка
`bot\d+:[A-Za-z0-9_-]+` по всем строковым колонкам находит это за минуту.

Правило: **функция, строящая адрес с секретом, не должна его ВОЗВРАЩАТЬ.**
Скачать по нему — законно; отдать наружу — нет. После правки
`getUserPhotoUrl` перекладывает файл к себе и отдаёт свой адрес, а при неудаче
возвращает `null` — но не адрес с токеном.

## Порядок важнее скорости: очистка без ротации даёт ложное спокойствие

Соблазн был сразу почистить 264 строки. Не стал, и не из осторожности ради
осторожности: **пока токены не перевыпущены, очистка базы не защищает** —
утечка уже произошла. А закрытый тикет создаёт ощущение решённой проблемы.

Правило: **сначала то, что меняет реальность (ротация), потом уборка следов.**
Если можешь только второе — скажи прямо, что это не лекарство.

## Инструмент, не ловящий тот дефект, ради которого сделан

Написал искалку «идентификатор, собранный из чужого ответа». Первая версия
искала слово из ответа ВНУТРИ шаблона — и не поймала бы исходный случай:

    const versionHash = eventData.output.version      // строкой выше
    modelUrl = `${username}/${name}:${versionHash}`   // здесь уже своя

Пришлось прослеживать на шаг назад: имена из шаблона искать среди присваиваний
в предыдущих 20 строках.

Правило: **проверь искалку на том самом случае, ради которого её пишешь.**
Восстанови исходный код во временном файле и запусти. У меня она сначала давала
ноль находок — и это выглядело как «класс чист».

Результат после правки: класс действительно чист, других таких склеек нет. Но
теперь это измерение, а не совпадение.

## Граница слова `\b` не срабатывает внутри слова — и это дало «ноль находок»

Искалка секретов с шаблоном `\b\d{8,10}:[A-Za-z0-9_-]{30,}` нашла НОЛЬ токенов
Telegram. При том что итерацией раньше я нашёл их вручную.

Причина: токен лежит внутри `…/file/bot7137641587:AAH…`. Между `t` и `7`
границы слова НЕТ — оба символа словесные, и `\b` не срабатывает.

Спасло только то, что я знал правильный ответ заранее. Иначе «секретов не
найдено» ушло бы в отчёт как хорошая новость.

Правило: **у любой искалки должна быть самопроверка на заведомо-положительных
образцах.** Три строки кода: набор примеров, на которых шаблоны ОБЯЗАНЫ
срабатывать, и остановка, если хоть один не сработал. Пустой результат без
самопроверки не значит ничего.

Правило: **`\b` перед цифрой ломается, если слева буква.** Для секретов внутри
адресов границы слова лучше не использовать вовсе — структура (`:`, префикс)
надёжнее.

## Исправленный шаблон завысил втрое — проверяй крупнейшее слагаемое

После починки шаблон дал 787 вхождений в шести местах. Ручная проверка: 518 из
них — НЕ токены, а ссылки на модели вида `<telegram_id>:<64-значный хеш>`
(`ghashtag/user7631002280:a3dba63e…`). Формально подходят, по сути безобидны.

Настоящие токены отличаются КОНТЕКСТОМ: стоят после `bot` в адресе
`api.telegram.org/file/`. С уточнением — 269 вхождений в двух местах.

Правило: **для секрета проверяй не только форму, но и окружение.** Форма
`цифры:строка` встречается всюду; секретом её делает то, где она стоит.

## Поиск по содержимому находит то, чего не находит поиск по именам

Первый заход искал в `users.photo_url`, потому что я уже знал про это поле.
Поиск по СОДЕРЖИМОМУ всех строковых значений — включая вложенные объекты в
`metadata` — нашёл второе место: `payments_v2.metadata.image_url`. И довёл счёт
действующих токенов с шести до восьми.

Правило: **обходи вложенные объекты.** Секрет в `metadata.image_url` не виден
ни одному запросу по колонкам. Рекурсивный обход значений — двадцать строк, и
он находит то, о чём не догадаешься.

## Секреты живут в трёх местах: база, файлы, история

База проверена — нашлись токены ботов. Проверил остальные два:

**Файлы репозитория.** Служебный ключ Supabase (`service_role`, полный доступ в
обход правил, срок до 2035) лежит в ОДИННАДЦАТИ файлах под `scripts/`.
Проверен запросом — **работает**.

**История коммитов.** 800 коммитов: два ключа ElevenLabs, и **оба работают**.
Остальное (Replicate, OpenAI, Telegram, GitHub, Fly) — мёртвое.

Правило: **секрет, удалённый из файла, остаётся в истории навсегда.** Проверять
надо все три места, и история — единственное, где нельзя «просто исправить»:
нужна ротация.

Побочная находка, которая стоит отдельно: девятнадцать итераций в отчётах
стояло «нужен ключ ElevenLabs, синтез заблокирован» — а два рабочих ключа
лежали в истории коммитов. **Учётная запись существует.** Задача была не
«завести аккаунт», а «перевыпустить ключ».

Правило: **прежде чем записывать задачу в «ждём от владельца», поищи, нет ли
ответа в репозитории.** История коммитов — тоже источник фактов о проекте.

## Приватный репозиторий не отменяет утечку

Репозиторий приватный — и это снижает остроту, но не убирает: доступ есть у
всех участников, ключ уезжает в каждую копию, в резервные копии и в журналы CI.

Правило: **«приватный» — это про порог входа, а не про отсутствие проблемы.**
Работающий ключ с полным доступом к базе в отслеживаемом файле остаётся
работающим ключом.

## Список известного долга вместо игнорирования

Тест на секреты в файлах падал бы всегда: ключи там уже есть. Вместо
отключения — список `KNOWN_DEBT` с причиной у каждой записи и ТРЕТЬЯ проверка:
в списке нет файлов, которые уже вычищены.

Так тест не даёт добавить НОВЫЕ места и заставляет убрать запись, когда старое
почистят.

Правило: **когда проверка не может быть зелёной сразу, фиксируй долг явно, а не
глуши проверку.** Заглушенная проверка молчит и о новом; список долга — нет.

## «Ждём от владельца» — это диагноз, и он тоже требует проверки

Перепроверил все задачи, записанные как заблокированные. **Две из семи были
мнимыми:**

- «нет ключа ElevenLabs» — два рабочих ключа лежали в истории коммитов,
  аккаунт активен; задача была «перевыпустить», а не «завести»;
- «ждём доступы к S3 для зеркалирования» — не нужны вовсе, Supabase Storage
  работает текущими ключами.

Обе — там, где я заключил «отсутствует» по переменным окружения и не проверил
другие места.

Правило: **признак мнимой блокировки — формулировка «нет X».** Прежде чем
записывать, спроси: «нет НИГДЕ или нет там, где я посмотрел?» Места, которые
стоит перебрать: переменные окружения, хранилище секретов, история коммитов,
альтернативный сервис, живая диагностика приложения.

## Проверяя одно, смотри, ЧЕМ проверяешь

Доступность поставщиков я узнал у эндпоинта диагностики — и заодно заметил, что
он отвечает **без авторизации**. Проверил соседние: открытыми оказались шесть
адресов, включая `/api/billing` с финансами по всем ботам и
`/api/models/:telegramId` с чужими обученными моделями.

Номер в Telegram не секрет и перебирается, так что «знать адрес» защитой не
было.

Правило: **инструмент, которым ты пользуешься, — тоже часть системы.** Если для
диагностики хватает обычного запроса без ключа, значит, и постороннему хватает.

## Отказ закрытый у защиты, а не открытый

В охраннике маршрутов: если служебный ключ НЕ НАСТРОЕН — маршрут не
открывается, а отвечает 503.

Соблазн был сделать наоборот («ключа нет — пропускаем, чтобы не сломать»).
Тогда забытая переменная окружения тихо вернула бы всё как было, и починка
выглядела бы сделанной.

Правило: **у защиты отказ должен закрывать, а не открывать.** Иначе она
работает ровно до первой ошибки в настройке — то есть тогда, когда нужна
меньше всего.

## Список «должно остаться открытым» — с причиной у каждого

В тесте два списка: что обязано быть закрыто и что обязано остаться открытым
(проверки живости, обратные вызовы платёжной системы и поставщиков). У второго
— причина у каждой записи, и отдельная проверка, что в нём нет уже закрытых.

Так новый открытый роутер становится осознанным решением, а не забывчивостью.

## Открытый эндпоинт, берущий telegram_id из тела, — это чужой кошелёк

`POST /api/generate/neuro-photo-sync` и `/api/generate/voice-avatar` не
проверяли ничего и брали получателя ИЗ ТЕЛА запроса. Проверено живым запросом к
проду: доходит до обработчика.

Что это давало постороннему:
- запустить генерацию, списав звёзды с ЛЮБОГО номера на выбор;
- потратить наш бюджет у поставщика — План Б зовёт `replicate.run()`.

Правило: **если идентификатор пользователя приходит из тела запроса, а проверки
нет — это не «внутренний эндпоинт», это открытый кошелёк.** Признак ищется
одним grep: `telegram_id` в `req.body` рядом с маршрутом без охранника.

## Своя метка вместо подписи, которой нет

Обработчик обратного вызова видео берёт получателя из адреса, ссылку из тела и
шлёт человеку — не сверяясь ни с какой задачей. Подписи от поставщика нет и
может не быть.

Но **адрес обратного вызова составляем мы сами** — значит, можем положить в
него метку и проверить на входе. Метка = HMAC(наш ключ, номер получателя),
16 знаков.

Ключевое свойство: **метка привязана к получателю.** Подсмотрев чужую, нельзя
отправить что-то другому человеку. Именно это и проверяет тест в первую
очередь — не «метка совпадает сама с собой», а «метка от другого номера не
проходит».

Правило: **когда чужой подписи нет, подпиши свой адрес.** Это работает везде,
где обратный вызов идёт на URL, который мы передали.

## Мой же список исключений заставил меня вернуться

В прошлой итерации я закрыл диагностику и биллинг, а генерацию оставил открытой,
записав в список причину: «вызывается изнутри, ключ добавить отдельной задачей».

Через итерацию я эту запись перечитал, проверил — и оказалось, что там чужой
кошелёк.

Правило: **список исключений с причинами — это не свалка, а очередь.** Причина,
записанная честно («не сделал, откладываю»), читается как задача. Причина вида
«так надо» — не читается никак.

## Отпечаток надо проверять на достижимость, а не придумывать

Искал следы использования эндпоинтов, которые были открыты. Дважды подряд выбрал
признак, который выглядел естественным — и оба раза он не мог попасть в данные
в принципе.

**Попытка 1.** Маршруты подставляют `from: { username: 'api_user' }`. Поискал
`api_user` по всем таблицам: ноль из 30 063 промптов, 17 136 платежей, 1509
ассетов. Убедительно — пока не проверил, попадает ли `username` в базу ВООБЩЕ.
Не попадает: он идёт только в сообщение аналитического канала. Ноль был
гарантирован.

**Попытка 2.** Мок-контекст не содержит `session.mode`, значит
`processBalanceOperation` запишет `service_type = 'unknown_mode'`. Ноль таких.
Тоже мимо: путь нейрофото идёт через `directPaymentProcessor`, где
`service_type` задан ЖЁСТКО.

Правило: **прежде чем делать вывод из отсутствия признака, докажи, что признак
появился бы, если бы событие произошло.** Достаточно прочитать путь записи до
конца. Я не сделал этого ни в первый, ни во второй раз.

Правило: **«следов не найдено» без такого доказательства — это не результат, а
формулировка.** Разница между «не было» и «не обнаружено» — вся ценность
отчёта.

## Если отличить нельзя — сначала сделай отличимым

Итог разбора: запись, сделанная через API, НЕОТЛИЧИМА от сделанной в боте — ни
по типу услуги, ни по способу оплаты, ни по форме идентификатора.

Значит, вопрос «пользовались ли» был безответным по устройству данных, а не по
недостатку усердия.

Поэтому вместо продолжения поисков — пометка происхождения: если бот не назван,
пишем `api-route`. Теперь такой вопрос решается одним запросом.

Правило: **когда расследование упирается в неразличимость, чини наблюдаемость,
а не копай глубже.** Второе бесконечно, первое — на десять строк.

## Класс «обратный вызов шлёт контент по данным из запроса»

Третий представитель подряд, и все три устроены одинаково: обработчик берёт
ПОЛУЧАТЕЛЯ из запроса, ССЫЛКУ НА МЕДИА оттуда же и отправляет человеку от имени
бота — не сверяясь ни с какой задачей.

    /api/video-callback/:telegramId    закрыт меткой
    /api/telegram/ai-reels-callback    закрыт меткой
    /api/webhooks/replicate            закрыт проверкой существования обучения

Опасность не в чужом видео, а в том, что сообщение приходит **от бота, которому
человек доверяет**.

Правило: **ищи этот класс по паре признаков — «получатель из запроса» и
«отправка человеку» в одном обработчике.** Grep по `sendVideo|sendPhoto` рядом
с `req.body` или `req.params` находит все.

## «Пусть разберётся следующий слой» — это не проверка

В вебхуке обучения стояло:

    if (!trainingRecord) {
      logger.warn('не найдено (will be handled in Inngest)')
      // Все равно отправляем событие
    }

То есть проверка была, а следствия у неё не было. Живая проверка прода: POST с
выдуманным идентификатором возвращает 200 «Webhook received and forwarded».

Правило: **проверка, после которой выполняется то же самое, — это лог, а не
проверка.** Отличать легко: посмотри, есть ли `return` в ветке отказа.

## Тест на порядок, а не только на наличие

В проверке обратных вызовов есть третий тест: **метка проверяется ДО отправки**.
Наличие `verifyCallbackToken` в файле ничего не значит, если вызов стоит после
`sendVideo`.

Правило: **для защиты проверяй не присутствие, а позицию.** Сравнение индексов
двух подстрок в файле — три строки кода, и они ловят целый способ ошибиться.

## Молчащая функция обезоруживает правильный вызывающий код

`setPayments` создаёт строку PENDING ПЕРЕД тем, как человека отправят платить.
При ошибке вставки она писала в журнал и возвращала `undefined` — выглядела
успешной. Внешний `catch` тоже глотал всё и не пробрасывал.

Самое горькое: вызывающий делал ВСЁ ПРАВИЛЬНО. `getRuBillWizard` оборачивает
вызов в try/catch и говорит человеку «не удалось создать платёж, попробуйте
снова». **Эта защита не срабатывала никогда**, потому что бросать было нечему.

Цена: записи нет → человек уходит платить → деньги списываются → обратный вызов
Robokassa не находит платёж по `inv_id` → «Payment not found» → звёзды не
начислены, следа в базе нет.

Правило: **прежде чем добавлять обработку ошибки у вызывающего, проверь, что
вызываемое вообще умеет её сообщить.** try/catch вокруг функции, которая молчит,
— это украшение.

Правило: **у функции, создающей предусловие для денег, молчаливого пути быть не
должно.** Либо бросает, либо возвращает явный результат, который нельзя
проигнорировать случайно.

## Класс «проверка без следствия» — 242 места, 64 в денежных

Инструмент `scripts/probe-checks-without-effect.cjs` ищет блоки `if`, где есть
запись об ошибке и НЕТ ни `return`, ни `throw`, ни `res.status`, ни `continue`.

Нашлось 242, из них 64 в местах, связанных с деньгами и защитой. Не все дефекты
— иногда «записать и продолжить» осознанно. Но именно так выглядели оба
серьёзных случая последних двух итераций.

Самопроверка искалки — на реальном образце из вебхука обучения, который я чинил
накануне. Без неё пустой результат ничего не значил бы.

Правило: **ищи не «нет проверки», а «проверка без последствий».** Первое видно
глазами при чтении, второе — нет: код выглядит защищённым.

## Итерация с отрицательным результатом — тоже результат

Искал «функции, возвращающие успех при неудаче». Инструмент дал 20 кандидатов в
денежных путях. Прочитал все — **настоящих нет ни одного**:

- `handlePaymentButtons` и `handleCallbackQuery` возвращают `true` из `catch`,
  но их `true` означает «обработано, не передавай дальше». Пропустить нажатие
  дальше было бы ХУЖЕ: текст кнопки уехал бы в сцену как сообщение.
- `checkSubscription` в `catch` делает `throw error` — правильно.
- `kickUnpaidUser` возвращает `true` после неудачи УВЕДОМЛЕНИЯ: кик состоялся,
  не сообщили только человеку.

Правило: **прочитай, что означает возвращаемое значение, прежде чем считать его
ложным успехом.** `true` в цепочке обработчиков и `true` в «операция удалась» —
разные вещи, а выглядят одинаково.

Правило: **не раздувай отчёт, когда находок нет.** Соблазн назвать 20
кандидатов находками велик; честнее сказать «класс чист» и показать, чем
проверял.

## Смежный поиск дал то, чего не дал основной

Основной класс оказался чист, а смежный — «возврат выдуманного значения» —
нашёл `return "https://example.com/generated_image.png"` в
`generateImageFromPrompt`. Адрес, которого не существует; вызывающий принимал
его за картинку.

Функция недостижима от точек входа, то есть дыра латентная. Всё равно заменил
на честный отказ: заготовка, возвращающая выдумку, однажды окажется
подключённой.

Правило: **если основной поиск пуст, сдвинь формулировку на шаг вбок.** «Успех
при неудаче» и «выдуманное значение вместо результата» — один и тот же вред,
но ловятся разными шаблонами.

## Отметка «сделано» раньше самого дела делает отказ неисправимым

В обработчике оплаты Robokassa порядок был такой:

    1. пометить платёж COMPLETED
    2. начислить звёзды
    3. если не начислилось — записать в журнал и ПРОДОЛЖИТЬ
    4. сказать человеку «оплата прошла успешно»

Деньги списаны, звёзды не начислены, человеку сказано, что всё хорошо.

Но хуже другое: **починить это не мог даже повтор.** Robokassa повторяет вызов
при неуспешном ответе, а повтор упирался в проверку в начале — «платёж уже
обработан, 200 OK» — и звёзды не начислялись НИКОГДА.

Отказ не выдуманный: `updateUserBalance` отклоняет MONEY_INCOME, если у
человека нет строки в `users`.

Правило: **отметку «готово» ставь ПОСЛЕ работы, а не до.** Тогда неудача
оставляет запись незавершённой, и повтор — свой или чужой — доводит дело до
конца. Порядок «пометил → сделал» превращает временный сбой в постоянную
потерю.

Правило: **проверка идемпотентности («уже обработано») должна стоять после
отметки, которая ставится по факту успеха.** Иначе она превращается из защиты
от двойного начисления в защиту от исправления.

## Порядок операций проверяется статически

Тест на это не поднимает сервер: сравнивает индексы подстрок в файле.

    at('updateUserBalance(') < at('status: COMPLETED') < at('sendSuccessNotification(')

Три сравнения ловят целый класс ошибок, который иначе виден только в проде и
только при сбое. Плюс проверка «подпись проверяется раньше любых изменений».

Правило: **если свойство — это ПОРЯДОК, тест может быть статическим.** Не надо
имитировать платёжную систему, чтобы убедиться, что начисление идёт раньше
отметки.

## Прежде чем менять порядок — выясни, ЧТО именно делает работу

Вчера я переставил в обработчике оплаты «сначала начислить, потом пометить» —
рассуждение общее и верное. Сегодня проверил данные и выяснил, что здесь оно
неприменимо: **отметка COMPLETED и есть начисление**.

Баланс считается как сумма `stars` по строкам со статусом COMPLETED. На один
номер счёта ровно одна строка: 16 681 уникальный inv_id на 17 136 строк, дублей
ноль — вставка второй блокируется уникальностью, и код прямо обрабатывает это
как 23505.

Значит `updateUserBalance` в этом месте — ВТОРИЧНЫЙ шаг. Мой перенос приводил к
тому, что при его отказе строка оставалась PENDING и человек НЕ получал звёзды —
хотя до правки получал. И отказ вероятнее всего у тех, **у кого нет строки в
users**, то есть у тех, кого я и собирался защитить.

Правило: **общее правило («сначала дело, потом отметка») не освобождает от
вопроса «а что здесь дело?»** Прежде чем переставлять шаги, найди тот, который
меняет наблюдаемое состояние. Здесь достаточно было одного запроса: сложить
баланс по строкам и сверить с функцией базы.

Правило: **правка в денежном пути требует проверки ПОСЛЕ, а не только до.**
Я проверил, что новый порядок соответствует замыслу, но не проверил, что
замысел соответствует данным.

## Переименованный тест выглядит как регрессия

Проверка `npm run test:gate` сравнивает МНОЖЕСТВА имён пройденных тестов.
Переименовав два теста, я получил «❌ РЕГРЕССИИ: 2» — хотя тесты не сломались,
а были заменены на более точные.

Правило: **при срабатывании проверки на переименованных тестах сверь, есть ли
замена по смыслу.** Если есть — обнови снимок и скажи об этом прямо; если нет —
это настоящая регрессия. Молча обновлять снимок нельзя: тогда проверка
перестанет что-либо значить.

## Выясни путь денег по данным один раз — и закрепи тестом

Я трижды подряд ошибся в предположениях о том, как устроено начисление, и один
раз откатывал собственную правку. Каждый раз рассуждал по коду.

Один замер снял весь класс: баланс = сумма `stars` по строкам `COMPLETED`,
`MONEY_OUTCOME` вычитается, **всё остальное прибавляется** (совпало с функцией
базы 6 из 6). Отсюда сразу: перевод строки в `COMPLETED` И ЕСТЬ начисление;
любой новый тип операции молча становится начисляющим.

Правило: **прежде чем менять денежный путь, выясни его по данным и запиши.**
Разбор — `docs/audit/money-map.md`, инварианты —
`src/__tests__/money/money-invariants.test.ts`: список типов операций и
поимённый перечень мест, где код переводит платёж в `COMPLETED`. Каждое такое
место выдаёт деньги; новое не должно появляться незаметно.

## «Нет новых плохих записей» ≠ «правка работает»

Проверял по данным, работают ли выкаченные правки: новых чужих ссылок нет,
новых токенов в профилях нет, новых кривых ссылок на модели нет. Выглядит как
подтверждение.

Пока не посчитал знаменатель: **новых записей нет ВООБЩЕ**. Ни платежей, ни
промптов, ни ассетов, ни обучений. Последний промпт — двумя неделями раньше,
последний ассет — двумя месяцами.

Правило: **прежде чем радоваться нулю нарушений, посчитай, сколько было
событий.** Ноль из нуля не значит ничего. И это стоит сказать вслух: «правку в
проде подтвердить не могу — не на чем» честнее, чем «нарушений не найдено».

## «Safe» — спроси, для кого

В защите от повторной выдачи промо стояло:

```ts
} catch { return false }  // Assume not received on error to be safe
```

Безопасно для человека. Для кошелька — наоборот: пока база отвечает ошибкой,
промо выдаётся снова и снова, по 1303 звезды (2999 ₽) за раз.

Правило: **у денежной защиты цена ошибки несимметрична — сравни две стороны
явно.** Не выдать: человек нажмёт ссылку ещё раз. Выдать лишний раз: не
вернуть. Значит, при неизвестном состоянии — не выдавать. И проверяй не
возвращаемое значение, а факт: начисления не произошло.

## Защита может быть настоящей — проверь запросом, а не чтением

Прежде чем чинить, выполнил ЗАПРОС ЗАЩИТЫ против прода — ровно теми же
фильтрами, включая `metadata=cs.{…}`. Выданное промо нашлось: защита не
декоративная, дефект только в ветке отказа.

Правило: **у проверки, которая ищет в базе, два разных вопроса — «находит ли
она то, что записано» и «что она делает, когда не смогла посмотреть».** Первый
решается одним запросом к проду, второй — тестом. Смешивать их нельзя: я
чуть не переписал работающую защиту целиком.

## «Сломалось» или «перестали приходить» — различают только когорты

Помесячные суммы говорили: людей, которые тратят, было 81 в декабре и 2 в
августе. Из этого одинаково следуют два противоположных вывода — продукт
отпугивает или притока нет.

Различает только когортный счёт: из заведённых В ЭТОМ месяце — сколько
КОГДА-ЛИБО что-то сделали. Ответ: 13% в сентябре 2025, 32% в декабре, 39% в
марте, 29% в августе. Доля не падает — значит, воронка цела, а иссяк приток.

Правило: **прежде чем чинить продукт, посчитай когорты.** Помесячная сумма
смешивает приток и удержание, и по ней чинят не то. И называй размер выборки:
29% от 24 человек — это семь человек.

## Обещание в интерфейсе — обязательство, проверяемое по данным

Сцена приглашения обещала три вещи: бонусные звёзды, эксклюзивные функции,
повышение уровня. Ни одна не выполнялась: наград за приглашение ноль на 17 136
платежей, `level` равен нулю у 2351 профиля из 2354, функций в коде нет.

Правило: **любую фразу «вы получите» проверяй запросом.** Это дешевле любого
теста и находит то, чего не находит код: обещание живёт в строке текста, а
исполнение — в другом модуле, и между ними нет связи, которую поймает
компилятор.

Следствие для правок: пока награда не включена, её не должно быть и в тексте.
Условие вокруг обещания — часть механизма, а не оформление.

## Проверка на «одинаковый номер» проходит и со случайностью

Номер счёта должен быть детерминированным — иначе повтор оплатят второй раз.
Проверка «два вызова дают одно и то же» это НЕ ловит: оба вызова случаются в
одну миллисекунду, и `Date.now()` в них совпадает.

Правило: **свойство «здесь нет времени и случайности» проверяй по исходнику**,
а не по совпадению результатов. Мутация подтвердила: рантайм-проверка осталась
зелёной, упала статическая.

## Сравнивай с кодом, а не с рассказом о нём

Мой тест требовал, чтобы в сцене не было слов «повышение уровня». Тест упал —
на моём же комментарии, который объяснял, почему этих слов быть не должно.

Правило: **перед сравнением вырезай комментарии.** Человеку показывают код, а
не рассуждения о нём; иначе объяснение правки ломает саму правку.

## Обязательный параметр вместо умолчания — когда различие важно

Дважды за итерацию понадобилось, чтобы КАЖДОЕ место назвало причину: возврат
денег (наша поломка или отмена человеком) и запись о генерации (получилось или
нет). Соблазн — добавить необязательный параметр с разумным умолчанием.

Умолчание тут вредно: оно рано или поздно проставит «успех» или «отмена» там,
где этого не было, — и колонка снова станет бессмысленной, но уже незаметно.

Правило: **если различие нужно для счёта, делай параметр обязательным.**
Заодно компилятор перечислит все места сам — и это единственный надёжный
список. У возвратов их оказалось 21 вместо 7, найденных поиском по тексту; у
записей о генерации 17 вместо 12. Многострочные вызовы grep не видит.

## Свой же детектор соврал — проверяй его находки поштучно

Скрипт пометил три вызова как «внутри catch». Прочитал все три: `catch` там
относится к удалению служебного сообщения десятью строками выше, а сам вызов —
в обычной ветке. Если бы поверил, пометил бы удачные генерации как неудачные —
то есть испортил бы ровно тот сигнал, ради которого всё делалось.

Правило: **находка инструмента — это кандидат, а не факт.** Особенно когда по
ней собираешься записать что-то в базу.

## Отрицательный контроль отличает сигнал от фона

112 возвратов из 114 стояли рядом с записью, у которой пустой статус. Похоже
на доказательство «возврат = отказ генерации».

Но в сентябре 2025 таких пустых 279 при НУЛЕ возвратов. Значит, пустой статус —
это фон, а не признак отказа, и связь ничего не доказывает.

Правило: **прежде чем объявить совпадение признаком, посмотри, как часто
признак встречается БЕЗ события.** Без этого любая частая метка выглядит
причиной.

## Агрегат показывает связь, поштучный разбор — направление

По сводке выходило: «у 120 из 154 однодневок есть возврат» — и я прочитал это
как «их прогнали отказы генерации». Достаточно было выписать реестр ОДНОГО
человека построчно, чтобы увидеть обратный порядок: возврат идёт ПЕРВЫМ, до
всякого списания, и на него же покупается единственная генерация.

Правило: **прежде чем объяснять сводку, выпиши три-четыре случая целиком.**
Агрегат не показывает порядок событий, а именно порядок чаще всего и есть
объяснение. Стоит это пять минут и спасает от целой итерации, построенной на
перевёрнутой причине.

## Защита, сверяющаяся с текстом для человека, — не защита

Единственное место, где заметили, что возврат нельзя делать при «недостаточно
звёзд», проверяло так:

```ts
&& !errorMessageToUser.includes('Недостаточно звёзд')
```

Переписал формулировку — потерял защиту. Плюс защита стояла в одном месте из
двадцати одного.

Правило: **условие для денег проверяй по данным и в одном месте**, а не по
строке, показанной человеку. Общий приём тот же, что с зеркалированием файлов:
одна дверь, а не двадцать одна копия правила.

## Направление «открыто/закрыто» выбирается по цене ошибки, а не привычкой

В одной итерации понадобились оба:

- **промо** — отказ ЗАКРЫТЫЙ: не смогли проверить, что человек уже получал —
  не выдаём. Ошибка стоит 1303 звезды безвозвратно.
- **возврат** — отказ ОТКРЫТЫЙ: не смогли проверить, было ли списание —
  возвращаем. Не вернуть человеку ЕГО ЖЕ деньги хуже, чем ошибочно создать
  восемь звёзд.

Правило: **выпиши обе цены в одной строке и выбери большую.** «Fail closed
всегда» — такое же суеверие, как «fail open всегда».

## Вырезая комментарии, сохраняй число строк

Искалка делала `s.replace(/\/\*[\s\S]*?\*\//g, '')` — и все номера строк ниже
уезжали вверх на длину комментария. Отчёт указывал на соседний код. Заметил
только когда пошёл читать «находку» и увидел там другое.

Правило: **`m => '\n'.repeat(число переносов в m)` вместо пустой строки.**
В этом проекте комментарии длинные (я сам их такими пишу), поэтому сдвиг
получается в десятки строк — достаточно, чтобы отчёт стал бессмысленным, но
недостаточно, чтобы это бросилось в глаза.

## Приоритет и размер класса — разные вопросы

Искалка требовала, чтобы в пределах двенадцати строк после вызова стояло
видимое действие. Условие хорошее для приоритета: наверх выходят места, где
человеку прямо что-то обещают. Но как оценка размера класса оно занизило
вчетверо — 8 мест против 30 при полном обходе.

Правило: **посчитай класс без фильтра приоритета, и только потом сортируй.**
Иначе «нашлось восемь» превращается в «их всего восемь», а это разные вещи.

## Долг списком лучше, чем починка вслепую

Тридцать мест, где результат денежной операции выбрасывается. Починил шесть —
те, где человеку прямо говорили неправду. Остальные требуют решения по
существу (повторить? отменить? сообщить?), и делать это без понимания пути —
верный способ сломать работающее.

Правило: **чини то, что понял, остальное запиши списком в тест.** Список
должен уметь три вещи: не пускать новые файлы, не давать расти счётчику в
старых и требовать удаления записи, когда файл почищен. Иначе он превращается
в индульгенцию.

## Контроль внутри того же замера, а не отдельной проверкой

Замер «списаний без следа работы» дал по видео 71–86%, по картинкам 2–10%.
Соблазн — объявить потерянными 67 544 звезды.

Спас контроль, встроенный в тот же замер: `neuro_photo` держит 97–100% во ВСЕ
семнадцать месяцев. Это доказывает, что способ рабочий, и одновременно
показывает, что у видео цифра означает не «не сделали», а «не записали».

Правило: **в замер закладывай ряд, который ОБЯЗАН выйти хорошим.** Если он
выходит плохим — сломан замер. Если хорошим — разница между рядами настоящая.
Без такого ряда любой процент можно прочитать двумя способами, и выберешь ты
тот, что интереснее.

## «Мы этого не знаем» — законный вывод итерации

Дважды подряд вывод звучал так: отличить «сделали, но не записали» от «не
сделали» нечем. Тянет дожать до находки — цифры-то крупные.

Правило: **если данные не различают две версии, так и напиши, и почини
различимость.** Названная неизвестность полезнее выдуманной уверенности: она
превращается в измеримое через месяц. Выдуманная — в поправку через день.

## Меняя поведение, чини тесты, которые закрепляли старое

Правка уронила два теста: один требовал `logger.warn`, другой — возврата
`undefined`. Оба закрепляли ровно то поведение, которое оказалось дефектом.

Правило: **упавший тест — это вопрос «кто прав», а не «как починить».** Если
прав код — перепиши тест И объясни в нём, почему прежнее ожидание было
неверным. Удалять нельзя: пропадёт причина. Молча обновлять снимок нельзя:
проверка перестанет что-либо значить.

## Self-check before reporting done

1. Does the changed component actually render? (live DOM, not build)
2. Did the deploy pick up the commit? (compare deployed commitHash to HEAD)
3. Does the endpoint answer from the caller's origin? (CORS, auth headers)
4. For data: counts AND exact sums as text, not counts alone.
5. Say plainly what was NOT verified. A green build is not verification.
