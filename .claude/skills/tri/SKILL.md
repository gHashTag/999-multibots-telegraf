# /tri — человек ↔ человек, агенты между ними в помощь

Имя дал владелец 20.09.2026: **tri** — это команда, где на концах два живых
человека, а агенты стоят между ними и помогают. Не агенты вместо людей.

Подробный разбор ловушек — в скиле **`rainbow-bridge`**. Здесь только порядок
прогона и роли; правило живёт в одном месте.

## Три роли (слова владельца, 21.09.2026)

> «один делает запрос на функцию, второй её предоставляет, третий смотрит
> целостность ответа на вопрос и корректирует в случае проблемы»

| Роль            | Кто                                      | Что делает                                          |
| --------------- | ---------------------------------------- | --------------------------------------------------- |
| **Просящий**    | аккаунт стороны A (юзер-бот, `crm_duet`) | шлёт команду / вопрос / файл боту фермы             |
| **Исполняющий** | бот фермы и агент рендера                | отвечает, как ответил бы живому человеку            |
| **Судья**       | агент, читающий переписку (`tg_history`) | сверяет ответ с вопросом, при сбое — в улей и чинит |

## Порядок прогона

```bash
tri bridge 144022504 435572800   # 1. машина: боты, профили обеих сторон, агент на двух поверхностях
tri commands                     # 2. какие команды меню ещё НИКТО не нажимал
```

1. **`tri bridge`** — минута, параллельно, никому не пишет. Смотреть только
   жёлтые и красные строки. Раздел «профили» говорит, готова ли сторона к
   **реальной работе**: продавец ли она (подключён ли Telegram), читается ли
   живой кошелёк, знает ли её рендер. У каждого пробела — чьё нажатие его
   закрывает. Код входа вводит сам человек; начислять токены решает владелец.
2. **`tri commands`** — по переписке владельца с каждым ботом: ✓ ответил,
   ✗ молчит, · не пробовали. Строки «·» — список нажатий для людей.
3. **Люди** проходят только то, что машина не может: настоящее голосовое в обе
   стороны, настоящий `.md` и `.pdf`, оплату через свою кассу, мини-апп со
   своего аккаунта.
4. **Судья**: после нажатий — снова `tri commands`; красное уходит в улей
   (`bot-errors`, `client-unanswered` пишутся сами).

### Бот на нашем Bot API сервере (с 22.09.2026)

**`tri` — только из копии текущего `main`.** Хост выбирается по токену
(`scripts/lib/telegram-api.cjs`) только в свежем коде. 22.09 `tri bridge` из
устаревшей основной копии спросил `api.telegram.org` про только что
перенесённого бота — и облако через три минуты после `logOut` взяло его
обратно (никаких «10 минут»). Перед `tri`: `git fetch && git merge --ff-only
origin/main`, если копия на `main` и чистая.

`tri botapi` — какие боты на нашем сервере и согласны ли три списка (бот,
рендер, допуск сервера), со следующим шагом для каждого расхождения.
`tri bridge`, `tri pack`, `tri commands` сами откажутся запускаться из копии,
отставшей от `main` в файлах выбора хоста (выход 3).

С ноутбука такой бот видится строкой `· id … on our Bot API server; not
reachable from here` — это не поломка: сервер слушает только приватную сеть
Railway. Его здоровье — строки `[bot-api]` в логе бота. Какие боты переехали и
как откатить — `deployment/telegram-bot-api/README.md`, шаг 4b.

## Живой диалог двух сторон: `crm_duet`

То, что владелец хочет **видеть в личке** — юзер-боты разговаривают, — уже
есть: инструмент `crm_duet` (рендер, `crm-duet-tool.ts`, спека
`t27 specs/automation/crm-duet.t27`). Продавец владельца пишет из его сессии,
модель-персона отвечает из сессии второй стороны, материал делается для её
настоящего продукта. Судья — `crm_duet_status`: транскрипт, каждый вызванный
инструмент (ok / fail), число платных генераций.

```bash
# через MCP как владелец (скрипт hive.cjs из скилла mcp-owner-access)
crm_duet        {"buyer":"<id>","turns":2,"dry_run":true}    # сначала пробный: ничего не уходит
crm_duet_status {}                                           # транскрипт и инструменты
crm_duet        {"buyer":"<id>","turns":4}                   # настоящий: видно в обеих личках
```

**Когда можно.** Обе стороны сами подключили свои аккаунты в приложении
(`tg_sessions`), и владелец **разрешил этот запуск в чате** — каждый запуск,
не «вообще». Платные генерации идут с баланса продавца. Сначала пробный прогон:
код меняется каждый день, а кривое сообщение с живого аккаунта не вернуть.

**Персона — не человек.** Её ответы — догадки модели. В профиль клиента
(`crm_client_profile`, статус «черновик») они фактами не записываются: ответы
на вопросы знакомства даёт сам человек.

## Чего /tri НЕ делает (и почему)

- **Не пишет от чужого имени без двух условий** — аккаунт подключён самим
  человеком и владелец разрешил именно этот запуск. Иначе — только нажатие
  живого человека.
- **Не шлёт от аккаунта владельца без его разрешения.** Вне дуэта каждая
  отправка с его аккаунта — карточка с кнопкой «Отправить».

## Проверка перед тем, как сказать «работает»

«Работает» — это когда живой человек с телефона получил правильный ответ, а не
когда тест зелёный. Доказательство — строка ✓ в `tri commands` или цитата из
`tg_history`, а не вывод `vitest`.
