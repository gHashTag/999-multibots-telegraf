# Доступ к аккаунту владельца через MCP

## Правило

**«Мне нужна ваша сессия» — почти всегда неправда.** У проекта есть
server-to-server вход, и владелец ожидает, что им пользуются.

Я говорил «не могу, требуется подпись Telegram» **пять раз за смену** — про
баланс, про профиль, про одобрение, про сохранение SOUL, про вызов агента. Во
всех пяти случаях механизм был, и владелец в итоге сказал прямо: _«ты должен
уметь подключаться к моему аккаунту через MCP»_.

Отказ, у которого есть обход, — это не осторожность, а недоделанная работа.

## Что это за вход

`RENDER_API_KEY` сервиса `vibee-render`. Сервер принимает его как
`X-Api-Key` и считает вызывающего доверенным; личность владельца при этом
передаётся **явно**, параметром `telegram_id`.

Так уже устроены `DELETE /api/feed/:id`, `POST /api/feed/publish`,
`GET /api/feed/pending` и весь `/mcp`.

## ДВА РАЗНЫХ КЛЮЧА, И ЭТО НЕ ОДНО И ТО ЖЕ

Замерено 07.09.2026 на живом сервисе. Навык раньше говорил, что `/mcp`
принимает `X-Api-Key` — это неправда, и стоило двух запросов вслепую:

    curl /mcp -H "X-Api-Key: …"     →  401
    {"error":{"code":-32001,"message":"Нужна подпись Telegram
     (X-Telegram-Init-Data) или корректный ключ агента (X-Agent-Key)"}}

Правильно так:

| Куда                                 | Заголовок     | Откуда значение                         |
| ------------------------------------ | ------------- | --------------------------------------- |
| `/mcp` (88 инструментов, 16.09.2026) | `X-Agent-Key` | `AGENT_KEYS`, формат `ключ:telegram_id` |
| `/api/feed/*`, `/api/tg/connect/*`   | `X-Api-Key`   | `RENDER_API_KEY`                        |

Ключ агента НЕСЁТ личность в себе — отдельный `telegram_id` ему не нужен, и
`whoami` это подтверждает. `RENDER_API_KEY` личности не несёт, поэтому
маршруты из второй строки требуют `telegram_id` параметром.

## Как брать ключи (единственный допустимый способ)

Ключ **не попадает ни в контекст, ни в файлы, ни в вывод**. Он живёт внутри
скрипта, в переменной, одну команду:

```bash
KEY=$( (railway service vibee-render >/dev/null 2>&1; railway variables --kv 2>/dev/null) \
       | grep -E '^RENDER_API_KEY=' | cut -d= -f2- )

# ключ агента — для /mcp. Берём первый и только его идентификатор до двоеточия.
AK=$( (railway service vibee-render >/dev/null 2>&1; railway variables --kv 2>/dev/null) \
      | grep -E '^AGENT_KEYS=' | cut -d= -f2- | cut -d, -f1 | cut -d: -f1 )
```

Так уже сделано в `bin/tri feed` и `bin/tri feed-hide` — новые команды
повторяют этот приём, а не изобретают свой.

**Никогда:** не печатать значение, не писать в файл, не подставлять в
сообщение коммита, не показывать в отчёте. `grep '^ИМЯ='` без значения —
можно, само значение — нет.

## Что через это можно

```bash
BASE="https://vibee-render-production.up.railway.app"
OWNER=144022504     # telegram_id владельца

# инструменты агента (тот же реестр, что у Claude/Codex снаружи)
curl -s "$BASE/mcp" -H "X-Agent-Key: $AK" -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'

# вызов конкретного инструмента
curl -s "$BASE/mcp" -H "X-Agent-Key: $AK" -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/call",
       "params":{"name":"soul_get","arguments":{}}}'

# маршруты, принимающие явный telegram_id
curl -s "$BASE/api/feed/pending?telegram_id=$OWNER" -H "X-Api-Key: $KEY"
curl -s -X DELETE "$BASE/api/feed/17?telegram_id=$OWNER" -H "X-Api-Key: $KEY"
```

## Чего это НЕ отменяет

- **Коды авторизации и пароли я не ввожу.** Ключ сервиса — не учётные данные
  человека: он лежит в окружении, которым владелец сам управляет, и его
  ротация ничего не отнимает у человека.
- **Смета вперёд** для трат и видимого снаружи остаётся. Доступ не равен
  разрешению: скрыть посты можно только по названному id, тратить кредиты —
  после сметы.
- **Ничего необратимого.** Скрытие вместо удаления, отдельная копия вместо
  правки чужого.

## Проверка, которую этот вход открывает

Раньше я писал «проверено тестами, глазами нельзя — нужна сессия». Теперь
цепочки проверяются целиком и бесплатно:

```bash
# опубликовать СКРЫТО, как это делает агент
curl -s -X POST "$BASE/api/feed/publish" -H "X-Api-Key: $KEY" \
  -H 'Content-Type: application/json' \
  -d "{\"telegram_id\":\"$OWNER\",\"is_public\":false,\"name\":\"проверка\",\"video_url\":\"https://example.com/x.mp4\"}"

# увидеть его в «ждут одобрения», одобрить, убрать
curl -s "$BASE/api/feed/pending?telegram_id=$OWNER" -H "X-Api-Key: $KEY"
```

Именно так нашёлся дефект, который тесты не видели: `/api/feed/pending`
сверялся с ПОЛНЫМ адресом, и любой параметр уводил запрос в общий сторож
ленты с ответом «лента такого не обслуживает». Веб зовёт без параметров и
работал — поэтому и не падало.

## Признак, что пора загрузить этот скилл

Любая фраза вида «нужна ваша сессия», «войдите по коду», «без подписи не
могу», «сохранить не могу — требует вашей подписи». Прежде чем её написать,
проверь: маршрут принимает `X-Api-Key`? У инструмента есть аналог в `/mcp`
(тогда `X-Agent-Key`)? Почти всегда — да.

## Ответ агента приходит ПОТОКОМ, а не одним JSON

`POST /api/agent/chat` отдаёт NDJSON: строка на событие,
`{"тип":"размышление"|"инструмент"|"результат"|"текст"|"готово"}`. Ответ
человеку — это склейка `текст`. `json.load` на всём теле падает с
«Extra data», и это не поломка сервера.

Тело запроса — `{"messages":[{"role":"user","content":"…"}]}`; поле
`message` в единственном числе сервер отвергает.

## Замер 16.09.2026: 88 инструментов, и `crm_money` среди них НЕТ

Дверь проверена ещё раз, все три варианта значения перебраны: в заголовок
идёт часть ДО двоеточия, целиком и часть после — отказ. В проде 88
инструментов, 39 из них CRM и Telegram.

`crm_money` — воронка денег, написанная два витка назад, — в этом списке
отсутствует. Она живёт в ветке, которая отстала от main на 132 коммита и не
может быть слита как есть (форма 34 в скилле blind-guards). Владелец не может
ею пользоваться, и никакие зелёные тесты этого не показывают.

**Осторожно с самим замером.** Первая попытка сосчитать `AGENT_KEYS` дала
«0 записей»: переменную передали питону АРГУМЕНТОМ (`python3 -c "…" AK=$AK`),
а читали из окружения. Ноль от сломанного замера неотличим от настоящего —
пока не спросишь у того же замера длину значения.
