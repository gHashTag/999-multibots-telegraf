## 2. Метод: как здесь принято работать

Один цикл = одна тема. Восемь шагов, ни один не пропускается.

**1. Замер, а не догадка.** Любое утверждение о проде подтверждается запросом
к данным. Код показывает замысел, данные — результат; расходятся они постоянно.

**2. Знаменатель обязателен.** «Нашлось 169 мест» — заготовка. «169 из 479, и
большинство из них молчат правильно» — результат. Число без знаменателя и без
оговорки о составе публиковать нельзя.

**3. Отрицательный контроль.** В замер закладывается ряд, который ОБЯЗАН выйти
хорошим. Вышел плохим — сломан замер. Пример: `neuro_photo` держит 97–100%
следов во все 17 месяцев, и это доказывает, что 71% у видео — про запись, а не
про потерю.

**4. Самопроверка искалки.** Искатель обязан начинаться с проверки на
заведомо-положительном и заведомо-отрицательном образце и падать с кодом 2,
если она не сработала. Без этого «ничего не найдено» означает «ничего не
искали» — за неделю это случалось четыре раза.

Здесь раньше стояло «**каждый** `scripts/probe-*.cjs` начинается с такой
проверки». Это было неверно, и написал это я: на 04.09.2026 контроль есть у
**8 из 38**. Требование осталось требованием, но описанием положения дел оно не
было — а прочитавший его считал искателей проверенными и не перепроверял.

Текущее состояние показывает `tri probes`. Он делит по тому, где контроль
возможен дёшево: **5 искателей по исходникам** без контроля (образец лежит в
самом файле — там это обязательно, и на них стоит потолок ратчета) и **25 по
живым данным** (стабильного образца может не быть вовсе; там честнее оговорка
в отчёте, чем выдуманный контроль). Образец правильного контроля —
`scripts/probe-id-concat.cjs`.

Важно, какой именно вопрос задаёт самопроверка. Все 38 печатают размер
популяции — это ответ на «я запустился?». Ответ на «я **вижу** свой предмет?»
даёт только образец, который ОБЯЗАН найтись. Первый вопрос не заменяет второго:
наблюдатель за сетью имел проверку первого рода — и с 27.08 по 04.09.2026, до
первого запуска, не видел axios вовсе.

**5. Правка минимальная и объяснённая.** В комментарии — что было, чем это
стоило и почему теперь так. Комментарий пишется для того, кто откроет файл
через полгода.

**6. Тест с мутацией.** Тест без проверки мутацией не считается написанным:
сломай именно то свойство, которое он стережёт, и убедись, что падает именно
эта проверка. Мок легко маскирует мутацию — см. раздел в hard-won.

**7. Гейт.** `npm run test:gate` сравнивает МНОЖЕСТВА имён пройденных тестов, а
не их число. Переименование выглядит как регрессия: сверь, что замена
покрывает то же и точнее, обнови снимок и скажи об этом в отчёте. Молча
обновлять снимок нельзя.

**8. PR и отчёт.** Ветка → PR → squash-merge. В отчёте: что измерено, что
сделано, **чего это не чинит**, и три варианта следующего лупа.

### Запрещено без владельца

Перевыпуск ключей. Изменение чужих балансов. Удаление данных. Рассылка живым
людям. Регистрация Inngest-функций, меняющих статусы. `git push --force`.
Запись в прод вообще: все замеры — только SELECT.

### Главные уроки этапа

1. Отсутствие сигнала — НЕ отрицательный ответ. Пустой grep, несвежая
   ссылка, не загрузившийся модуль. У проверки должно быть ТРИ исхода.
2. Живость функции нельзя установить поиском по тексту. Только живой запрос.
3. Swift сообщает о таймауте вывода типов как об ошибке `Binding` и о
   присваивании там, где идёт чтение. Лечить размер выражения, не строку.
4. Буква `ё` НЕ входит в диапазон `а-я` — grep обрезает на ней имена.
5. Локальный main может молча отстать на сотню коммитов; ветку брать ОТ
   origin/main, и мерить не по локальной копии.

### Lessons of 2026-09-27: signing in to networks through the agent's browser

6. **A page's error message is not the server's verdict.** Habr said «Неверный
   код» three times while the code was right: the endpoint's own JSON at
   `/ru/ident/verify/check` answered «Сессия входа истекла» -- the sign-in
   session had expired. Ask the endpoint, not the rendered text, or you treat
   the wrong illness: I had already begun suspecting the mail reading and the
   typing.
7. **Gmail's collapsed thread does not show the newest message.** The snippet
   kept serving the previous code while a newer one was already in the thread.
   The reliable read is the Atom feed
   `https://mail.google.com/mail/u/0/feed/atom`: a plain GET, every entry
   carries `<summary>` and `<issued>`, and no click inside Gmail is needed --
   which matters, because the render's own guard forbids acting on
   `mail.google.com` anyway.
8. **`input.value` set from JS is not input.** Habr's verify page has two forms
   and NO button inside either: "Войти" sits outside and is handled by script.
   A DOM write is invisible to the page's model, so there is nothing to submit.
   The only truthful input is real keystrokes: `browser_click` on the field,
   then `browser_type`. And `i.focus(); i.select()` first, or the old value is
   concatenated with the new one -- that is how "159010159010" happened.
9. **`browser_evaluate` on the render throws on a top-level `await`** ("page
   threw: Uncaught") but it DOES resolve a returned promise. The wrapper is an
   IIFE with `return fetch(...).then(...)`; `tri mcp eval --example` prints it.
10. **Going back to an open tab needs its own tool.** While `browser_open` was
    the only way back, returning cost a second tab of the same site; at the cap
    that second tab was paid for with the token-bearing page of the sign-in in
    progress. `browser_focus_tab` (PR #3143) closed that, and it proved itself
    the same day in exactly the situation that produced it.
11. **The person still types the password, and that is a tool, not a dead end.**
    `browser_ask_input` with `kind: password` and the field's coordinates puts
    the request on their screen: the value reaches the page without passing
    through me or through the chat. Asking for a password in chat is forbidden
    -- the tool's own answer says so in as many words.

### Урок 07.09.2026: защита, которая сама и есть авария

В итерации 1 я закрыл отказ в обслуживании на входе: промах кода гасил живые
коды ВСЕХ людей платформы. Поставил тормоз с ключом `socket.remoteAddress`.

В итерации 2 собрался тем же тормозом закрыть остальные двери (`/api/auth/*`) —
и на полпути проверил собственную правку. **Railway обрывает TLS на своём краю
и идёт в контейнер сам, поэтому `remoteAddress` — адрес прокси, ОДИН НА ВСЕХ.**
Десять попыток в минуту на такой ключ — это не тормоз злоумышленнику, а запрет
входа всей платформе: ровно тот отказ в обслуживании, который я чинил, только
теперь встроенный в защиту и без всякого нападающего.

Правило, которое из этого следует:

> **У любого лимита спроси: чей это ключ и сколько людей за ним стоит.**
> Ключ из соединения за прокси — это ключ «все». Ключ из заголовка —
> подделываемый. Годится только пара: узкий лимит на клиента
> (`X-Forwarded-For`, слева) плюс широкий потолок на соединение.

Проверять: `tri throttle` — показывает, чем ключуются лимиты и есть ли
разделение клиент/канал.

Второй слой урока: **правка, сделанная по образцу вчерашней правки, наследует
и её незамеченные допущения.** Тормоз был верен для `pair/claim`, где риск —
подбор, и грубость лимита была платой. Для `/api/auth/refresh`, куда ходит
каждый живой клиент раз в десять минут, та же грубость — отключение сервиса.
Один и тот же код, противоположные последствия; различает их не код, а вопрос
«кто сюда ходит в норме».

### Урок 07.09.2026: тест, названный не тем, что он проверяет

Мутация «поменять порядок начислений» выжила при зелёном тесте с именем
«упёршийся в лимит клиента не копит попытки в потолке канала». Тест проверял
другое — и имя лгало о покрытии.

Что сделал: переименовал под реально закреплённое свойство и **записал прямо в
тесте, какое свойство закреплять НЕ стал и почему** (когда канал закрыт, он
закрыт для всех, и счётчик клиента ничего не меняет — проверка без
последствий). Незакрытая мутация с объяснением честнее, чем тест, дописанный
ради зелёной галочки.

### Урок 07.09.2026: «различить невозможно» — почти всегда неправда

`rotateRefreshToken` писал: честный повтор и кражу «снаружи различить
невозможно», и выбирал жёсткое чтение — гасил всю семью. Из-за этого две
вкладки одного браузера (общий refresh в localStorage, общий таймер, разница в
миллисекунды) ежедневно выбрасывали человека из приложения, и вернуться он мог
только через восьмизначный код.

Различить было можно — не по факту повтора, а по **промежутку**: вкладки
сталкиваются за миллисекунды, вор приходит между обновлениями клиента, то есть
через минуты. Правило:

> Когда код объявляет два случая неразличимыми, спроси, по какому признаку.
> Обычно неразличимы они по одному признаку, а рядом лежит второй — время,
> порядок, источник, — по которому они расходятся на порядки.

Проверять: `tri session` — сроки и то, как на гонку отвечают все три клиента.

### Урок 07.09.2026: срез «плюс N символов» — ненадёжная граница

Дважды за один цикл: тест брал `indexOf(метка) + 400` и захватывал соседний
блок. Первый раз упал на чужом коде, второй — тоже. Опаснее обратное: такой
срез может **позеленеть** на чужом коде. Границу задавать концом конструкции
(`return true`, следующий `guard`), а длину среза проверять отдельно
(`expect(блок.length).toBeGreaterThan(...)`) — иначе пустая строка проходит все
`not.toContain`.

### Урок 07.09.2026: тест, который меряет себя

Проверка границы окна вида `внутри(КОНСТАНТА - 1)` / `внутри(КОНСТАНТА + 1)`
доказывает форму и НЕ доказывает величину: растяни константу до суток — тест
поедет следом и останется зелёным. Мутация это и показала. К относительной
проверке всегда добавлять абсолютную: `expect(КОНСТАНТА).toBeLessThanOrEqual(60)`
и случай в живых секундах.

### Урок 07.09.2026 (повтор ошибки): кириллица в bash — уверенная ложь

Третий раз за цикл. `Ф="${F%%:*}"` даёт `command not found`, но цикл крутится
дальше и печатает вывод ветки `else`: `tri session` объявил «НЕТ» про все три
клиента, у которых защита была на месте. Ошибка в скрипте выглядела как
находка. Имена в bash — ТОЛЬКО ASCII, и у каждой проверки файла должно быть
третье состояние «файла нет — проверка не выполнена».

### Урок 07.09.2026: `CREATE TABLE IF NOT EXISTS` — это не описание базы

Я прочитал grep и решил, что вставка кода спаривания не заполняет две колонки
`NOT NULL`, то есть выдача кодов падает. Замер по живой базе показал: колонки
принадлежат ДРУГОЙ таблице, а сама база старше объявления в коде.

Отсюда два правила:

> На существующей базе `CREATE TABLE IF NOT EXISTS` **не выполняется**.
> Объявление в коде и схема в проде расходятся молча и живут так годами.
> Ошибка вылезает в день пересоздания базы — новое окружение, стенд,
> восстановление, — то есть в худший день из возможных.

> Номер строки из grep не говорит, к какому блоку она относится. Прежде чем

## Урок 16.09.2026: веб достаётся curl-ом, когда WebFetch мёртв

В настройках владельца псевдонимы моделей указывают на `glm-*`, которых у
аккаунта нет. Из-за этого умирают `WebSearch`, `WebFetch` и классификатор
браузера. Долгое время это записывалось как «веб-исследование невозможно» —
и это было неверно.

Публичная страница берётся `curl` из Bash и разбирается своим скриптом: так
за минуту прочитан весь журнал Bot API за 2026 год и полный справочник на
860 КБ — то, что `WebFetch` не сделал бы и при живой модели. Файл кладётся в
scratchpad и передаётся агентам ПУТЁМ: они читают его сами, и факты у всех
одни. Для справочника Telegram теперь есть `tri api <имя>`.

Чего curl НЕ берёт: страницы, которые рисуются скриптом на клиенте. Цены
конкурентов (`salebot.pro/prices`, `puzzlebot.top/tariffs`) приходят пустыми.
Это повод сказать «не проверено», а не повод выдумать число.

**Дата сессии в системном приглашении — не то же самое, что время сервера.**

## Проверяй, что починка ДОЕХАЛА до прода, а не только до ветки

16.09.2026, пятнадцатый виток подряд правок в одной ветке. Спросил у прода
список инструментов — и `crm_money`, написанного час назад, там нет. Дальше
проверил главное:

```
в main есть isBorrowedConnection?            0
в main есть «счёт гасится после зачисления»?  0
```

То есть **в проде живы обе денежные дыры**: каждый платёж звёздами
откатывается (деньги взяты, токены не пришли), а погашенный заранее счёт
делает тот платёж невосстановимым. Починки лежат в ветке, потому что PR ждёт
слова владельца — и это правильно, сливать без него нельзя.

**Чего делать нельзя:** говорить «починено», имея в виду «починено в ветке».
Для владельца «починено» значит «работает у клиентов».

**Что делать каждый виток, одной командой:**

```bash
tri waiting     # что лежит в открытом PR: деньги / видно клиенту / тесты
```

И раз в несколько витков — спросить сам прод: `tools/list` через `/mcp`,
`git show origin/main:<файл> | grep <признак починки>`. Ветка зелена — это про
меня; прод — про людей.

**Отдельно про отчёт.** Если дыра в проде жива, это первая строка отчёта, а не
сноска. Даже если она не выстрелила: «не выстрелила» значит «никто не платил»,
а не «не страшно».

## Что делать в цикле, когда владелец спит (24.09.2026)

Правило, выведенное за три прохода: **не нажимать за него то, что по нашему же
решению нажимает только он.** Переключатель AUTO, отправка карточки, создание
группы — это его дверь. Ночью вместо этого:

1. **Снять аномалии** — три сервиса, красные ворота на main, диск. Красный
   шлюз на main блокирует ВСЕХ: это всегда первое.
2. **Проверить своё вчерашнее** на дыры. За три ночи так нашлись: инструмент,
   которым модель могла включить отправку без человека; мой же мерж, молча
   заменивший чужую починку; жёсткое число в тесте, ломавшееся при удалении
   функций.
3. **Сделать то, что снимает страх нажать.** Если метрика говорит «0% без
   тебя» — дело не в метрике, а в том, что кнопку страшно трогать. Ответ не

### Lesson of 01.10.2026: a guard that skips itself is not a guard (CRM mobile loop, tick 7)

A cron loop keeps every mutation a past tick proved in
`.claude/loop-state/<name>-mutants.json`, and `tri loop-guard start`
re-runs them all. Tick 6 rewrote one line that an entry was anchored to.
`tri mutants` refuses a list with any stale anchor, so tick 7 started with
**all 27 guards unchecked**, and loop-guard printed a `warn` and GO.
**Unchecked is not green.**

- `start`: a stale anchor now stops the tick.
- `end`: the lock is kept while the anchors do not match the code or the
  tree is dirty. The tick that moved the code knows the new line; the next
  tick would have to guess.

The new `end` check caught two more stale anchors in the same tick's own
change, before its commit. Run `tri mutants --check <list>` after every edit
to guarded code. The details live in the header of
`bin/helpers/loop-guard.sh`; they are not copied here.

A proven batch goes into the guard list with `tri mutants --adopt
<batch.json> <guards.json>`, run where the batch ran. The hand-made copy
it replaces once rewrote the whole list's indent.

**Wrapping code re-indents its guards.** Tick 10 wrapped a heading and its
list in a `<section>`: not a token changed, but a past mutation anchored
inside went stale, and `--adopt` refused the new batch (as it should).
`tri mutants --reanchor <guards.json>`, run from the repo root, follows an
indent-only move: the `from` found once with every line shifted by the same
amount, and `to` shifted with it. A changed token stays stale and is named;
someone decides what that mutation should now be.

**A guard is adopted with the files that killed it; the next start runs it
with the marker.** Tick 11 adopted three guards that only
`crmMatches.test.ts` killed. The `<!-- loop-tests: -->` marker did not name
that file, so the next start would have reported "a past mutation SURVIVES",
a false regression blamed on the wrong tick. `tri loop-guard end` now runs
the guards added since `start` under the marker and stops on a survivor
(ten guards took 95 s). Add the killing test file to the marker.

**Never edit a file while a mutation batch runs in the background.** The
restore writes back the pre-mutation snapshot. `tri mutants` now keeps such
an edit as `<file>.edited-during-mutants`, but that is a rescue, not a way
to work.

**Commit the feature before you mutate it by hand.** `git checkout <file>`
restores the INDEX, not "the line I changed": on 03.10.2026 (PR #3436) two
hand mutations of the Fastfile and `tri` were reverted that way, and the
revert erased the uncommitted lane and command they were testing. The
verdicts (3, 1 and 5 red) stood; the code had to be re-applied from notes.
`git add` or commit first; then the revert lands on your version.
Then run the suite ON THE COMMIT before reading any mutation: pre-commit
prettier rewraps code, and a test that greps the source can turn red in the
commit itself. On 03.10 a five-line `while (` broke such a test, and two
"red" mutations meant nothing (#3444). Grep source with whitespace collapsed.

**Before you retry a failed push or fetch, ask `tri online`.** On 03.10.2026
github.com stopped resolving mid-tick; three git commands failed in turn and
each was retried by hand. `tri online` (#3442) says which kind of failure it
is: exit 1 = the network (wait: `tri online --wait 300`), 3 = GitHub refuses
the credentials (a retry never helps, look), 4 = unrecognised (read the line).
Chain it WITHOUT a pipe: `./tri online --wait 300 && git push`. Written as
`./tri online --wait 120 | tail -1 && git push`, the `&&` reads `tail`'s exit
code, so the push goes ahead with the network down (done exactly so the same
tick, caught on reading back).

**Run the system Ruby before you trust a regex in fastlane code.** Ruby 3.2+
memoises regex backtracking; `/usr/bin/ruby` 2.6 does not. `TeamGroup.scrub`
took 52 s on 6000 characters of `a@` there and 1 ms on Ruby 4 (#3443).

**A test of a network tool runs with the network off.** The no-git test of
`tri online` asked the real DNS and App Store Connect, so it would fail in
the very outage the tool diagnoses (bee review of #3445); every host is now
an environment override and the test pins the whole verdict (#3447).

(`bin/helpers/fetch.sh`) warns with the ref's age and keeps the code; a test
fails on any helper that fetches around it. The age comes from the remote
ref's reflog, NOT `FETCH_HEAD`'s mtime: a failed fetch rewrites that file and
it reads "0 min ago" (caught by running the first draft). And parse only the
number inside `@{...}`: `tr -dc 0-9` kept the digits of `fix/abc-123` too and
read a negative age (bee review of #3448). **A digit filter over a string that
holds a name is a parser for the name as well.**

**Audit the class, then fix the stragglers.** After `tfetch`, every gh, railway
and curl call in tri whose stderr goes to `/dev/null` was read for one
question: does a failure print like "nothing there"? 18 of 19 already said
"no verdict" (exit 2). The one that did not was `tri inflight`, the FIRST
command of every cycle: a failed railway call printed a blank deployment line
("nothing deployed"). Now "unknown" and "none" are separate words, and
`scripts/tri-inflight.test.ts` proves it with gh and railway stubbed on PATH -
the pattern for testing any tri helper that talks to a service, offline.

**An upload is not a delivery.** `tri iphone testflight --yes` uploads with
`skip_waiting_for_build_processing` (processing takes minutes to an hour), so
"uploaded" left the owner opening an empty TestFlight. `tri iphone processed
[--wait MIN]` asks Apple (read-only, no --yes): 0 ready, 1 refused/expired,
4 not yet, 3 no app record; waiting, it posts a Mac notification. After the
first upload: `tri iphone processed --wait 60`. The guard test over the
hand-typed `modes:` list caught the new word missing from the refusal.

**"The newest build" is the wrong build right after an upload.** App Store
Connect lists an upload minutes after it, so the first `processed --wait 60`
answered "nothing uploaded" at once and never waited, and a second upload
would have read the PREVIOUS build (VALID) as "ready". `beta` now writes the
number it sent to `build/last-upload`, and `processed` watches that number,
waiting while it is unlisted or PROCESSING. A wait that runs out notifies
too; Apple's text goes to osascript as an argument, never into the script.
Ask of every "wait for X": what does the world look like in the first minute,
before X even exists?

### Lesson of 02.10.2026 (iOS loop, iteration 11): a tool that reports "passed" for fewer than it was given
